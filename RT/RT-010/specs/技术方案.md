# 技术方案

## 模块拓扑

```
scripts/
├─ cwk_entity_catalog.py       # 新增：目录构建、家族规则、raw 精确锚点扩展
├─ cwk_wiki_search_index.py    # 修改：构建索引时联动构建目录，绑定 hash
├─ cwk_wiki_query.py           # 修改：目录加载 + 实体解析 + scope 硬过滤
└─ cwk_sync_mirror_to_docdb.py # 修改：排除本地 catalog/cache/registry 覆盖
tests/
├─ test_wiki_entity_scope.py   # 新增：property/synthetic 与真实镜像样本
├─ test_rt010_registry_binding.py # 新增：registry 三处审计绑定与 Local-First 排除
└─ test_cloud_first_index_restore.py # 修改：暂停 cloud 路径兼容回归
config/
└─ entity-family-registry.json # 仓库版本化的跨类型合并唯一真源
knowledge/工作协同镜像/wiki/_system/
├─ entity-catalog.json(.gz)    # LOCAL-ONLY 派生工件：本轮完整目录
├─ entity-catalog-meta.json    # LOCAL-ONLY 元数据（版本、语义 hash、构建信息）
├─ entity-anchors-cache.json   # LOCAL-ONLY 匿名锚点缓存（幂等重扫）
├─ entity-family-registry.json # 可选本地实验覆盖，被 sync 排除
└─ search-index.json           # 索引在 manifest 中新增 `entity_catalog_sha256`
```

**Local-First 边界**：以上标为 LOCAL-ONLY 的四个派生 / 覆盖工件
（`entity-catalog.json{,.gz}`、`entity-catalog-meta.json`、
`entity-anchors-cache.json`、`wiki/_system/entity-family-registry.json`）
**不会** 出现在 `changed_relative_paths`，也**不会** 被
`cwk_sync_mirror_to_docdb.iter_items` 上云。查询运行时以 search index
payload 的 `entity_catalog_sha256` 绑定经过自身校验的 catalog；
`index-meta.json / manifest.json` 保存相同构建摘要用于审计，但不作为
重复授权源。catalog 缺失、损坏或 SHA 不匹配时走 catalog-mismatch
fail-closed 路径。

`cwk_wiki_search_index.build_index` 在写入索引前调用
`cwk_entity_catalog.build_catalog(mirror)`，将 catalog 的 hash/schema/
registry version 与稳定 registry source 写入 search index payload、
`index-meta.json` 与 `manifest.json`；source 作为三处构建期审计标签并
参与 index SHA。catalog 自身以 registry version/applied 决策及证据表达
授权语义，不重复保存来源路径。索引与目录都是纯派生工件，其他数据源
（raw、summaries）保持不可变。

## 数据流

```text
wiki/summaries/*.md
  └─ 候选实体 段落  ─┐
                     │
raw/**/*.md ────────┤ → cwk_entity_catalog.build_catalog
                     │       (family rules + raw anchor extension)
                     │
                     ▼
        wiki/_system/entity-catalog.json(.gz)
                     │
                     ▼
        cwk_wiki_search_index.build_index
        （在 index payload / meta / manifest 里绑定 catalog 快照）
                     │
                     ▼
        cwk_wiki_query.query_mirror
        （resolver + scope hard filter + intent 支持度）
```

## Catalog 构建

### Surface 采集

对每个 summary 解析 `## 候选实体` 段落里的 `- text `type``：
- `surface_text` → clean → `normalize_surface`；
- `entity_type` 从 `` `type` `` 反引号读取，仅接受 `{system, project,
  product, person, organization, other}`；
- `origin = "summary_candidate"`；
- 在 `raw_provenance[(entity_type, normalized)]` 累加 `{report_id, quote}`。

### 家族合并（general rules）

1. **精确合并**：`(entity_type, normalized)` 完全相同直接同族；
2. **括号缩写**（`parenthetical_acronym`）：
   - 正则 `^(?P<acr>[A-Z][A-Z0-9._-]{1,4})[（(](?P<full>[^)）]+)[)）]$`
     或 `^(?P<full>[^（(]+)[（(](?P<acr>[A-Z][A-Z0-9._-]{1,4})[)）]$`；
   - `acr` 与完整声明保留同一 entity_type 的家族关系；若 `full` 是裸通用
     名称，则其独立 surface 只标记 `generic_candidate`，不得自动成为
     hard alias；
   - `provenance = {rule: "parenthetical_acronym", source_report_id, surface}`；
3. **受控通用后缀**（`controlled_generic_suffix`）：
   - `system.suffixes = {"系统", "平台", "体系"}`；
   - `project.suffixes = {"项目", "项目组"}`；
   - 若 `long = short + suffix` 且 `short` 亦为**同 type 已声明**的
     entity，则合入 `short` 的族（provenance 记录 rule/suffix）；
4. **合成别名**（`compound_alias`）：迭代扩展。
   若族 `F` 中已批准表面 `A`，同 type 后缀集 `B ∈ suffixes`，
   则 `A + B`（若在语料中作为独立实体表面出现）合入 `F`；
   反向 `B + A` 也允许，但前提是参与组合的表面已经是 hard/approved
   surface；`generic_candidate` 不能借 compound rule 自动升级；
5. **禁止**：
   - 跨 entity_type 的自动合并；
   - 基于任意子串匹配的合并；
   - 从 `wiki/entities/*.md` 或 `wiki/topics/*.md` 读入合并线索。

`family_id` = `sha256(entity_type + "\\0" + canonical_normalized)[:16]`。

`canonical_surface` 选取规则：族内出现在最多 report 中的 surface，
tiebreak 按 `(len asc, unicode asc)`。

### Cross-type Approved Family Registry

- **输入文件（规范来源）**：仓库 `config/entity-family-registry.json`；
  `wiki/_system/entity-family-registry.json` 仅作为**本地实验覆盖**，
  被 sync 排除、不参与 DocDB、也不落入 `changed_relative_paths`。
  当仓库文件存在时**总是**优先加载，跨机器可复现；
- 加载后按 `entries` 显式合并跨类型 seed family；每条 entry **必须**
  携带稳定审计字段 `entry_id / decided_by / decided_at`（向后兼容
  legacy `approved_by / approved_at`）、可选 `decision_ref`（决策
  文档/工单锚点）、与 `evidence[*] = {report_id, quote}`；
  catalog build 对每条 evidence 的 `quote` 做 whitespace-collapse
  verbatim raw 校验，任何漂移都以 `RegistryValidationError` 硬失败；
- 合并保留每个成员原始 `entity_type`；`approved_family.entity_type` = 集合
  （例如 `["system","project"]`）；
- 每条被合并的 seed 在 `posting_provenance` / `surface.provenance` /
  `approved_family_evidence` 里追加 `rule = "approved_family_registry"`、
  `entry_id / decided_by / decided_at / decision_ref /
  registry_version` 全套审计字段；
- 无对应条目时同 surface 跨 type 家族保持独立，resolver 返回 `ambiguous`；
- 括号形式派生的**裸通用别名**（`训战系统 / AI训战系统 /
  示例平台 / AI陪练系统` …）默认 `scope_role = "generic_candidate"`
  — **不会**自动扩张 acronym 家族的 scope；要 hard 化必须在注册表的
  `members` 里显式列出，才会被 catalog build 提升回 `scope_role =
  "hard"`；
- Registry 是一份可版本化的**数据**文件，任何修改（包括 `decision_ref`）
  都会改变 `catalog_sha256` 并强制索引失效重建，跨机构建结果确定性。

### Postings

- 从每个 `候选实体` 声明拿到 report_id 列入 postings（`origin = summary_candidate`）；
- 对**该族**每个已批准 surface 扫描 raw 原文：
  - 边界：ASCII 用 `\b`；中文两侧不能是 CJK 字符（`u4e00-u9fff`）也不能
    是 `+_.-` 等胶合符；
  - 命中即添加为 posting（`origin = raw_anchor`，携带 `surface` 与
    `char_offset`）；
  - **绝不**因 raw 命中生成新的 surface 或家族；
- postings 去重后按 `report_id` 数值升序输出；
- `scope_hash = sha256(sorted postings)[:16]`。
- Catalog 的 semantic core 包含 family/surface/posting、完整边级 provenance
  以及 registry version/source/applied 决策；anchor cache、cache hit/miss、
  build duration、时间戳、输出路径等运行态字段不进入 `catalog_sha256`。

### 扫描可扩展性

朴素 `O(#raw × #surfaces × #text)` 在 8k raw × ~1k surface 上不可接受。
本实现使用**单遍 Aho-Corasick 自动机**（自研 Python 实现，无外部依赖）：

- 一次性把所有 surface 编译为多模式 trie + 失败链接；
- 每个 raw 文件顺序扫描一次，时间 `O(len(text) + #matches)`；
- 命中位置做归一化边界二次校验，保证与 `find_exact_anchors` 语义一致；
- 内存开销 `O(∑ len(surface))`，实测数百 KB；
- Raw 内容通过 `raw_sha256`（摘要 frontmatter 已提供）做**幂等缓存**：
  `wiki/_system/entity-anchors-cache.json` 记录 `{raw_sha256:
  [family_id:surface:offset]}`，同 raw 不重复扫描；缓存只影响构建性能，
  **不**进入 `catalog_sha256`，因此 cold/warm 构建的语义 hash 必须一致；
- 真实镜像基准测量结果写入 `RT/RT-010/reports/交付验证报告.md`。
  基准会在实现完成后测得，本方案不预先给出耗时数值。

## 索引绑定

`cwk_wiki_search_index.build_index`：

- 在计算 `index_sha256` 前先构建 catalog 得到 `catalog_sha256`；
- 将 `catalog_sha256 / catalog_schema / catalog_registry_version /
  catalog_registry_source` 加入 index `payload` 与 `meta`；
- `manifest.json` 追加同一组 `entity_catalog_*` 字段；registry source 在
  index payload/meta/manifest 三处一致，并随 payload 进入 index SHA；
- **Local-First 边界**：`entity-catalog.json{,.gz}`、
  `entity-catalog-meta.json`、`entity-anchors-cache.json`、
  `wiki/_system/entity-family-registry.json` 均为**本地派生 / 本地
  覆盖**，**不**进入 `changed_relative_paths`、**不**通过
  `cwk_sync_mirror_to_docdb.iter_items` 上云；
- `entity_catalog_registry_source` 为**稳定逻辑标签**（如
  `repo:config/entity-family-registry.json`、`mirror:...`），
  绝不出现绝对路径。

`cwk_wiki_query.query_mirror`：

- `load_precomputed_index` 先校验 index payload 自身 SHA 与 meta 中的
  `index_sha256`；
- `cwk_entity_catalog.load_catalog` 独立校验 catalog schema、semantic SHA
  与 `entity-catalog-meta.json` 的 catalog SHA；
- 查询再要求 `catalog.catalog_sha256 ==
  payload.entity_catalog_sha256`；任一失败均进入实体查询 fail-closed，
  不触发不受约束的全库兜底。

## Resolver + Scoped Ranking

在 `query_mirror` 中新增：

```python
resolution = resolve_entity(question, catalog, intents)
if resolution.status == "resolved":
    scope_postings = catalog.family(resolution.family_id).postings
    candidates = [d for d in summaries if d.report_id in scope_postings and filters_ok(d)]
    if not candidates:
        return safe_empty(resolution, reason="filters_removed_all" or "no_indexed_reports")
    # 排序时禁用 nav_bonus；从 query_tokens 中剔除 resolved surface tokens
    ranked = rank_scoped(candidates, query_tokens_minus_entity)
elif resolution.status in {"ambiguous", "unknown", "resolved_empty"}:
    return safe_empty(resolution)
else:  # unscoped
    ... 保持既有行为（含 nav_bonus）...
```

- `unscoped` 的普通事实查询走**既有**代码路径（含 nav_bonus / graph smearing）；
- `resolved` scope 内查询：
  - `nav_bonus = 0`（避免 aggregate 页拉高得分）；
  - `query_tokens_minus_entity`：把 `matched_surfaces` 的 token 从查询里剔除；
  - 排序仍然 BM25 + title anchor + report_id anchor；
  - `results[].scope_support` 记录该结果被纳入的 surfaces + rules；
- `kind` 参数对 `resolved` 情况下的 nav 保持 `all|summary|topic|entity` 的
  语义正确性：`resolved` 时 `topic|entity` kind 也不再返回 nav_bonus（仍可
  返回 nav_hits 作为审计信息，score bonus 归零）。

## Intent 支持度与置信度

`intents.requested`：从查询中检测 `进展|规划|计划|风险|负责|next\s*plan|
next\s*step|下一步|owner|进度` 等意图，去重后按稳定顺序排序（意图顺序
及标点稳定性属于测试面）。

对每条结果：
- `verified_intents[report_id]` 只接受通过结构边界校验的 raw
  entity-intent link；实体锚点与意图必须位于同句、同列表项、同表格行，
  或满足受限 heading subtree/距离规则，并输出原 raw offsets/snippets/SHA；
- summary candidate quote 必须回读映射到 raw；仅“关键词存在于同一篇 raw”
  不构成 query support；
- `intents.verified = ∪ verified_intents`，`intents.missing = requested \ verified`。

`support`：
- `source_integrity`：verified evidence 存在且 raw hash 校验通过 → `verified`；
- `scope_integrity`：`resolved` 且 `scope precision = 100%` → `verified`；
- `query_support`：`intents.missing == []` → `verified`，否则 `partial`
  或 `insufficient`。

`confidence`：
- `high` 要求：`resolved(exact|approved_alias)` + `source_integrity=verified`
  + `scope_integrity=verified` + `query_support=verified`；
- 否则最多 `medium`，其余按现有阈值下调；
- `resolved_empty | ambiguous | unknown` 直接 `none`。

## 降级 & Fail-Closed

- 持久化索引属于 catalog-bound snapshot 时，payload 声明的 catalog
  缺失/不可读、catalog 内部 schema/hash 校验失败，或实际 catalog SHA 与
  payload 不一致，都标记 `catalog_bound_snapshot_broken`；meta/manifest
  仅为构建期审计副本，不参与查询时的重复授权；
- 该状态下实体查询**禁止**回落全库：可读 catalog 仅用于精确 surface
  检测，不参与排序；catalog 不可读时使用保守 entity-shape 检测，覆盖
  NFKC 后的 ASCII、引号/分隔符名称和 `>=2` 字 CJK 残留，返回
  `unknown + confidence=none + results=[]`；
- 普通非实体事实查询继续走既有 unscoped BM25，不因 catalog 故障整体停机；
- CLI `--require-catalog` 用于测试与构建门禁，但关闭该参数也不会绕过
  bound snapshot 的 fail-closed 规则。

## 已知限制

- **排序仍以 summary BM25 为主，证据以 raw 结构链为准**：scope 内
  summary 零分候选保留在稳定尾部；管理意图未覆盖时继续分批回读 raw，
  直到最终 Top-K 可覆盖请求意图或 scope 耗尽。系统不把整篇 raw 当作
  bag-of-words 直接加分，避免远端章节关键词制造假支持；因此结构不清或
  无法建立局部 entity-intent link 的 fallback 汇报会安全降级，而不是
  被推断为高置信证据。
- **CJK 陌生实体的启发式**：管理意图查询经通用意图词与分隔符剥离后，
  仍有 `>=2` 字 CJK 残留即视为 entity-shaped 并 fail-closed；普通非实体
  问句由通用残留词表排除，继续走 unscoped BM25。该规则只决定安全门禁，
  不创建实体或别名，也不参与 ranking。

## 性能

指标在真实镜像上测量后填入 `RT/RT-010/reports/交付验证报告.md`。方案
不预设具体数字，只给出可接受的上限：

- 目录构建：与既有 `cwk_wiki_search_index` 同量级（`<`2×）；
- 目录压缩后：`<`5 MB gz；
- 查询延时：`resolved` 场景 `<`2× 于 `unscoped` 场景；
- 缓存命中时构建耗时应显著低于全量重扫。
