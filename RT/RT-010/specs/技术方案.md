# 技术方案

## 模块拓扑

```
scripts/
├─ cwk_entity_catalog.py       # 新增：目录构建、家族规则、raw 精确锚点扩展
├─ cwk_wiki_search_index.py    # 修改：构建索引时联动构建目录，绑定 hash
└─ cwk_wiki_query.py           # 修改：目录加载 + 实体解析 + scope 硬过滤
tests/
└─ test_wiki_entity_scope.py   # 新增：property/synthetic 与真实镜像样本
knowledge/工作协同镜像/wiki/_system/
├─ entity-catalog.json(.gz)    # 派生工件：本轮完整目录
├─ entity-catalog-meta.json    # 版本、hash、绑定的索引 sha256
└─ search-index.json           # 索引在 manifest 中新增 `entity_catalog_sha256`
```

`cwk_wiki_search_index.build_index` 在写入索引前调用
`cwk_entity_catalog.build_catalog(mirror)`，将 `catalog_sha256` 写入
索引 payload 与 `index-meta.json`；索引与目录都是纯派生工件，其他数据源
（raw、summaries）保持不可变。

## 数据流

```text
wiki/summaries/*.md
  └─ 候选实体 段落  ─┐
                     │
raw/**/*.md ────────┤ → cwk_entity_catalog.build_catalog
                     │       (family rules + raw anchor extension)
                     │
                     ▼
        wiki/_system/entity-catalog.json(.gz)
                     │
                     ▼
        cwk_wiki_search_index.build_index
        （在 index payload / meta 里绑定 catalog_sha256）
                     │
                     ▼
        cwk_wiki_query.query_mirror
        （resolver + scope hard filter + intent 支持度）
```

## Catalog 构建

### Surface 采集

对每个 summary 解析 `## 候选实体` 段落里的 `- text `type``：
- `surface_text` → clean → `normalize_surface`；
- `entity_type` 从 `` `type` `` 反引号读取，仅接受 `{system, project,
  product, person, organization, other}`；
- `origin = "summary_candidate"`；
- 在 `raw_provenance[(entity_type, normalized)]` 累加 `{report_id, quote}`。

### 家族合并（general rules）

1. **精确合并**：`(entity_type, normalized)` 完全相同直接同族；
2. **括号缩写**（`parenthetical_acronym`）：
   - 正则 `^(?P<acr>[A-Z][A-Z0-9._-]{1,4})[（(](?P<full>[^)）]+)[)）]$`
     或 `^(?P<full>[^（(]+)[（(](?P<acr>[A-Z][A-Z0-9._-]{1,4})[)）]$`；
   - `acr` 与 `full` 在同一 entity_type 下建 approved_alias；
   - `provenance = {rule: "parenthetical_acronym", source_report_id, surface}`；
3. **受控通用后缀**（`controlled_generic_suffix`）：
   - `system.suffixes = {"系统", "平台", "体系"}`；
   - `project.suffixes = {"项目", "项目组"}`；
   - 若 `long = short + suffix` 且 `short` 亦为**同 type 已声明**的
     entity，则合入 `short` 的族（provenance 记录 rule/suffix）；
4. **合成别名**（`compound_alias`）：迭代扩展。
   若族 `F` 中已批准表面 `A`，同 type 后缀集 `B ∈ suffixes`，
   则 `A + B`（若在语料中作为独立实体表面出现）合入 `F`；
   反向 `B + A` 也允许（如 `TBS训战系统` = `TBS`+`训战系统`，
   但仅当 `训战系统` 已通过 rule 2/3 成为 `TBS` 族批准别名后才生效）；
5. **禁止**：
   - 跨 entity_type 的自动合并；
   - 基于任意子串匹配的合并；
   - 从 `wiki/entities/*.md` 或 `wiki/topics/*.md` 读入合并线索。

`family_id` = `sha256(entity_type + "\\0" + canonical_normalized)[:16]`。

`canonical_surface` 选取规则：族内出现在最多 report 中的 surface，
tiebreak 按 `(len asc, unicode asc)`。

### Cross-type Approved Family Registry

- 输入文件：`wiki/_system/entity-family-registry.json`；
- 加载后按 `entries` 显式合并跨类型 seed family；
- 合并保留每个成员原始 `entity_type`；`approved_family.entity_type` = 集合
  （例如 `["system","project"]`）；
- 每条被合并的 seed 记录 `rule = "approved_family_registry"` 与
  `entry.evidence.report_id`；
- 无对应条目时同 surface 跨 type 家族保持独立，resolver 返回 `ambiguous`；
- Registry 是一份可版本化的**数据**文件，任何修改都会改变
  `catalog_sha256` 并强制索引失效重建。

### Postings

- 从每个 `候选实体` 声明拿到 report_id 列入 postings（`origin = summary_candidate`）；
- 对**该族**每个已批准 surface 扫描 raw 原文：
  - 边界：ASCII 用 `\b`；中文两侧不能是 CJK 字符（`u4e00-u9fff`）也不能
    是 `+_.-` 等胶合符；
  - 命中即添加为 posting（`origin = raw_anchor`，携带 `surface` 与
    `char_offset`）；
  - **绝不**因 raw 命中生成新的 surface 或家族；
- postings 去重后按 `report_id` 数值升序输出；
- `scope_hash = sha256(sorted postings)[:16]`。

### 扫描可扩展性

朴素 `O(#raw × #surfaces × #text)` 在 8k raw × ~1k surface 上不可接受。
本实现使用**单遍 Aho-Corasick 自动机**（自研 Python 实现，无外部依赖）：

- 一次性把所有 surface 编译为多模式 trie + 失败链接；
- 每个 raw 文件顺序扫描一次，时间 `O(len(text) + #matches)`；
- 命中位置做归一化边界二次校验，保证与 `find_exact_anchors` 语义一致；
- 内存开销 `O(∑ len(surface))`，实测数百 KB；
- Raw 内容通过 `raw_sha256`（摘要 frontmatter 已提供）做**幂等缓存**：
  `wiki/_system/entity-anchors-cache.json` 记录 `{raw_sha256:
  [family_id:surface:offset]}`，同 raw 不重复扫描；缓存也纳入
  `catalog_sha256` 计算，保持全流程确定性；
- 真实镜像基准测量结果写入 `RT/RT-010/reports/交付验证报告.md`。
  基准会在实现完成后测得，本方案不预先给出耗时数值。

## 索引绑定

`cwk_wiki_search_index.build_index`：

- 在计算 `index_sha256` 前先构建 catalog 得到 `catalog_sha256`；
- 将 `catalog_sha256` 与 `catalog_version` 加入 `payload` 与 `meta`；
- `manifest.json` 追加 `entity_catalog_*` 字段；
- 变更时把 `entity-catalog*.json*` 加入 `changed_relative_paths`。

`cwk_wiki_query.load_precomputed_index`：

- 除现有 sha256 校验外，读取 `entity-catalog-meta.json`，要求：
  - `catalog.schema_version == "cwk.entity_catalog.v1"`；
  - `catalog.catalog_sha256 == payload.entity_catalog_sha256`；
  - `meta.entity_catalog_sha256 == catalog.catalog_sha256`；
  - 任一失败 → 返回 `None`（触发 live 重扫，或若 CLI 明确要求索引则 fail-closed）。

## Resolver + Scoped Ranking

在 `query_mirror` 中新增：

```python
resolution = resolve_entity(question, catalog, intents)
if resolution.status == "resolved":
    scope_postings = catalog.family(resolution.family_id).postings
    candidates = [d for d in summaries if d.report_id in scope_postings and filters_ok(d)]
    if not candidates:
        return safe_empty(resolution, reason="filters_removed_all" or "no_indexed_reports")
    # 排序时禁用 nav_bonus；从 query_tokens 中剔除 resolved surface tokens
    ranked = rank_scoped(candidates, query_tokens_minus_entity)
elif resolution.status in {"ambiguous", "unknown", "resolved_empty"}:
    return safe_empty(resolution)
else:  # unscoped
    ... 保持既有行为（含 nav_bonus）...
```

- `unscoped` 的普通事实查询走**既有**代码路径（含 nav_bonus / graph smearing）；
- `resolved` scope 内查询：
  - `nav_bonus = 0`（避免 aggregate 页拉高得分）；
  - `query_tokens_minus_entity`：把 `matched_surfaces` 的 token 从查询里剔除；
  - 排序仍然 BM25 + title anchor + report_id anchor；
  - `results[].scope_support` 记录该结果被纳入的 surfaces + rules；
- `kind` 参数对 `resolved` 情况下的 nav 保持 `all|summary|topic|entity` 的
  语义正确性：`resolved` 时 `topic|entity` kind 也不再返回 nav_bonus（仍可
  返回 nav_hits 作为审计信息，score bonus 归零）。

## Intent 支持度与置信度

`intents.requested`：从查询中检测 `进展|规划|计划|风险|负责|next\s*plan|
next\s*step|下一步|owner|进度` 等意图，去重后按稳定顺序排序（意图顺序
及标点稳定性属于测试面）。

对每条结果：
- `verified_intents[report_id] = { intent | intent 关键词精确出现在 raw 或
  summary_quote 内，边界匹配 }`；
- `intents.verified = ∪ verified_intents`，`intents.missing = requested \ verified`。

`support`：
- `source_integrity`：verified evidence 存在且 raw hash 校验通过 → `verified`；
- `scope_integrity`：`resolved` 且 `scope precision = 100%` → `verified`；
- `query_support`：`intents.missing == []` → `verified`，否则 `partial`
  或 `insufficient`。

`confidence`：
- `high` 要求：`resolved(exact|approved_alias)` + `source_integrity=verified`
  + `scope_integrity=verified` + `query_support=verified`；
- 否则最多 `medium`，其余按现有阈值下调；
- `resolved_empty | ambiguous | unknown` 直接 `none`。

## 降级 & Fail-Closed

- 目录构建失败：查询侧读到 `entity-catalog-meta.json` 缺失 → resolver
  只能 fall back 到 `unscoped`（普通事实查询兼容），但**管理型意图 +
  未知实体** 依旧 `unknown` 归零；
- 目录与索引 hash 不一致：`load_precomputed_index` 返回 `None`，
  live scan 依旧安全；
- CLI 新增 `--require-catalog`（默认关闭）用于测试与 nightly 校验。

## 已知限制

- **Intent 排序仍以 summary 为主**：raw 精确锚点只扩展 scope 的
  postings 集合，但候选排序 + 意图证据核对仍走摘要 evidence quotes 与
  BM25 raw 摘要抽取。对于**只**通过 raw_anchor 进入 scope 的 fallback
  汇报，如果 summary 里没有关于 progress/plan/risk 的引文，intent
  support 会保持 partial/insufficient；这属于 RT-010 有意的取舍，避免
  从整份 raw 里做无锚点关键词计数带来的假高信心。后续 RT 可以专门解决
  raw-anchor-only 汇报的 fallback intent recall。
- **CJK 陌生实体的启发式**：本次实现只在 ASCII acronym / 引号名 / 长
  CJK 残留 (>=4 字符) 命中之一时将查询判为 entity-shaped。短 CJK 提词
  加管理意图仍旧走 unscoped BM25。这是保守选择，需要更强的中文命名实体
  识别时再由后续 RT 拓展，不在本 RT 范围内。

## 性能

指标在真实镜像上测量后填入 `RT/RT-010/reports/交付验证报告.md`。方案
不预设具体数字，只给出可接受的上限：

- 目录构建：与既有 `cwk_wiki_search_index` 同量级（`<`2×）；
- 目录压缩后：`<`5 MB gz；
- 查询延时：`resolved` 场景 `<`2× 于 `unscoped` 场景；
- 缓存命中时构建耗时应显著低于全量重扫。
