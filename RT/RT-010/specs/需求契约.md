# 需求契约

## 用户、动作与系统响应

| 用户/系统动作 | 系统响应 | 成功标准 | 失败处理 |
| --- | --- | --- | --- |
| 用户查询指向唯一实体（如“TBS 项目进展与下一步”） | 解析为 `resolved`，对候选做 scope 硬过滤后再排序 | Top-K 每一条都必须能在该实体的机器 postings 中审计到 | 若 scope 应用后候选为空，返回 `resolved_empty` |
| 用户查询指向同名但类型冲突的实体（system vs project） | 解析为 `ambiguous`，返回结构化澄清 | 结果为空、`confidence=none` | 不做隐式合并、不做全局 BM25 兜底 |
| 用户查询包含未知实体形态且属于“进展/规划/风险/负责/next plan/owner”类管理型意图 | 解析为 `unknown`，failed-closed | 结果为空、`confidence=none`、`reason` 说明未识别 | 不做全局 BM25 兜底 |
| 普通事实型查询（无实体形态） | 保持 `unscoped`，走既有 BM25 召回 | 与目前行为兼容 | 不受本次修改影响 |
| 摘要中未出现该实体，但 raw 原文中出现精确锚点 | 允许**已知**规范/别名将该 report 纳入 postings，附来源为 `raw_anchor` | 严格边界匹配、可回读证据 | 未知子串不得创建别名，不得合并家族 |
| 用户查询命中实体但要求“progress + plan + risk” | 只在**逐意图**都能被验证时判为 `high` | 若任一意图未验证，最多 `medium`，缺失全部则 `low` | 支持度未评估或不完整必须降级 |
| 索引与目录 hash/schema 不一致 | 查询 fail-closed，返回错误式空结果 | 不使用陈旧 postings | 允许 CLI 明确重建后恢复 |

## 机器实体目录契约

新增文件：`knowledge/工作协同镜像/wiki/_system/entity-catalog.json.gz`
（以及非压缩 `entity-catalog.json` 与元数据 `entity-catalog-meta.json`）。

- `schema_version = "cwk.entity_catalog.v1"`；
- `catalog_sha256`：目录核心内容的规范化 sha256；
- `families[*]`：
  - `family_id`：由 `(entity_type, canonical_normalized)` 生成的稳定哈希；
  - `entity_type ∈ {system, project, product, person, organization, other}`；
  - `canonical_surface / canonical_normalized`：家族规范形；
  - `surfaces[*]`：`{surface, normalized, origin, provenance_report_ids}`；
  - `postings[]`：**去重、排序**的完整 report_id 列表；
  - `posting_provenance[report_id][]`：形如 `{surface, rule, source_report_id}` 的边级证据；
  - `scope_hash`：postings 的规范化 sha256；
- `surface_index[normalized] = [family_id, ...]`：可能多值以表达同名跨类型的歧义；
- `statistics`：家族数、平均 postings 长度、按 `entity_type` 的分布等。

**信息来源仅限**：
1. 汇报摘要 `wiki/summaries/*.md` 的 `## 候选实体` 段落；
2. 每条汇报对应的 raw 原文，用于把已知规范/已批准别名扩展到 raw 上的 posting。

**忽略**：`wiki/entities/**` 与 `wiki/topics/**` 的任何页面（不作为 scope 源）。

## 家族合并规则（通用）

规则集 `cwk.entity_catalog.v1.family_rules`（同 entity_type 内自动生效）：

1. `exact_normalized`：`(entity_type, normalized)` 一致直接合并（同一节点）；
2. `parenthetical_acronym`：当某声明形如 `X（Y）` 且 `X` 为 2–5 位 ASCII 大写
   字母（可含 `.`、`-`）时，`X` 与 `Y` 在**同一 entity_type** 内建立
   `approved_alias`，并把源汇报作为 provenance；
3. `controlled_generic_suffix`：仅当两方的规范形只相差一个来自受控封闭
   后缀集时合并；
   - 允许集合（system）：`{"系统", "平台", "体系"}`；
   - 允许集合（project）：`{"项目", "项目组"}`；
   - 且要求较短形本身已在目录中作为**同 type** 的独立实体存在。
4. `compound_alias`：若 `S = A + B` 其中 `A` 是家族的已批准别名、`B` 属于
   同 type 的受控后缀集，则 `S` 视为该家族的合成别名（如 `TBS` 家族批准了
   `TBS`+`训战系统`，则 `TBS训战系统` 合入同一家族）；
5. 单纯子串匹配（如 `TBS销售部` 中含 `TBS`）**不合并**；
6. 陈旧 Markdown 页面**不作为规则输入**。

跨 `entity_type` 的自动合并**默认禁止**——同一 surface 在两个 type 里
出现即视为 `ambiguous`。要跨 type 合并必须经过下节的
**Approved Family Registry** 数据层，且每条合并都必须携带 provenance。

## Approved Family Registry（跨类型合并数据层）

**规范文件**：仓库内 `config/entity-family-registry.json`（版本控制的**唯一
真源**）；镜像内 `wiki/_system/entity-family-registry.json` 仅作为本地实验
用途，仓库文件存在时优先使用（catalog build 强制此优先级）。

- `schema_version = "cwk.entity_family_registry.v1"`；
- `version`：注册表版本（例如 `2026-08-18`）；
- `entries[*]`：
  - `entry_id`（必填）：稳定审计 ID，进入所有 provenance；
  - `canonical_display`：人类可读的家族名（不参与哈希）；
  - `members[*]`：`{entity_type, normalized}` 元组，被显式合并的种子家族；
  - `evidence[*]`：`{report_id, quote}`，跨类型合并的原文证据；
    catalog build **必须**逐条到 `report_id` 对应的 raw 里做 whitespace-
    normalise 后的 verbatim 校验，失败即 `RegistryValidationError` 硬失败；
  - `decided_by / decided_at`（必填，向后兼容 `approved_by / approved_at`）：
    真实决策审计字段，不得填写工具名或 RT 编号；
  - `decision_ref`（可选）：指向本次决策的文档/工单锚点；
  - `notes`（可选）：说明性字段。

Catalog 构建按顺序应用：先做同 type 内的四条通用规则得到种子家族，然后
按注册表的 `entries` 显式合并跨类型的种子家族，形成 `approved_family`。
每个由注册表引入的合并在 `posting_provenance` 里追加 `rule =
"approved_family_registry"`，并附上 `entry_id / decided_by / decided_at`。

约束：
- 注册表是**数据**、可版本化、可审计；不得写入 TBS/任何实体特定的代码、
  加权、固定 rank。系统只做 “有则合、无则 ambiguous”；
- 缺少注册表条目时，任何同 surface 跨 type 情况**必须** `ambiguous`；
- 注册表被修改会改变 `catalog_sha256`，进而破坏与旧索引的绑定；
- **括号形式派生的裸通用别名**（例：`训战系统 / AI训战系统 /
  示例平台 / AI陪练系统` 从 `X（Y）` 派生的 Y 侧）是
  `scope_role = "generic_candidate"` 的**可见候选**——**即使**当前
  语料里不存在独立同名家族，仍然保持 generic。**不会**自动扩张
  acronym 家族的 scope。要让此类通用 surface 进入 hard scope，
  **必须** 在注册表 `members` 中显式列出，才会被 catalog build 提升回
  `scope_role = "hard"`；
- 保留所有 TBS-bearing surfaces（如 `TBS`, `TBS系统`, `TBS平台`, `TBS项目`,
  `TBS训战系统`）作为 hard scope 表面；registry 里的三条 `system:tbs /
  project:tbs / product:tbs` 亦为 hard。TBS 的 scope/结果**必须**排除仅
  由 `训战系统` 通用别名接入的报告；
- 单元测试覆盖：无注册表 → ambiguous，有注册表 → resolved；注册表
  evidence 与 raw 不一致 → 硬失败；仅通用别名 → 不入 acronym scope。

## 解析器状态

`entity_resolution.status ∈ {unscoped, resolved, ambiguous, unknown, resolved_empty}`：

- `unscoped`：查询里未识别到任何实体形态（且没有实体形状的管理意图）；
- `resolved`：唯一家族（`resolution_kind ∈ {"exact", "approved_alias"}`）；
- `ambiguous`：多个家族匹配同一表面且类型不同；
- `unknown`：查询包含实体形态但无匹配家族，且查询属于“管理意图”类；
- `resolved_empty`：家族存在但 postings 空，或经显式过滤后为空。

管理意图 = 匹配 `进展|规划|计划|风险|负责|owner|next\s*plan|next\s*step|下一步|进度` 之一（大小写与全/半角标点无关）。

## 结果契约

`cwk.wiki_query.v1` 顶层新增字段：

- `entity_resolution`：`{status, family_id, family_name, entity_type, matched_surfaces, resolution_kind, reason}`；
- `scope`：`{applied, postings_size, filtered_out, scope_hash, filter_reasons[]}`；
- `intents`：`{requested[], verified[], missing[]}`；
- `support`：`{source_integrity, scope_integrity, query_support}`；
- `global_fallback_used`：`bool`；
- `results[].scope_support`：`{surfaces[], rules[], evidence_source ∈ {summary_candidate, raw_anchor}}`；
- 原 `confidence` 保留：由三支 support 联合决定。

## 验收标准

1. `TBS`、`TBS 训战`、`TBS 训战系统`、`TBS(训战系统)`、`TBS 平台`、`tbs`
   等变体经过通用家族规则解析到**同一** `family_id`；
2. 明确解析后，`Top-K` 每条结果都能在 `scope_support` 中给出至少一条
   合规匹配（`scope precision = 100%`）；
3. 若人为使用不存在的实体形态（例如 `霜蓝鲸鱼量子披萨-进展`），返回
   `resolved_empty` 或 `unknown`，结果为空，`global_fallback_used=false`；
4. Property tests 在 30+ postings、单条 postings、陈旧页面、括号缩写、
   规范化变体、同名跨类型歧义、未知实体、`no_indexed_reports`、
   `filters_removed_all`、raw 精确锚点、目录/索引不一致、意图顺序与
   标点变体上稳定通过；
5. `python3 -m unittest discover -s tests` 全量通过；
6. `wiki_smoke_test.py` 全绿；
7. `python3 -m compileall scripts` 通过；
8. 构建耗时、索引尺寸、查询延时的 before/after 指标写入交付报告，
   增量在可控范围内（catalog 附加物 <5MB gz，查询延时 <2x）。

## 非目标

- 不改动云/影子查询、DocDB、cron；
- 不修改 `cwk_cloud_wiki_topics_entities.py` 的 30 条列表限制；
- 不引入向量库或外部依赖；
- 不针对 TBS 或任何单一实体、单一 reportId 或固定排名做特判。

## Local-First 派生物边界

- `wiki/_system/entity-catalog.json{,.gz}`、`entity-catalog-meta.json`、
  `entity-anchors-cache.json` 是**本地派生物**，仅落盘到本地镜像。它们
  **不进入** `changed_relative_paths`，也**不通过** `cwk_sync_mirror_
  to_docdb.iter_items` 上云——gz 二进制经 UTF-8 同步会破坏，且 anchor
  cache 只反映本机构建状态。云端读者依赖 `manifest.json /
  index-meta.json` 里的 `entity_catalog_sha256 / _schema / _registry_
  version / _registry_source` 检测 drift；命中 drift 时按 catalog-
  mismatch 路径 fail-closed。
- `wiki/_system/entity-family-registry.json` 是**可选本地实验覆盖**，
  同样被 sync 排除、不进入 `changed_relative_paths`；仓库
  `config/entity-family-registry.json` 是**唯一规范来源**。
- `entity_catalog_registry_source` 写入 index / manifest 时必须是
  **稳定逻辑标签**（`repo:config/entity-family-registry.json` /
  `mirror:<relative>`），**绝不**写入绝对路径。
- 相同规则适用于任何后续新增的 entity 派生物。

## 查询硬化不变量（本轮独立审计后强化）

- **scoped 完备召回**：scoped-management 查询在有 `min_score=0.1` 时
  仍包含所有 in-scope 候选（零分尾部按 date/quality/report_id 稳序），
  批扫直至每个 requested intent 都有 raw-verified 支撑或 scope 耗尽。
  unscoped 路径保留 `min_score` 过滤。
- **catalog mismatch**：持久化索引 catalog SHA 缺失/不匹配时，若查询能
  被 (untrusted) catalog 命中为已注册实体（含 CJK 如 `云端虾`）则
  fail-closed；catalog **不用于** ranking。通用非实体查询（如
  `本周有哪些风险`）保持 unscoped BM25。
- **语义 linkage**：
  - `same_block` 需 `distance ≤ 256` 且无 sentence terminator/换行；
  - `heading_ancestor` 需 anchor 是 heading 且 `distance ≤ 256`；
  - `same_leaf_section` 需 **命名**（非空 `heading_path`）且中间无结构
    性块；
  - 扁平化 Markdown（行内 `##` / list / table / blockquote /
    5/20 空格 首缩进）在 parser 内被拆分/复原；
  - 每条 `intent_link`（含任何 title 关系）**必须**给出
    `anchor_offset + anchor_snippet + intent_offset + intent_snippet +
    block kind + heading_path + relation + distance + raw_sha256`；
  - 最终 `evidence` 必须包含 linked raw 片段（`linked_intent_excerpt`）
    并把 verified summary quote 映射回 raw offset。
- **CJK 前缀防撞**：家族最长匹配（catalog-global）：当同一 raw H1 同时
  被短家族（如 `云端`）和长家族（如 `云端虾`）覆盖时，只有长家族获得
  strong linkage；此规则不依赖任何 entity 特判。
