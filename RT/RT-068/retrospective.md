# RT-068 复盘

## 目标达成了吗

达成。2026-09-20 上线，`https://192.168.91.72:8793/members` 登录后即可管理成员。
线上用真实身份验证：三个库都显示"我的角色=所有者"，成员是本人与问答服务，数据与授权表一致。

边界实测：没有会话时接口一律 401；注册面上没有任何管理接口（`/console`、`/api/overview` 都是 404）；
管理台 8791 上 `/members` 是 404。

## 做对了什么

- **把"放在哪"当成安全决策，而不是布局问题**。用户说的是"控制台里的成员管理页"，
  但控制台是明文 + 局域网可达 + 共享密码，给它写权限等于把授权能力交给密码持有者。
  这一页需要的 TLS 与本人身份，注册面已经有了，所以它去了那一面。
- **规则一条都没有在页面里重写**，全部调用 `kb_authz`。页面只是不给按钮，
  真正的拒绝发生在服务端——两者不一致时，以服务端为准。
- **在浏览器里真的点了一遍**，因此抓到一个判据抓不到的缺陷（见下）。

## 踩到什么

- **两种 409 被显示成同一句话**。"库至少要保留一位所有者"和"名单刚被别人改过"都返回 409，
  页面一律说成后者——用户会一直重试，却永远不会成功，而且永远不知道真正的原因。
  判据当时只断言状态码，两种情况都满足，所以测试是绿的。
  修法：版本冲突单独成一类（`VersionConflict`），页面按类型分别说明；
  判据同时断言错误类型与文案不同。
  教训：**同一个状态码下有多种成因时，判据必须断言成因，不能只断言状态码。**
- 提交信息里带了引号，把整条命令拆碎，导致一次提交失败、后续命令乱跑。
  多行提交信息改用文件传递。
- 页面 JavaScript 里一度写了个中文变量名（能跑，但不合适），自查时改掉。

## 留给下一次

- 页面只管成员，不管库本身（建库、改来源、归档仍在命令行）。
- 人员目录只能本人注册写入；页面不提供"替别人报到"，这是有意的。
- 控制台与这一页是两个入口。日后要统一，方向应当是把控制台的只读面并到加密面上，
  而不是把写权限挪回明文面。
- 同事那条链路仍未被真人走通：注册 → 拿令牌 → 被加进库 → 能查到东西。
