# RT-Lite: RT-062 - 读原文接口鉴权补漏

> profile: Spec-Lite | execution_mode: collaborative

## 方案（给人看）

- 做什么：读原文接口（8790 的 `/read`）改为**按文档真实所属的库**核对令牌权限，
  POST 和 GET 两种调用方式都一样。
- 为什么：2026-09-17 复核 RT-061 时发现两个线上漏洞，并在生产上用只看状态码的方式确认过：
  1. `POST /read` 完全不校验令牌——不带令牌、带假令牌都返回 200，能直接读走原文。
     文档和 Skill 都写着"必须带令牌"，但代码里这条分支漏掉了鉴权调用。
  2. `GET /read` 虽然校验令牌，校验的却是**调用方自己报的库名**；而文档编号在索引里是全局的，
     报一个自己有权的库名，就能读走别的库的文档。
- 代价：极小。只改鉴权判定，读取逻辑、响应格式、分页规则都不动。
- 这次故意不做什么：不改令牌体系（那是 RT-061）；不给 `POST /read` 新增 `bank` 字段；
  不改检索 8787 和问答 `/answer`（复核确认它们一直在鉴权）。
- 用户怎样算成功：不带令牌读原文一律 401；持有 A 库令牌读 B 库文档一律 403；
  正常带令牌的同事调用结果与今天完全一样。
- 建议：定论——修完立即上线。线上两支有效令牌的授权范围都覆盖全部三个库，
  按文档正常调用的客户端不会被挡。

## 判定规则

```
拿 doc_id 去索引里查它的路径
  ├─ 查得到 → 路径第一段就是它所属的库（cwork-3m/…、docdb-touqian/…）
  │           单段路径（单库部署）归默认库 RAG_BANK
  │           → 按这个库核对令牌：无效 401，库不在范围 403，通过才读
  └─ 查不到 → 先核对令牌是否有效：无效 401（和"查得到"时一模一样）
              令牌有效 → 照常走读取流程，结果只可能是 404 / 400
```

"查不到时也先要令牌"是为了不给没令牌的人留探测口：他们对存在和不存在的编号拿到的
回应完全相同，猜不出哪个编号是真的。

## 假设与现状

- 关键假设：快照索引的路径第一段就是库 ID，且与令牌 `kb_ids` 用的是同一套名字。
  **已在生产核对（2026-09-17，只读元数据）**：索引 703 条的首段分布为
  `cwork-3m` 502 / `docdb-touqian` 114 / `spbp-2027` 87，没有第四种；
  登记表里两支有效令牌的 `kb_ids` 都是这三个库。
- 现状依据：`adapters/rag_answer/server.py`（`do_POST` 把 `/read` 直接交给 `_read`，
  `_read` 里没有鉴权调用；`do_GET` 用查询参数里的 `bank` 鉴权）、
  `adapters/rag_answer/resolver.py`（索引是 doc_id → 相对路径的全局映射）、
  `adapters/kb_auth.py`（401/403 语义）。

## 实现备注

- `DocResolver.bank_of(doc_id, default)`：查索引返回所属库，未索引返回 `None`。
- `Handler._read_refusal(doc_id)`：POST 与 GET 共用的唯一判定入口。
- GET 的 `bank` 查询参数不再参与鉴权（保留兼容，不报错）。
- 已知且接受的残余：**持有有效令牌**的人，对别的库的编号会拿到 403、对不存在的编号拿到 404，
  可以借此判断"某编号存在于我无权的库里"。编号本身不含正文，内部令牌持有人也都是实名签发，
  暂不为此牺牲 403 的可诊断性。
- 输入校验（缺 `doc_id`、分页参数非法）仍先于鉴权返回 400，与 `/answer` 的既有顺序一致。

## 验证

- `tests/test_rt062_read_authz.py`（15 条，全部合成夹具）：无令牌/假令牌 401、同库 200、
  跨库 403 且响应里没有正文、多库令牌两库都通、无令牌时已知与未知编号回应逐字节相同、
  有效令牌读未知编号 404、GET 报假库名仍 403、单段路径归默认库、鉴权关闭时本地开发照常可读、
  API 参考写明 401/403。
- **反向验证**：把同一份测试跑在修复前的 `server.py` 上，7 条失败，两个漏洞各自被抓到。
- 既有 `test_rt055_rag_answer` / `test_rt055_auth` 等 121 条相关测试不改一行全部通过。
- 上线后复测：重跑当初的状态码探测，`POST /read` 不带令牌与带假令牌都应为 401。

## 变更记录

- 用户能感到什么变化：正常使用无感；没带令牌或越权读原文会被拒绝。
- API 参考的读原文一节补上 401/403 两行，并说明"不用传库名，服务端按编号判定"。

## 遗留事项

- 漏洞存在期间（RT-055 上线 2026-09-14 起）是否有人未带令牌读过原文，服务端没有访问日志
  （`log_message` 为防正文泄露而静默），无法追溯。RT-061 的鉴权改造应补一条只记
  「时间 / 令牌 ID / 库 / 结果码」的审计，不记编号与正文。
