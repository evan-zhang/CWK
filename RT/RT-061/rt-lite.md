# RT-Lite: RT-061 - 库对象与自有授权模型

> profile: Spec-Lite | execution_mode: collaborative

## 方案（给人看）

- 做什么：把"库"从"某个来源的投影"提升为一等对象——它有自己的所有者、来源清单和授权表。
  授权完全由 CWK 自己管；只向玄关借身份（人员 ID 与真名），不借权限。
  令牌改为只证明"你是谁"，"能看什么"交给授权表。
- 为什么：一个库可以是多个来源里各取一部分的并集（几个玄关空间的某些目录 + 工作协同的某个
  时间窗 + 用户上传的一批文件）。**上游任何一套权限都表达不了这种集合**——继承谁的都是错的，
  要么给多要么给少。所以权限必须是库自己的属性。
- 代价：多一张授权表要维护；现有令牌的 scope 字段要迁移；鉴权路径改动会碰到线上服务。
- 这次故意不做什么：不做控制台的权限管理界面（RT-062）、不做自助建库与上传（RT-063）、
  不做摄取时的来源权限校验（见遗留事项）、不处理跨组织。
- 用户怎样算成功：给某人加一个库或收回一个库，**立即生效且不需要重签任何令牌**；
  控制台里看到的是真名而不是哈希；现有两条有效令牌在切换前后行为完全一致。
- 建议：定论——迁移期用"从现有 scope 推导授权条目"保证切换当天行为字节级一致，
  并用判据锁住这个等价性。鉴权是线上路径，不能靠肉眼确认没改坏。

## 三个对象

```
库 bank
  bank_id / 名称 / 所有者(人员ID) / 创建时间 / 状态
  来源清单 sources[]  ← 可多条，各自独立：
        {type: docdb,  space_id, path}     玄关某空间的某目录
        {type: cwork,  window}             工作协同的某时间窗
        {type: upload, drop_dir}           用户上传（RT-063 才启用）

授权 grant
  bank_id / 人员ID / 角色 / 授权人 / 授权时间

令牌 token（改造现有登记表）
  + person_id   ← 新增：这把令牌代表谁
  - kb_ids      ← 迁移后不再作为鉴权依据，保留一代作回滚
```

三档角色，按你定的：

| 角色 | 能做什么 |
|---|---|
| `owner` | 查、改来源、授权别人、删库 |
| `writer` | 查、往库里加内容（RT-063 上传/摄取触发时才有实际用途） |
| `reader` | 只能查 |

所有者可以授权别人；管理员对所有库都有权。

## 鉴权流程的变化

```
现在：令牌 → 取出 kb_ids → 目标库在不在里面
改后：令牌 → person_id → 查 (person_id, bank) 的授权条目 → 有则放行，无则 403
```

关键收益：**授权变更不再需要重签令牌**。现在给人加一个库必须重新签发，签发又受"每人 5 支"上限
挤压；改后加权限只是往表里写一行，令牌纹丝不动。

## 身份接入（只借身份，不借权限）

已实测确认（2026-09-17，只读调用）：

- `/document-database/project/personal/getProjectId` → 个人空间 ID
- `/document-database/project/list` → 该 Key 有权访问的空间列表，其中个人空间那条的
  `createBy` 就是**稳定的人员 ID**，`creator` 是真名

因此 `person_id` 取自玄关，控制台从此能显示真名。**但 `project/list` 的结果不参与授权判断**——
它只用来在签发时确认"这把 Key 是谁"，拿到 ID 和名字就丢掉。

顺带填掉一个已知坑：现在线上签发都用 OPS 那一把 Key 派生身份，导致全组共用一个 owner、
"每人 5 支"变成"全组 5 支"。改用本人身份后，上限恢复为每人。

## 假设与现状

- 关键前提：人员 ID 不随 Key 变化。**已实测验证（2026-09-17）**——用同一个人的两把不同
  appKey 分别调用，人员 ID、个人空间 ID、真名三者完全一致，连 `project/list` 返回的
  25 个空间也完全相同。结论：身份与权限都跟着"人"走而不是跟着 Key 走，
  人员 ID 可以安全地当作授权表主键。
- 现状依据：`scripts/kb_token.py`（登记表结构、`owner_ref` 由业务 Key HMAC 派生、
  每 owner 上限）、`adapters/kb_auth.py`（线上 8787/8790 的鉴权入口、401/403 语义）、
  `scripts/kb_ops.py`（控制台的只读投影）。

## 实现备注

- 新增 `scripts/kb_identity.py`（玄关身份解析，只读、只取 ID 与姓名）与
  `scripts/kb_authz.py`（库与授权两张表的读写，沿用现有原子写 + 写后读回的做法）。
  `scripts/` 是 exact-only 区，两个新脚本都要补治理规则和代表文件。
- 改 `adapters/kb_auth.py` 的判定路径；`scripts/kb_token.py` 的记录增加 `person_id`。
- 不能破坏的约定：登记表只存令牌指纹不存明文；授权表不存任何凭据；
  401/403 语义不变；8787/8790 的对外契约不变。
- 内部阶段：两张表与 schema → 身份解析 → 鉴权改造（带回退开关）→ 迁移脚本 → 等价性判据。

## 验证

- **等价性判据（最重要的一条）**：对现有登记表里的每一对（令牌，库），
  新旧两条鉴权路径必须给出相同的放行/拒绝结果。切换当天行为不得有任何变化。
- 授权变更立即生效：加一条授权后，同一支令牌立刻能访问，全程不重签。
- 角色判据：`reader` 不能授权别人；`owner` 可以；越权一律 403 而不是 500。
- 身份判据：解析失败时 fail-closed（拿不到人员 ID 就不签发），不得回退成"匿名放行"。
- 回退：保留一个环境开关可切回按 scope 判定，线上出问题能立刻退回去。

## 变更记录

- 用户能感到什么变化：加/收权限立刻生效且不用重签令牌；控制台里看到的是人名；
  每人的令牌额度不再被全组共用。

## 遗留事项

- **摄取时不校验来源权限**（2026-09-17 决定，理由是时间成本）。风险是：有权访问某空间的人
  可以把内容摄进自己的库，再授权给对该空间无权的人——等于绕过上游权限。
  当前由"只有管理员能执行摄取"兜住，**自助建库（RT-063）上线前必须补上这道校验**。
- 控制台的权限管理界面属 RT-062；自助建库与上传属 RT-063。
- 跨组织（实测存在两个 `corpId`）本次不处理。
