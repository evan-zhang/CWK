# RT-Lite: RT-061 - 库对象与自有授权模型

> profile: Spec-Lite | execution_mode: collaborative

## 方案（给人看）

- 做什么：把"库"从"某个来源的投影"提升为一等对象——它有自己的来源清单和成员表。
  授权完全由 CWK 自己管；只向玄关借身份（人员 ID 与真名），不借权限。
  令牌改为只证明"你是谁"，"能看什么"交给成员表。
- 为什么：一个库可以是多个来源里各取一部分的并集（几个玄关空间的某些目录 + 工作协同的某个
  时间窗 + 用户上传的一批文件）。**上游任何一套权限都表达不了这种集合**——继承谁的都是错的，
  要么给多要么给少。所以权限必须是库自己的属性。
- 代价：多一张成员表和一张人员目录要维护；鉴权路径改动会碰到线上服务；
  过渡期新旧两种令牌并存，判定逻辑多一个分支。
- 这次故意不做什么：不做控制台的成员管理界面（后续「界面 RT」）、不做自助建库与上传（后续「自助建库 RT」）、
  不做本人自助签发（见"签发"一节）、不做摄取时的来源权限校验、不处理跨组织。
- 用户怎样算成功：给某人加一个库或收回一个库，**秒级生效且不需要重签令牌**；
  数据层能按人员 ID 给出真名；现有两支有效令牌在切换前后对每个库的放行/拒绝结果完全一致。
- 建议：定论——过渡期用"成员表 ∩ 旧令牌自带范围"的交集判定，保证切换当天零变化，
  并用判据锁住。鉴权是线上路径，不能靠肉眼确认没改坏。

## 2026-09-17 复核后的修订

原型完成后用两个独立审查做了复核（计划与原型对照、原型代码审查）。对计划有实质影响的结论：

| 编号 | 问题 | 处理 |
|---|---|---|
| A1 | 现有令牌全用 OPS 那一把 Key 签发，`owner_ref` 是单向 HMAC，推不回"这支令牌是谁的"。直接按人汇总权限会让只读一部分库的令牌扩权 | 迁移**用签发 Key 重算指纹来证明归属**（见"迁移"），证明不了就整体拒绝；旧令牌判定取交集，结果只可能收紧不可能放宽 |
| A2 | "用本人 Key 签发、每人 5 支"没有安全的实现通道：本人 Key 得交给 OPS 进程，局域网又是明文 HTTP | 本 RT 签发仍由管理员执行，身份仍只来自当场核实的 Key；给别人报到推迟，前提是先有加密通道 |
| A3 | 额度和 Agent 绑定仍按 Key 派生，一人两把 Key 可拿 10 支 | 新令牌的额度计数键与绑定一律改为按人 |
| A4 | `POST /read` 不鉴权、`GET /read` 可跨库读 | **已拆出单独修复（RT-062）**，本 RT 不再承担 |
| Q8 | 问答服务调检索服务用的是自己的服务令牌，新判定第一天就要能识别它 | 新增"服务身份"，见下 |
| Q9 | 计划里库对象有单个所有者字段，成员表里又有所有者角色，两处都存所有权 | 所有权只由成员表表达，支持多位所有者，见下 |

编号调整：原计划里预定的"控制台权限界面 RT-062"和"自助建库 RT-063"不再预留编号，
下文称「界面 RT」「自助建库 RT」，届时按并集最大号 +1 实际占号（RT-062 已用于读原文鉴权修复）。

## 四张表

```
库 bank
  bank_id / 名称 / created_by(人员，不可变) / 创建时间 / 状态(active|archived)
  —— 不再有"所有者"字段；谁是所有者只看成员表

来源 source（一个库可以有多条，同类型也可以多条）
  source_id(稳定) / bank_id / type / 选择条件 / 采集凭据引用 / 添加人 / 添加时间
     type=docdb   选择条件 {space_id, path}
     type=cwork   选择条件 {from, to, keywords[]}     ← 关键词字段先预留
     type=upload  选择条件 {drop_dir}                 ← 自助建库 RT 才启用
  采集凭据引用只存环境变量名，不存值

成员 grant
  bank_id / principal / role / granted_by / granted_at
  —— 表里只存当前状态；每次增删改另写一条回执，历史不丢

人员目录 person
  principal / corp_id / person_id / 姓名 / identity_source / first_seen / last_verified
```

`principal`（主体）是鉴权看到的"你是谁"，两种形态：

- 人：`person:<corp_id>:<person_id>`。ID 一律按**字符串**存——19 位数字超出 JavaScript
  安全整数范围；实测存在两个 corpId，主键带上组织避免碰撞。
- 服务：`service:<name>`，如 `service:rag-answer`。

三档角色：

| 角色 | 能做什么 |
|---|---|
| `owner` | 查、改来源、增删成员、删库 |
| `writer` | 查、往库里加内容（自助建库 RT 有了上传/摄取入口才有实际用途） |
| `reader` | 只能查 |

## 两个已定的设计问题

**Q8 服务身份（定论）**：问答服务调检索服务的那支令牌，主体是 `service:rag-answer`。

- 不算任何人的额度，不能当所有者，不能授权别人，不出现在任何人的"我的令牌"里。
- 在成员表里显式拿 `reader`；新建库时由建库流程一并授予，`kb_doctor` 检查漏授。
- 不挂在管理员名下的理由：否则管理员一旦被移出某个库，所有人在那个库上的问答都会中断。

**Q9 多位所有者（定论）**：

- 所有权只由成员表里 `role=owner` 的行表达；库对象只留不可变的 `created_by`。
- 一个库可以有多位所有者。转让 = 先加新所有者，再把自己降级，不另设转让动作。
- 所有者可以增删 `reader`/`writer`、可以新增所有者；**不能降级或移除其他所有者**，
  只能降级自己。管理员不受此限。
- "至少保留一位所有者"在同一次写入里检查：成员表带一个版本号，写入前比对，
  版本变了就拒绝重来，避免两人同时操作把最后一位所有者弄没。

## 鉴权流程

```
现在：令牌 → kb_ids → 目标库在不在里面

改后：令牌 → principal
        ├─ 令牌没有 principal（历史上的共享令牌等）→ 403 no_principal
        ├─ 库不存在或已归档 → 403 bank_inactive
        ├─ 旧令牌（带 kb_ids、未标记新判定）→ 成员表有条目 且 库在 kb_ids 里 → 放行
        └─ 新令牌（标记为按成员表判定）   → 成员表有条目 → 放行
```

- 401/403 语义不变：令牌本身无效是 401，令牌有效但无权是 403。
- 新令牌仍然写一份 `kb_ids` 快照——只为回滚：回滚到旧代码时它们还能按快照工作，
  而不是全体 401。代价是回滚期间快照之后的授权变更不生效，回退说明里写明。
- 登记表 schema 保持 `cwk.kb.token-registry.v1`，所有新字段都是追加，旧代码读得懂。
- 成员表和人员目录跟登记表放在同一个挂载目录里，通过新环境变量传给两个容器；
  每次请求重读，所以变更"秒级生效"（线上同步有秒级延迟，不是字面上的立即）。
- 环境开关 `RAG_AUTHZ_MODE=scope|grants`，默认 `scope`（即今天的行为），切换靠改开关，
  出问题立刻切回。

## 迁移

实现时发现原计划的"管理员手填令牌 → 人对照表"违反 RT-047 定下的铁律：
**身份只能由当场核实通过的 Key 推导，不接受任何手填身份**（`kb_token.py` 连 `--owner-ref`
这类参数都在解析前驳回）。改为可证明的归属：

1. 管理员用 `--verify-env` 交出签发过现有令牌的业务 Key（传变量名不传值）。
   每把 Key 先经玄关核实是谁，再用登记表的盐重算 `owner_ref`。
2. 有效令牌的 `owner_ref` 与某把核实过的 Key 重算结果相同 → 归给这把 Key 的持有人。
   服务令牌另需 `--service rag-answer=<Agent 标识>`，其绑定 ID 能由该标识重算出来才认作服务身份。
3. 有一支有效令牌证明不了归属，或 `--service` 没匹配到任何令牌，**整体拒绝执行**，两个文件都不动。
4. 为每支令牌的每个 `kb_ids` 生成 `reader` 成员条目；不降级已有角色；可重复执行。
5. 现有库的所有者：`--owner-env` 指定的那把 Key 的持有人。
6. 写完立即用线上判定代码跑等价性核对，不相等则返回非零，开关不动。

单库共享令牌（RT-053）没有人在背后，继续按它自带的单库判定，但库本身须处于启用状态。

## 签发（本 RT 的边界）

- 签发仍由有 OPS 登记表写权限的管理员执行，不新增任何网络入口。
- 签发探针由工作协同 `todoList` 改为玄关身份解析：同一次核实既证明 Key 有效，又得出人员 ID 与真名，
  记录带 `principal`。解析失败一律拒签。
- 人员目录只接受玄关核实的身份（`identity_source=xuanguan_verified`），没有"管理员代录"这条路。
- 给别人报到（让同事的 Key 在不经明文传输的前提下被核实）推迟：前提是先有加密通道。
  在此之前人员目录里基本只有管理员本人，管理员替同事签的令牌仍归管理员名下、靠 `--kb-id` 收窄——
  与今天完全一样，没有退步，但"按人授权"要等报到通道。
- 额度（每人 5 支有效令牌）和 Agent 绑定对新令牌一律按 principal 计算；服务身份不计额度。
- 令牌可带一个使用者自填的显示名 `label`（不自动取主机名），供日后界面显示。

## 身份接入（只借身份，不借权限）

已实测确认（2026-09-17，只读调用）：

- `/document-database/project/personal/getProjectId` → 个人空间 ID
- `/document-database/project/list` → 该 Key 有权访问的空间列表，其中个人空间那条的
  `createBy` 就是**稳定的人员 ID**，`creator` 是真名

`project/list` 的结果**不参与授权判断**。本 RT 里 `kb_identity.py` 只提供"给一把 Key，
返回人员 ID、组织和姓名"的只读解析，供管理员签发前核实用；Key 只在内存里用一次，不落盘。

## 假设与现状

- 关键前提：人员 ID 不随 Key 变化。**已实测验证（2026-09-17）**——同一个人的两把不同
  appKey，人员 ID、个人空间 ID、真名三者一致，`project/list` 返回的 25 个空间也完全相同。
- 线上现状（2026-09-17 只读核对）：登记表 5 条，2 条有效，有效两条的 `kb_ids` 都是全部三个库；
  其中一条是问答服务的服务令牌。
- 现状依据：`scripts/kb_token.py`（登记表结构、`owner_ref` 由 Key 的 HMAC 派生、每 owner 上限、
  整文件原子替换）、`adapters/kb_auth.py`（8787/8790 的鉴权入口、schema 版本硬校验）、
  `adapters/rag_answer/pipeline.py`（服务令牌 `RAG_AUTH_TOKEN`）、`scripts/kb_create.py`
  （`kb.json`/`kb_members.json` 旧成员模型）。

## 实现备注

- `scripts/kb_identity.py`：玄关两次只读调用（个人空间 ID → 空间列表里那一行的
  `createBy`/`corpId`/`creator`）。实测形状：Key 无效时 HTTP 200、`resultCode=401`；成功为 1。
  任何歧义（找不到或找到多个个人空间、ID 非数字字符串、姓名为空）都拒绝，不猜。
- `scripts/kb_authz.py`：四张表的写面、角色规则、来源登记、`show`、`migrate`、
  `check-equivalence`、`check`。写入在排他锁内"重读 → 比对版本 → 修改 → 原子替换"，
  只有真有变化才升版本、写回执。判定函数直接调用线上的 `adapters.kb_auth.membership_verdict`，
  写面与读面没有第二份实现。
- `adapters/kb_auth.py`：`RAG_AUTHZ_MODE=scope|grants`，默认 `scope`（原逻辑原样保留）；
  开关值写错 → 401 `authz_mode_invalid`；`grants` 下成员表不可读 → 401，fail-closed。
- `scripts/kb_token.py`：记录追加 `principal`/`authz`/`label`；新绑定 `agent|v2` 按人派生，换代时
  连同旧的按 Key 派生的绑定一起找；额度按"同一把 Key 或同一个人"计数；
  `issue-service`/`rotate-service`；迁移用的 `bind_principal`。登记表 schema 版本不变。
- CLI 的操作者是"OPS 文件写权限持有人"（`admin:ops-registry`），与共享令牌的授权依据一致；
  角色规则对任何操作者都生效，界面 RT 可以直接传真人进来，不用另写一套。
- 部署：`deploy/docker-compose.yml` 给两个服务透传 `RAG_AUTHZ_MODE`（默认 `scope`）与 `RAG_AUTHZ_PATH`。
  线上检索容器从仓库构建、问答容器从 `rag-overlay` 构建，两处都要同步 `adapters/kb_auth.py`。
- 治理：新增 `R-runtime-rt061-kb-authz`（exact_set 两个新脚本），`_REPRESENTATIVE_TRACKED` 补代表文件。
- 运维手册：`docs/KB-AUTHZ.md`；管理 Agent Skill 同步更新，并改正了其中已过时的登记表路径
  （线上只有 `auth/registry/rt055-tokens.json`）。

## 验证

新增 5 个测试文件、共 74 条判据，全部合成夹具，不联网、不含真实 Key：

- `test_rt061_auth_grants.py`：默认模式完全不读成员表；开关写错全拒；加/收成员下一次请求即生效；
  旧令牌被自己的 `kb_ids` 收窄；归档库全员 403；成员表损坏 401；
  **只收紧判据**：穷举 3 个库的全部范围组合 × 全部成员表组合，`grants` 放行集合 ⊆ `scope`。
- `test_rt061_authz_store.py`：角色规则全集；服务身份只读且只归管理员管；来源按类型校验、凭据只收变量名；
  回执版本连续；文件 0600；旧版本号写入被拒；**两位所有者并发退出，恰好一人成功**；失败的写入不碰文件。
- `test_rt061_token_principal.py`：记录带 principal；grants 令牌无身份拒签；同一人两把 Key 共用额度、
  同一 Agent 不能各持一支；旧绑定换代可找到；服务令牌不占额度、一服务一支。
- `test_rt061_migration.py`：按线上形状（同一把 OPS Key 签发，2 有效含服务令牌，3 已吊销）迁移后

## 变更记录

- 代码上线后（开关保持 `scope`）：用户无感。
- 迁移并切到 `grants` 后：管理员加/收某人对某库的权限，约 10 秒生效且不用重签令牌；
  一个库可以有多位所有者；同一个人换 Key 不再多占额度。
- 暂时做不到：给同事本人报到（需要加密通道），所以"按人授权"目前只对管理员本人成立。

## 遗留事项

- **摄取时不校验来源权限**（2026-09-17 决定，理由是时间成本）。风险是：有权访问某空间的人
  可以把内容摄进自己的库，再授权给对该空间无权的人——等于绕过上游权限。
  当前由"只有管理员能执行摄取"兜住，**自助建库 RT 上线前必须补上这道校验**。
- **给别人报到 / 本人自助签发**需要加密通道，未排期。这是"按人授权"真正惠及同事的前提。
- **8790/8787 没有访问审计**（RT-062 发现）：为防正文泄露，服务端完全不记请求。
  建议在切到 `grants` 模式时一并加一条只记「时间 / 令牌 ID / 库 / 结果码」的审计。
- 旧 `kb_create` 的 `kb.json`/`kb_members.json` 成员模型与本 RT 的成员表是两套，
  取代还是映射在自助建库 RT 决定；本 RT 不改 `kb_create`。
- 服务端库清单（`CWK_RETRIEVAL_BANKS`、`RAG_BANK`）与库表是两个事实源；本 RT 以库表为准，
  `kb_doctor` 报告不一致，暂不自动同步。
- 跨组织（实测存在两个 `corpId`）本次不处理，但主键已带组织。
- 原型里推迟到界面阶段的问题（Q1–Q7）的推荐答案，记录在 `decisions.md`。
