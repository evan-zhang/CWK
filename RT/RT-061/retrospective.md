# RT-061 复盘

## 目标达成了吗

部分达成，边界清楚。

- **达成**：库成为一等对象，有自己的来源清单、成员表和人员目录。令牌记下"这是谁"。
  身份只向玄关借，由当场核实的 Key 推导。线上鉴权可以按成员表判定，开关默认关闭。
  额度与 Agent 绑定按人计算。问答服务有独立的服务身份。
- **已上线（2026-09-17，经产品负责人批准：合并 + 上线代码 + 迁移，暂不切换）**：
  - 检索 8787 与问答 8790 运行新代码，开关为 `scope`。
  - 线上令牌登记表已迁移：2 支有效令牌绑定身份（1 人 + 1 服务）。成员表建出 3 个库，
    每库一位所有者，外加问答服务只读。
  - 两道核对返回 0。20 项行为检查在重建检索、重建问答、迁移之后三次与基线逐项一致。
- **未做（有意）**：切到 `grants` 判定；给同事报到。后者需要加密通道，前者在报到通道出现之前收益很小，
  所以两者一起放到下一个 RT。

## 做对了什么

- **实现时回头检查方案是否违反既有铁律**。原计划"管理员手填令牌 → 人对照表"与 RT-047 的
  "身份只能由当场核实的 Key 推导"正面冲突。改成用签发 Key 重算 `owner_ref` 来证明归属，
  既守住铁律，又不需要任何人记住哪支令牌是谁的。
- **写面和读面只有一份判定**：`kb_authz.decide` 与等价性核对直接调用线上的 `adapters.kb_auth`。
  核对证明的就是 8787/8790 真正会做的判断，不是一份平行实现的判断。
- **判据先证明自己会红**：去掉旧令牌收窄、去掉写锁、允许所有者降级他人、额度只按 Key 计，四处故意改坏，
  各自被抓到。回滚兼容用主线上 RT-061 之前的 `kb_auth.py` 实际跑过。
- **先在线上真实数据上演练，再请批准**。第一次演练在登记表副本上跑，暴露了"先写文件再核对"的顺序问题：
  核对这一步出错时，文件已被改动却没有结论。改成内存演练通过才落盘后，第二次直接对线上登记表做 dry-run，
  全程零写入。
- **重建容器前渲染配置、逐项比对运行中的容器**，又抓到一个会造成全员问答中断的坑（见下）。

## 踩到什么

- **检索容器的回环端口 18887 在任何配置文件里都不存在**。问答服务经它调检索；这个端口只存在于
  9 月 14 日建容器时的一次性命令里。照常重建会把它弄丢，所有人的问答随即中断。已把它写进 OPS 本地的
  `deploy/docker-compose.production-auth.yml`，让容器可重建，重建前后比对确认端口一致。
- 演练打包漏了 `adapters/base.py`（`adapters/__init__.py` 会导入它），命令行因此崩出堆栈而不是 JSON。
  现已在命令行边界兜住任意异常。
- 管理 Agent Skill 里的登记表路径早已过时（写的是 `auth/rt055-tokens.json`，线上只有 `auth/registry/` 下那份）；
  手册初稿里用 `source` 读 `key.env` 也是错的——那个文件是一行裸 Key，`source` 会把 Key 当命令执行，
  报错时可能把 Key 打出来。两处都在上线前改正。
- 门户重启后头几秒返回 502，重试即好——与 RT-060 同一现象。
