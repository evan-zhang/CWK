# 技术方案

## 职责划分

```text
工作协同后台
  └─ 解析 AppKey 当前用户
  └─ 汇总发件、收件、流程节点、委托/转办、状态和权限规则
  └─ 批量返回权威关系 + 当前动作

CWK
  └─ 批量调用接口并保存本轮关系 manifest
  └─ 校验每个 reportId 都有返回
  └─ 按后台结果展示；接口失败时降级 unknown
  └─ 不再扫描 nodeList 人员清单做关系判定
```

## CWK 关系 manifest

本轮写入 `runs/{run_name}/report-relationships.json`：

- `schema_version=cwk.report_relationships.v1`
- `provider=work-report-backend`
- `provider_status=ok|unavailable|partial`
- `relation_version/evaluated_at`
- `items`：按 reportId 索引的规范化关系结果
- `missing_report_ids`：后台未返回的请求 ID，统一按 unknown 使用

manifest 不存 AppKey，不复制全量人员清单。

## 降级规则

- 未配置接口路径：`provider_status=unavailable`，所有关系 unknown。
- HTTP/API 失败：记录非敏感错误，关系 unknown；nightly 可继续。
- 单条 `unknown/not_found/forbidden`：仅该条待确认。
- 只有 `status=resolved && visibility=visible_only` 才显示“仅权限可见”。
- 待办列表本身是后台选择结果，可继续决定“今日处理”，但角色与可办理动作仍等待关系接口。

## 性能与一致性

- 使用批量接口，避免每篇汇报一次请求的 N+1 问题。
- 单批最多 200 条，超出时分批；每批有界超时。
- 返回 `relationVersion`，便于后台规则升级后审计与重算。
- 关系结果属于时点状态，不写入不可变事实层；每日重新查询并保留本轮 manifest。
