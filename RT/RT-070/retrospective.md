## 踩到什么

三个问题都只在**部署形态**下才出现，单测一条都测不出来：

1. **检索服务用固定索引名，不是别名**——切了别名也没用，成了"索引旧、映射新"的半新半旧状态。
2. **映射表是单文件 bind mount**——同步用原子改名落盘，容器里看到的永远是旧 inode，
   新同步进来的 67 份文档一律 404。改挂目录，并让 `DocResolver` 在
   `(mtime, 大小, inode)` 变化时重读，不必重启服务。
3. **映射表和文档共用一条 2MB 上限**——NAS 上大于 2MB 的文档搜得到、读原文 400。
   摄取侧上限是 64MB，两边从来没对齐过。

教训：**判据要断言"线上那条路径"，不只是"函数逻辑"**。三条里两条是"代码对、部署接不上"，
一条是"两侧上限没对齐"——都属于同一类：单测只看一侧，就看不见两侧的缝。

还踩到两个老坑：**第三次忘了同步 rag-overlay**（改 `adapters/` 后没同步，
双根配置下旧代码报错，读原文 400、问答 503 约 3 分钟）；
`git add -A` **把 18 个 Playwright 截图连同 21MB 的 .crx 一起提交了**，

## 当晚链路首跑又暴露两个（已修并各自补了判据）

RT 收口后第一次真跑整条夜间链路（`com.cwk.kb-sync` 手动触发，不等 23:30），又撞出两个：

4. **夜间脚本的报告部分根本跑不起来。** 它把「程序」和「数据」都塞给了 `python3 -`：
   `-` 本身就是"程序从 stdin 读"，后面又接了 `<<<"$OUT"` 喂数据，后者覆盖前者，
   于是 Python 把 kb_ingest 输出的 JSON 当程序执行，报 `NameError: name 'true' is not defined`。
   后果恰恰是这个脚本本来要解决的毛病：**刷新出了问题看不见，连日志都写不出来**。
   现在程序走 stdin、数据走临时文件。
5. **NAS 的 SMB 挂载会半死不活，而这一步没有超时。** 根目录列得出来，真去 `open()`
   一个文件却永远不返回——建索引那一步就那样挂了 12 分钟，CPU 全程是 0（调用栈停在
   `__open`）。没有闸的话夜间任务会一直挂着，第二天既没有新内容也没有任何报警。
   macOS 没有 `timeout(1)`，改用 python 子进程限时：单库刷新 90 分钟、建索引 30 分钟，
   超时按 124 报出来，并在报告里写成人话。

判据（隔离跑，不碰真实数据：把刷新和建索引换成回放假输出）：全部正常 → 写得出日志、
某库 failed>0 → 点名说几条失败且整体非 0、建索引失败 → 整体非 0、
某库卡住 → 3 秒内被闸终止且报"超时，已终止"。

**我自己也犯了一个错**：改这个脚本时它正在跑。bash 是按字节偏移边读边执行的，
改动一个正在运行的脚本可能让它从错位的地方接着读。这次没造成损害（卡住的那步
本来就要终止），但正确做法是先停再改。
