# RT-002 Shadow Mode 需求契约

## 1. 业务目标

把每日工作协同简报变成按 Evan 办理责任排序的交互工作台。用户能区分必须处理与可选意见，查看 AI 建议，编辑自己的意见，并在不写入 CWork 的前提下预览实际操作。

## 2. 用户角色

- 建议人：必须给出具体建议。
- 决策人：必须给出最终决定。
- 普通收件人：只需知悉，可选发表意见。
- 更新接收人：只需阅读变化，可选针对更新发表意见。

## 3. 使用场景

- 用户打开当日工作台，先处理决策待办，再处理建议待办。
- 用户对普通收件或更新通知选择“我要发表意见”，输入要求并编辑草稿。
- 用户点击任何业务按钮时，只看到 Shadow Mode 操作预览，不产生外部写入。

## 4. 功能范围

### 必须实现

- 从已有 run 的 raw、extracted、AI understanding 中生成唯一 `action-card`。
- 识别 `decision_todo`、`advice_todo`、`reactivated_todo`、`update_notice`、`inbox_awareness`、`historical`。
- 同一 `report_id` 只展示一次，以责任优先级最高的类型为准。
- 卡片显示责任、摘要、历史/变化信息、AI 建议、草稿、证据和允许操作。
- 生成 JSON、Markdown 和移动端 HTML。
- HTML 按钮可打开预览、编辑意见、显示目标与后果。
- 页面醒目标记 Shadow Mode，禁止写回。

### 明确不做

- 不调用审批、回复、转办、完成、标已读等 CWork mutating command。
- 不提交用户意见。
- 不生成可复用的长期操作令牌。
- 不支持批量办理。

## 5. 输入

- `runs/<run_name>/raw/*.md`
- `runs/<run_name>/extracted/*.json`
- 可选 `runs/<run_name>/ai-understanding/*.json`

## 6. 输出

- `action-cards.json`
- `action-center.md`
- `action-center.html`

## 7. 业务规则

- 待办责任高于收件和通知。
- 决策待办高于建议待办；结构化角色证据不足时不得提供真实审批能力。
- 待办出现新回复或更新时标为 `reactivated_todo`，同时保留底层角色。
- 非待办的更新记录标为 `update_notice`。
- 历史回填不进入必须处理区。
- “本地已知悉”与 CWork 标已读是不同动作。
- 所有卡片和建议都必须包含 `report_id` 证据入口。

## 8. 异常情况

- 缺少 AI understanding：使用规则抽取摘要并降低置信度。
- 待办角色不明确：标记 `requires_role_review=true`，只允许意见草稿类预览。
- 输入缺少 report_id：跳过并在 manifest 记录。
- 同一 report_id 多来源：合并标签，只保留一个主卡片。

## 9. 权限与安全要求

- Shadow Mode 不加载写适配器。
- HTML 不含写 API URL、`fetch`、XHR 或自动提交表单。
- 输出不得包含 appKey、token 或 secret-shaped 值。
- 操作预览必须显示“不会提交到 CWork”。

## 10. 验收标准

- 六类主类型均有测试覆盖。
- 同一 report_id 唯一展示率 100%。
- 强制待办与可选意见在页面上明显区分。
- 角色不确定时不显示审批同意类按钮。
- 页面可编辑意见并生成预览。
- mutating command 调用数为 0。
- 全量测试与 smoke 通过。

## 11. 测试场景

| 场景 | 输入 | 期望结果 |
|---|---|---|
| 决策待办 | todo scope + 决策人证据 | 主类型 decision_todo，显示同意/不同意预览 |
| 建议待办 | todo scope + 建议人证据 | 主类型 advice_todo，显示提交建议预览 |
| 更新后待办 | todo + updated/new reply | 主类型 reactivated_todo，仍保留底层角色 |
| 普通收件 | inbox，无强制责任 | 主类型 inbox_awareness，意见可选 |
| 更新通知 | 非 todo + updated/reply | 主类型 update_notice，只展示变化和可选意见 |
| 历史回填 | historical_backfill | 主类型 historical，不进入必须处理区 |
| 角色不确定 | todo，无角色证据 | requires_role_review，不出现审批按钮 |
| 安全检查 | 生成 HTML | 无 fetch/XHR/写 API，显示 Shadow Mode |

## 12. 2026-08-12 日报分流补充契约

### 业务目标

每日页面不再把轮转抽样的旧汇报混入“今日”主体。用户打开页面后，必须先看到当天新增内容和当前确需本人处理的待办；历史汇报只有在本轮发生真实变化时，才进入独立的“近期变更”视图。

### 视图规则

- `今日处理` 是默认视图：先展示当前必须处理的待办，再展示本轮新增汇报。
- `近期变更`：优先只接收运行基线确认的 `change_type=updated`；仅在没有基线分类（`unknown`）时，才用源端明确 `hasNewReply=true` 兜底。
- `持续未闭环`：接收未发生本轮变化、也不属于今日新增的延续事项；在“今日处理”内折叠展示，不占据首屏。
- 当日业务日期范围补采得到的汇报，即使采集器标记为 `historical_backfill`，只要原始汇报日期等于日报日期，也按“本轮新增”进入 `今日处理`。
- `reply_chain` 仅代表汇报历史上存在回复链，不能单独证明本轮发生变化；持续为真的陈旧 `hasNewReply` 标记也不能覆盖已确认的 `continuation`。
- 同一事项若既需要本人处理又在本轮发生变化，可同时进入 `今日处理` 与 `近期变更`；统计按视图分别计数，底层仍保持唯一 `report_id`。
- 早于日报日期的普通历史回填不进入两个主视图，只保留在知识库与运行证据中。

### 验收标准

- 默认页签为 `今日处理`，且必须处理项排在当天新增的非待办之前。
- `近期变更` 中不存在仅因 `source_lane=reply_chain` 而被误判的事项。
- 8 月 11 日最终业务日期补采的 31 条汇报能够进入重新生成的当日页面，不再只展示初始 bounded collector 的 18 条候选。
- HTML 使用单文件、无外部前端依赖；关闭 JavaScript时 Markdown 仍按同样三类保持可读。
- Shadow Mode 权限边界保持不变，页面不产生任何 CWork 写操作。

## 13. 2026-08-12 本人与汇报关系标记补充契约

### 业务目标

当当前账号能读取某篇汇报、但本人既不是汇报人，也不在接收、建议、决策、审批、反馈等节点人员清单中时，页面必须明确标记为“仅权限可见 · 与我无关”，避免把可见权限误解为业务责任。

### 判定规则

- 员工 ID 是本人身份的主键；姓名仅作为显式配置后的兼容证据，不从正文提及推断关系。
- `writeEmpId` 命中本人时，关系为 `author`。
- `nodeList[].userList[].empId` 命中本人时，关系为 `participant`，并按节点类型细分为决策人、建议人、接收人或其他参与人。
- `outbox/history_outbox` 是本人发件的强关系证据；`todo_pending/history_todo_pending` 是本人当前或历史待办的强关系证据。
- `inbox/unread/pending/date_range_search` 只证明账号可见，不能单独证明本人是收件人。
- 只有本人身份已配置、节点详情完整返回、且所有强关系证据均未命中时，才能标记 `visible_only=true`。
- 节点详情缺失或本人身份未配置时，必须标为 `unknown`，不得武断标记“与我无关”。
- 仅权限可见的卡片不得标为必须处理，也不得提供提交建议、审批或发表意见预览；只保留本地知悉、跟踪、稍后查看和查看原文。

### 展示规则

- 行动中心卡片显示醒目的 `仅权限可见 · 与我无关` 标记，并使用弱化视觉样式。
- 每日简报按组显示仅权限可见数量；整组均无关时直接显示同名标记，混合组显示“其中 N 条仅权限可见”。
- 页面总览显示仅权限可见数量，但这些条目不计入“必须处理”。
- JSON/Markdown/HTML 三种输出必须使用同一判定结果。

### 验收场景

| 场景 | 期望结果 |
|---|---|
| 本人是汇报人 | `relationship_status=author`，不显示无关标记 |
| 本人在接收人节点 | `relationship_role=recipient`，不显示无关标记 |
| 本人在建议/决策节点 | 使用对应角色与办理动作，不显示无关标记 |
| 本人不在完整人员清单 | `visible_only=true`，显示特殊标记，`mandatory=false` |
| 节点接口数据缺失 | `relationship_status=unknown`，不显示“与我无关” |
| 仅权限可见但正文提到本人姓名 | 仍为 `visible_only`，正文自然语言不作为关系证据 |
