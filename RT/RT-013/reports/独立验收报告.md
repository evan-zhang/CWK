### 4.2 T-11 一 Agent 一 tenant — **PASS**

- **拒双绑**：`bind-agent` 对已 active/suspended 的 hash 返回 EXIT_CONFLICT=3；
  跨 tenant 的重复 bind 同样 conflict（`agent already bound (tenant=..., status=...)`)。
- **rebind 强制两步**：`rebind-agent` 内部 = revoke_out + bind_in，两条 receipt
  分别 emit；`binding_epoch` 单调 +1（覆盖 old revoke → new bind 循环）。
- **revoke → resolve 拒绝**：revoke 后 4 项 purpose（`query_broker /
  collector_run / profile_ai / sampling_collect_bounded`）全部 `BindingRevoked`
  (code=revoked)；auth_epoch 从 2 → 4（`bump_auth_epoch` on revoke）。
- **stale context 复现**：revoked 状态不可再次 resolve；rebind 前 revoked 记录
  的 `binding_epoch` 保持，新 bind 从 revoked epoch+1 继续单调。
- **并发 CAS 8×**：`ThreadPoolExecutor(max_workers=8)` 8 个并发 `bind` 同一 raw
  agent id → 恰好 1 个 OK，7 个失败（`RevisionConflict`，见 Minor-2）；最终 record
  唯一，无双绑。
- **directly re-write 磁盘绕过 API**：手工 `A.write_atomic()` 将 revoked record
  改为 active，仍会在 `resolve()` 阶段被 tenant status gate 拦截（当前 tenant
  为 draft）；但如果 tenant 也是 active，`binding.status = active` 会被信任，因为
  RT-013 没有 receipt-绑定 record 的完整性验证。**这依赖 host service account
  独占 `registry/` 目录（0700/0600）** — 与 RT-012 相同的 assumption，非 RT-013
  独有；记为 §5 Minor-3。

### 4.3 T-10 撤权 + T-01 tenant 状态权限矩阵 — **PASS**

- `TENANT_OPERATION_MATRIX`（RT-012）与 broker 的 `_PURPOSE_ALLOWED_STATUSES`（RT-013）

  | draft | ∅（broker.lease 全拒） |
  | profile_pending | `sampling_collect_bounded / profile_ai / profile_confirm` |

### 4.5 T-11 rotation / disable / CAS / fault injection — **PASS**

- **binding-secret rotation**：`BindingSecretStore.rotate_begin(new_material=...)`
  → 写 `binding-secrets/material/2.material` → pointer `stable → dual_write`；
  期间 `bind / revoke / suspend / reactivate` 全部 `_refuse_mutations_during_rotation`
  抛 `BindingConflictError`（4 项独立复现）；`resolve()` 期间 double-probe
  current + secondary，old-epoch record 仍可 resolve。`rotate_finalize`
  → pointer `dual_write → stable(current=new)`；old-epoch records 全部移入
  `tombstone/<old_epoch>/`；resolve 找不到该 raw agent id（`BindingNotFound`）；
  operator 必须 re-bind。
- **credential rotation**：`rotate_begin(new_reference_uri=...)`
  → record.rotation.state=`dual_write`；期间 `broker.lease()` 抛
  `CredentialStateError('credential rotation in-flight (state=dual_write)')`；
  `rotate_finalize` → status=active、rotation.state=stable；lease 携带 NEW canary，
  不携带 OLD canary。tombstone 目录下 `t_<tid>.json` 无 OLD/NEW canary（只有
  reference_uri + backend + epoch + actor/reason）。
- **disable / revoke credential**：disable → subsequent lease `CredentialStateError`；
  revoke → 同样拒绝。auth_epoch 与 credential_epoch 同步 bump。
- **crash between rotate_begin and rotate_finalize**：手工模拟；`recover()`
  返回 `{'orphans_removed':0, 'journal_swept':N}` 幂等，两次调用第二次为 0；
  pointer 仍在 dual_write（recover 不强制 finalize，只清孤儿）；期间 mutation
  仍被拒。手工 `rotate_finalize` 后恢复正常。
- **schema tampering fail-closed**：注入 `raw_agent_id / credential_ref /
  attacker_field / super_active status / bad revoked_at`；`validate_binding_record`

### Minor（不阻塞 RT-014 / RT-015；建议在下一 RT 或 RT-024 顺手闭合）

- **Minor-1（新观察）**：`BindingRegistry._read_record_at()` 在 `strict_json_loads`
  抛 `json.decoder.JSONDecodeError` 时未被捕获包装为 `BindingRecordCorruption`；
  外层 CLI `except Exception` 兜底为 `EXIT_INTERNAL=6`。fail-closed 与不打印
  traceback / 绝对路径均正确，但退出码语义应为 `EXIT_CONTRACT=2`。修法：`_read_record_at`
  除 `C.ContractError / UnicodeDecodeError` 外，再显式 `except
  json.JSONDecodeError` → `raise BindingRecordCorruption(...) from exc`。

- **Minor-2（新观察）**：`CredentialBroker.lease()` 签名为
  `lease(agent_id_hash, tenant_id, purpose)`，与 rt-intake `需求契约.md` §7
  "Broker `lease(agent_context, purpose)` " 表述不一致；且 `agent_id_hash`
  仅做 64-hex shape 校验，不与 `tenant_id` 交叉核验（无 binding registry 查询）。
  当前威胁模型下不构成真实运行时越权（tenant_id 语法严约束，且 host service zone
  外无 caller），但违反 defense-in-depth。修法：让 `lease()` 接受
  `AgentContext`，从中取 `agent_id_hash / tenant_id`，同时校验
  `agent_context.tenant_id == binding_registry.resolve(...).tenant_id`（若能通过
  ID 反查而不牺牲 raw-id 无落地）。或以更小侵入方式：`lease(agent_context, purpose)`
  Wrapper + 内部去调用现有 `lease(hash, tid, purpose)`。

- **Minor-3（新观察）**：`registry/agent-bindings/current/<hash>.json` 与
  `registry/credentials/<tid>.json` 的完整性仅由 `A.cas_write` 的
  `expected_previous_sha256` 保护（用于 CAS 更新），不含 record-level 完整性
  校验。若攻击者直接写盘覆盖（例如把 revoked 改回 active），下次 `get_by_hash`
  仍按 payload 表面语义信任 → binding.status = active。**这依赖 host service
  account 独占 `registry/` 目录（0700 / 0600）**，与 RT-012 独立验收 §4.5 同层
  的信任假设；不是 RT-013 独有的问题。建议 RT-024 引入 receipt-绑定的
  outer-integrity（例如以 `provisioning.last_receipt_sha256` 反算 payload subset
  的 canonical sha256）。

- **Minor-4（新观察）**：RT-013 broker 的 `_PURPOSE_ALLOWED_STATUSES` 与 RT-012
  `TENANT_OPERATION_MATRIX` 语义漂移：
  - `_PURPOSE_ALLOWED_STATUSES['sampling_collect_bounded']` = `{profile_pending,
    pilot, active}`；
  - `TENANT_OPERATION_MATRIX['pilot' | 'active']` 都不含 `sampling_collect_bounded`。
  两道 check 组合下 fail-closed 保护（第二道 check 兜底），但表格语义应该一致。
  建议 broker 直接读 `TENANT_OPERATION_MATRIX`，或在文档中显式声明"broker 表
  为超集，最终以 RT-012 matrix 为准"。

- **Minor-5（新观察）**：`_read_record_at()` 只校验 `payload["agent_id_hash"]`
  与文件名一致，不校验 `payload["tenant_id"]` 与已知 tenant registry 交叉。
  攻击者 disk 直写可造出"hash 匹配文件名，tenant_id 指向任意 t_-prefixed 值"的
  记录；`get_by_hash` 会通过，但 `resolve()` 在 `_tenant_registry.get(tenant_id)`
  处若 tenant 不存在会 `TenantNotFound` fail-closed。若 tenant_id 指向 A 而
  binding 原本属于 B，则会误认 A 为该 hash 的合法 tenant。属"host disk write
  威胁下 tenant confusion" 风险，与 Minor-3 同层信任假设。

- **Minor-6（新观察）**：`_check_actor_reason` 只检查 `str` / 非空 / 长度上限，
  不拒 NUL / CR / LF / tab / Unicode 控制字符。actor/reason 会写入
  `state_history[].actor / reason` 与 receipt payload。审计若以文本查看，可能
  触发日志行注入。与 RT-012 独立验收的 Minor-3 (`state_history[].actor` NUL)
  同层建议：在 RT-013 或 RT-024 内深扫控制字符。

- **Minor-7（新观察 — 已知设计约束）**：`recover()` 无条件 unlink 所有
  `journal/*.journal`（`orphans_removed` + `journal_swept`）。若一次调用与另一
  legitimate mutation 的 phase-1(journal write) 到 phase-2(CAS) 之间竞争，journal
  可能被误清（但 CAS 是原子的，不会造成 record 损坏，只是审计事件的
  txn_id 记录丢失）。属"审计连贯性" 边缘 case，不构成安全违反。建议 recover()
  加"孤儿判定"：只清 orphan 到某个 age 阈值以上，或验证对应 record 已 finalize。

上述 7 项 Minor 均**非安全阻塞**，独立验收判定"允许启动 RT-015"。
