# RT-013 技术方案

## 1. 模块拆分与代码所有权

| 模块 | 职责 | 冻结点 |
| --- | --- | --- |
| `scripts/cwk_agent_binding.py` | Binding Registry (`bind/rebind/revoke/suspend/reactivate`)；HMAC hash；binding_epoch；secret rotation；receipt append；tenant `auth_epoch` bump | `BINDING_STATES = ('active','suspended','revoked')`；`HASH_LEN=64`；`SECRET_MIN_BYTES=32`；receipt schema id；`RESOLVE_HIT_STATUSES = ('active',)` |

| `PR/.../rt013/schemas/*` | 5 张 RT-013 v1 schema | `additionalProperties:false + unevaluatedProperties:false`，enum + pattern + forbidden fields |

## 2. 磁盘布局

RT-013 只在 RT-012 已预建的两个目录 (`registry/agent-bindings/`,
`registry/credentials/`) 下写入；`registry/binding-secrets/` 由 RT-013 首次
`ensure_secret_store()` 创建。

```
CWK_INSTANCE_ROOT/
├── registry/
│   ├── agent-bindings/
│   │   ├── current/<agent_id_hash>.json          # 活跃 binding record
│   │   ├── receipts/<receipt_id>.json            # 追加式审计 receipt
│   │   ├── journal/<binding_txn>.journal         # 未提交事务
│   │   └── tombstone/<binding_secret_epoch>/<old_hash>.json  # rotation 后旧 hash 归档
│   ├── credentials/
│   │   ├── <tenant_id>.json                      # 每租户 credential reference
│   │   ├── receipts/<receipt_id>.json
│   │   ├── journal/<credential_txn>.journal
│   │   └── tombstone/<credential_epoch>/<tenant_id>.json  # rotation 归档旧 ref
│   └── binding-secrets/
│       ├── pointer.json                          # {rotation_state, current_epoch, secondary_epoch, previous_epoch}
│       ├── material/<epoch>.material             # 0o600 opaque HMAC material（合成/测试）
│       └── receipts/<rotation_receipt>.json
```

- 所有文件 `0o600`；所有目录 `0o700`；umask 无关（`os.fchmod`）。
- 每个业务子目录都是 RT-012 `registry_fd()` 无法直接暴露的深子目录，本 RT
  用 `child_fd` + `_open_child_dir` 追加解析（RT-013 内部的深子目录 grammar 一
  样是 `_LEAF_ALLOWED`）。

**注意：material 不入 audit / receipt / log / manifest / prompt / git。**
`material/` 目录只在合成/测试 backend 使用；生产环境要求外部 secret backend
（Keychain / env / KMS），本 RT 仅提供 `env_ref` 与 `file_ref` 两个 adapter，
`file_ref` 的 material path 也不在 receipt 中记录（只记 `reference_uri`）。

## 3. Binding Registry

### 3.1 数据结构

```json
{
  "schema": "cwk.rt013.agent_binding.v1",
  "agent_id_hash": "<64-hex>",
  "tenant_id": "t_...",
  "binding_epoch": 3,
  "binding_secret_epoch": 2,
  "status": "active",
  "bound_at": "2026-08-19T02:00:00Z",
  "updated_at": "2026-08-19T02:05:00Z",
  "revoked_at": null,
  "provisioning": {
    "last_receipt_id": "rbnd_...",
    "last_receipt_sha256": "<64-hex>"
  },
  "history": [
    {"action": "bind", "at": "...", "actor": "...", "reason": "...", "binding_epoch_after": 1, "binding_secret_epoch": 1}
  ]
}
```

### 3.2 API

```python
BindingRegistry(layout)
    .bind(tenant_id, raw_agent_id, actor, reason)       # 拒绝 rebound-elsewhere
    .rebind(raw_agent_id, new_tenant_id, actor, reason) # revoke_old + bind_new
    .revoke(raw_agent_id, actor, reason)
    .suspend(raw_agent_id, actor, reason)
    .reactivate(raw_agent_id, actor, reason)
    .resolve(raw_agent_id, purpose) -> BindingRecord   # active + tenant policy
    .list_active() -> list[BindingRecord]
    .rotate_secret(new_epoch, new_material, actor, reason)
    .recover() -> summary
```

`resolve()`：

1. 读 pointer 一次快照 `(rotation_state, current_epoch, secondary_epoch)`。
2. `hash_current = HMAC(current_material, raw_agent_id)`。
3. 若 `current/<hash_current>.json` 存在 → 加载 record（必须 `status=active`）。
4. 否则若 `rotation_state=dual_write` 且存在 `secondary_material` →
   `hash_secondary = HMAC(secondary_material, raw_agent_id)`；查
   `current/<hash_secondary>.json` 或 `pending/<hash_secondary>.json` → 加
   载 record（`binding_secret_epoch=secondary_epoch`）。
5. 记录 hit 使用哪个 epoch，供审计。
6. 检查 tenant 状态：`TenantRegistry.get(tenant_id)` → status must satisfy
   `purpose ∈ TENANT_OPERATION_MATRIX[status]`；否则 fail closed。
7. 返回 `AgentContext(agent_id_hash, tenant_id, binding_epoch, tenant_auth_epoch,
   tenant_status, credential_epoch=None)`。
8. **绝不缓存** raw_agent_id 或 material；raw_agent_id 只在函数局部 stack 上
   短暂存在，随后 HMAC 结果覆盖。

### 3.3 mutate 事务顺序

所有 mutate 命令持有 `exclusive_lock(agent_bindings/current/.<hash>.lock)` +
`exclusive_lock(registry/tenants/.<tenant_id>.lock)`（先小后大字典序，避免
死锁）。事务：

1. 写 journal `journal/<binding_txn>.journal`（记录 action + actor + reason）。
2. `write_atomic()` 或 `cas_write()` 更新 record。
3. `TenantRegistry.bump_auth_epoch(tenant_id, actor, reason, expected_auth_epoch)`
   — 若 CAS 冲突：由 caller 处理（本 RT bind 前会先 `TenantRegistry.get()` 读
   auth_epoch）。
4. 计算 receipt sha，写 `receipts/<receipt_id>.json`。
5. Unlink journal。

崩溃恢复：`recover()` 遍历 journal；若对应 receipt 已 durable，unlink journal；
否则回滚 record（若 record 尚未持久化到 disk / sha 不匹配）。

### 3.4 Stage-10 late-snapshot 并发封口

`bind()` 的早期 existing-record 检查只用于快速拒绝，不能作为 CAS 时刻的授权
事实。构造新 payload 前的第二次 `get_by_hash()` 是最终 predecessor snapshot：

1. 不存在 → `expected_previous_sha256=None`，后续受 lock 内 CAS 保护；
2. `status=revoked` → 允许继承 epoch 与 previous SHA，保留两步 rebind；
3. `status=active|suspended` → 立即 `BindingConflictError`，不写 journal、record、
   receipt，也不 bump tenant auth_epoch。

确定性测试让两个线程都先观察 absent，再阻塞 loser 的第二次读取直到 winner 完成；
因此不依赖概率调度即可证明 loser 不能把 winner record 合法 CAS 成 epoch 2。
这次兼容修订只经中央 Stage-10 receipt 演进，不修改 binding schema 或 CLI ABI。

## 4. Credential Broker

### 4.1 数据结构

```json
{
  "schema": "cwk.rt013.credential_ref.v1",
  "tenant_id": "t_...",
  "reference_uri": "secret://<opaque>",
  "backend": "env_ref",
  "status": "active",
  "credential_epoch": 2,
  "created_at": "...",
  "updated_at": "...",
  "rotation": {
    "state": "stable",
    "secondary_reference_uri": null,
    "secondary_backend": null,
    "secondary_credential_epoch": null,
    "previous_credential_epoch": 1
  },
  "provisioning": {
    "last_receipt_id": "...",
    "last_receipt_sha256": "..."
  },
  "history": [...]
}
```

### 4.2 Backend

```python
class CredentialBackend(Protocol):
    def read_material(reference_uri: str) -> bytes: ...
```

RT-013 实现两个 backend：

- `EnvRefBackend`：`reference_uri = "secret://env-CWK_CRED_<opaque>"`；从 `os.environ` 读同名 var，读完立即从副本清除。此 backend 只用于合成/测试。
- `FileRefBackend`：`reference_uri = "secret://file-<opaque>"`；material 路径在 broker 构造时以字典注入 `{opaque_id: absolute_path}`；path 不进入 record / receipt。

Broker 不实现 Keychain / KMS — 生产 backend 由 RT-026 之后独立 PR 加入并做独立审核。

### 4.3 Lease 流程

```python
with CredentialBroker(layout, backend_registry).lease(agent_context, purpose="collector_run") as lease:
    # lease.env == {"CWK_INSTANCE_ROOT": ..., "CWORK_APP_KEY": <material>}
    # lease.reference_uri, lease.credential_epoch, lease.lease_id 可用于审计
    subprocess.run(..., env=lease.env, ...)
# 退出时 lease.env["CWORK_APP_KEY"] = "\0" * len；lease.env 变为 {}；material 局部变量置 None
```

保证：

- `lease.env` 只含白名单 key；purposeful `CWORK_APP_KEY` 是唯一敏感 key；
- lease id 只是一个不透明 audit 引用；audit receipt 只含 lease_id / reference_uri /
  credential_epoch / purpose / tenant_id，绝不含 material；
- purpose 校验：
  - `collector_run/scheduler_run/query_broker` → tenant 必须 `pilot|active`；
  - `sampling_collect_bounded/profile_ai/profile_confirm` → tenant 必须
    `profile_pending|pilot|active`；
  - `admin_configure` → 不允许通过 broker 拿 material（凭据管理不需要 material）；
- 违反 → `CredentialPolicyError` → EXIT_CONTRACT。

### 4.4 Rotation

1. `rotate-credential --new-reference-uri secret://<opaque2> --new-backend env_ref`
   → 新 record `rotation.state="dual_write"`, `secondary_reference_uri=<new>`,
   `credential_epoch += 1`；
2. Broker 读时：`state=dual_write` 且 `purpose in {read-only lookups}` 允许双读
   material 校验（本 RT 不做健康检查，只标注 policy 位）；`purpose in mutate` →
   read secondary（active writer 使用新 secret）；
3. `finalize`：atomic rewrite record `rotation.state="stable"`, secondary → null,
   `previous_credential_epoch = current-1`；旧 reference 归档到
   `credentials/tombstone/<epoch>/<tenant_id>.json`；
4. `disable-credential` 立刻 status=`disabled`；`bump_auth_epoch`。

Rotation 期间 `resolve()` 使用 record 一次快照，返回一致的 reference；不会命中
「旧 reference + 新 record」的中间态。

## 5. AgentContext

```python
TRUSTED_AGENT_SOURCES = frozenset({"gateway_authenticated_context", "admin_cli"})

@dataclass(frozen=True)
class AgentContextSnapshot:
    agent_id_hash: str
    tenant_id: str
    tenant_auth_epoch: int
    binding_epoch: int
    binding_secret_epoch: int
    tenant_status: str
    resolved_at: str  # ISO 8601 UTC

class AgentContext:
    @classmethod
    def from_trusted(cls, *, raw_agent_id, source, purpose, layout) -> "AgentContext":
        if source not in TRUSTED_AGENT_SOURCES:
            raise AgentContextError(f"untrusted source {source!r}")
        ...
    def snapshot(self) -> AgentContextSnapshot: ...
    def redact(self) -> dict:
        # only hash + tenant_id + epochs — never raw_agent_id / material
        ...
```

- `from_trusted` 内部立刻通过 `BindingRegistry.resolve(raw_agent_id, purpose)`；
  raw_agent_id 仅在栈上短暂存在，用完置 None；
- **`__init__` 不接受 raw_agent_id**，只接受 snapshot；所有构造走 `from_trusted`；
- `__repr__` / `__str__` 只输出 hash 前 8 位 + tenant_id 前 8 位 + epoch，不
  出现 raw_agent_id / material；
- `snapshot()` 是缓存键的组成来源；缓存实现（RT-022）复用 snapshot 元组。

  立即从内存移除并 zero-out；

## 8. Doctor 输出

RT-013 doctor：

- binding-secrets pointer 存在且合法；
- 每个 `current/*.json` 通过 schema 校验；
- 每个 receipt 通过 schema 校验；receipt_sha256 与内容匹配；
- journal 无残留（若有：告警并建议 recover）；
- credentials/<tid>.json 均属存在 tenant；status 与 tenant 状态兼容（`disabled`
  凭据 + `active` tenant 只是 warn，不是 error）。

Doctor **不读**：material、raw agent_id、tenant view / access ledger / raw。

## 9. 稳定退出码

沿用 RT-012：`{0, 2, 3, 4, 5, 6}`。

- `EXIT_CONTRACT=2`：schema / 状态机 / 策略；
- `EXIT_CONFLICT=3`：双绑冲突 / CAS 冲突；
- `EXIT_USAGE=4`：缺参 / 未知命令；
- `EXIT_IO=5`：文件缺 / tenant 缺 / material 缺；
- `EXIT_INTERNAL=6`：未预期。

## 10. 失败模型

| 失败 | 表现 | 处理 |
| --- | --- | --- |
| tenant 不存在 | `TenantNotFound` (RT-012) | EXIT_IO |
| agent 已绑他 tenant | `BindingConflictError` | EXIT_CONFLICT |
| unknown agent hash 请求 resolve | `BindingNotFound` | EXIT_IO |
| revoked / suspended agent 试 resolve | `BindingRevoked` / `BindingSuspended` | EXIT_CONTRACT |
| tenant 非 `pilot|active` + `collector_run` purpose | `CredentialPolicyError` | EXIT_CONTRACT |
| backend 缺 material | `CredentialBackendError` | EXIT_IO；**不 fallback repo `.env`** |
| CAS 冲突 | `BindingConflictError` / `RegistryConflict` | EXIT_CONFLICT |
| receipt sha 篡改 | `SchemaError` | EXIT_CONTRACT |
| 未预期异常 | dispatcher `_print_stable_error` + `internal failure (<Class>)` | EXIT_INTERNAL |

## 11. 与 legacy `.env` / cron / DocDB 的关系

RT-013 **不读 .env、不读 CWORK_APP_KEY、不启动 cron、不写 DocDB**。测试全部使用
`mktemp -d` + fake backend。任何试图 fallback 到 repo `.env` 的路径都被显式测试
拒绝。

## 12. 与 conservative_unknown 的关系

RT-013 不解锁 RT-011 冻结的 `conservative_unknown`：

- 真实 Gateway Tool / UDS peercred 通道 → RT-023；
- 真实撤权事件 / API → 由后续 RT 消费；
- report_id 全局唯一 → 与本 RT 无关。

`AgentContext.from_trusted` 的 `source` 参数值 `gateway_authenticated_context`
只是一个静态标签；真实通道生效前，`admin_cli` 是唯一的实际 caller。RT-023 加入
真实通道时，把 source 加入到 `TRUSTED_AGENT_SOURCES` 白名单即可，无需改本 RT。
