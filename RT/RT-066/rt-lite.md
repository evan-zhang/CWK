# RT-Lite: RT-066 - 线上鉴权切换到成员表判定

> profile: Spec-Lite | execution_mode: collaborative

## 方案（给人看）

- 做什么：把线上检索（8787）和问答（8790）的权限判定，从"看令牌自带的库清单"
  切换到"看成员表"。只改一个环境开关，不改任何产品代码。
- 为什么：RT-061 把成员表、身份绑定、等价性核对都做好了，但开关一直停在旧方式，
  所以"加/收权限立即生效、不用重发令牌"这件事还没真正成立。RT-065 让同事能自助报到之后，
  这一步的收益才完整。
- 代价：多一份线上依赖——成员表文件。它读不出来时所有请求一律拒绝（fail-closed），
  这是有意的，但意味着这个文件从此和令牌登记表一样重要。
- 这次故意不做什么：不改产品代码、不动令牌、不加新库、不给任何人新权限。
- 用户怎样算成功：切换前后，同一批请求的放行/拒绝结果逐项相同；
  并且能现场演示"改一条成员记录，十秒内生效"。
- 建议：定论。等价性已由代码核对过，回退是改回开关重建两个容器。

## 切换前必须成立的前提

1. `check-equivalence` 返回 0：逐支有效令牌 × 逐个库，两种判定结果完全一致。
2. `check` 返回 0：没有"令牌没有身份"、"库缺所有者"、"服务没被授权"这类问题。
3. 成员表文件在两个容器里都读得到（它和令牌登记表同目录，已经挂进去了）。

## 步骤

1. 线上跑两道核对，都必须是 0。
2. 备份 OPS 本地的两个 compose 覆盖文件。
3. 给 retrieval 与 rag-answer 加 `RAG_AUTHZ_MODE=grants` 与 `RAG_AUTHZ_PATH=/app/auth/kb-authz.json`。
4. 渲染配置与运行中的容器逐项比对，只应多出这两个变量。
5. 带 `KB_BIND_ADDR=0.0.0.0` 重建两个容器（否则服务会掉出局域网——RT-062/061 各踩过一次）。
6. 跑切换前录好的 20 项行为探测，逐项对照。

## 验证

- **等价判据**：20 项探测在切换前后逐项相同。
- **成员表真的在起作用**（这一条不做，就无法区分"切换成功"和"开关没生效"）：
  临时移除某个库上问答服务的只读授权 → 该库的问答/检索应立刻变成 403 →
  恢复授权 → 立刻恢复 200。全程不碰令牌。选影响最小的库，改完立即恢复。
- **回退演练**：把开关改回 `scope` 也要能一把恢复（记录命令，必要时真跑一次）。

## 变更记录

- 用户能感到什么变化：正常使用无感；此后加/收权限约 10 秒生效，不用重发令牌。

## 遗留事项

- 8787/8790 仍然没有访问审计（服务端为防正文泄露不记请求）。
  切到成员表之后，"谁在什么时候被拒了"更值得留痕，建议下一个 RT 补只记
  「时间 / 令牌 ID / 库 / 结果码」的审计。
