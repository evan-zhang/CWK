# RT-Lite: RT-060 - 文档中心与首页瘦身

> profile: Spec-Lite | execution_mode: collaborative

## 方案（给人看）

- 做什么：首页回归产品介绍，给没用过的人看；深度内容搬进文档中心，分五页：
  快速开始、架构与部署、API 参考、扩展开发、常见问题。参照 DeepSeek/OpenAI 这类
  产品站的分层方式。
- 为什么：RT-059 的单页把招揽和手册压在一起。小白看着累，想深入的人又没有系统的入口；
  而且再往里加 API 参考和扩展开发，单页会彻底失控。
- 代价：多了一层路由和一套侧栏布局；文档页与仓库里的 `docs/` 有内容重叠，要防止两处漂移。
- 这次故意不做什么：不做搜索框、不做版本切换、不引入前端框架或构建步骤；
  不开放公网；不把写操作放进 API 面。
- 用户怎样算成功：首页不看技术细节就能判断"要不要接"；文档中心侧栏每一页都打得开；
  照着 API 参考写的调用能被服务端接受。
- 建议：定论——API 参考的字段与限制直接对齐服务端契约，并用判据锁住，
  文档写错比没有文档更糟。

## 站点结构

```
/                    首页（产品介绍）
/docs                文档中心首页（卡片导航）
/docs/quickstart     快速开始（五步接入）
/docs/architecture   架构与部署（两张图 + 数据来源）
/docs/api            API 参考（三个端点）
/docs/extend         扩展开发（适配器 + Agent 接入）
/docs/faq            常见问题与边界
```

外壳与侧栏由 `_shell()` / `_doc_page()` 统一渲染，页面正文是纯内容常量；
新增一页只要往 `_DOC_NAV` 和 `_DOC_BODIES` 各加一条。

## 假设与现状

- 关键假设：内部团队要的"开放接口"就是现有三个端点的准确契约，不是新建一套面向外部的
  API 网关。因此本 RT 只做文档，不动服务。
- 现状依据：`adapters/opensearch_retrieval/service/contract.py`（`/query` 的字段白名单、
  4096 字符与 top_k 上限、三个错误码）、`adapters/rag_answer/server.py` 与 `pipeline.py`
  （`/answer` 与 `/read` 的字段与 400/404/416/503）、`docs/ADAPTER-CONTRACT.md`（四个操作）。

## 实现备注

- 只改 `scripts/kb_portal.py`，新增 `tests/test_rt060_docs_center.py`，
  并把 `tests/test_rt059_kb_website.py` 的判据指向内容搬家后的新位置。
- 路由只认注册过的 slug，路径里的任何内容都不会被当成文件名去找。
- 不能破坏的约定：门户仍不导入任何数据模块；页面不出现库内数据；
  控制台与 8787/8790 不受影响。

## 验证

- `tests.test_rt060_docs_center` 17 条：侧栏每页可达、文档首页链齐、未知 slug 与
  路径穿越都是 404、写方法 405；首页不得再出现命令、接口字段和图；
  API 参考的字段、错误码齐全，且长度与 top_k 上限**直接读服务端契约模块**比对。
- `tests.test_rt059_kb_website` 25 条改为按路由取页，意图不变。
- 真实浏览器：逐页打开，确认侧栏高亮、表格、代码块与复制按钮。
- 部署后从局域网复验每条路由。
