# RT-Lite: RT-058 - 知识库内网门户与管理控制台 v1

> profile: Spec-Lite | execution_mode: collaborative

## 方案（给人看）

- 做什么：产品目标是「官网 + 管理控制台」，本 RT 交付第一段——面向局域网的静态门户，
  加上管理控制台 v1（三个只读视图表格化、一次输密钥、错误态区分、环境标识），
  并补上「鉴权失败不进审计」这个观测缺口。
- 为什么：现有管理台是一页三个按钮把原始 JSON 倒进一个框，每点一次弹一次密钥框；
  而且谁在外面试密钥，管理审计里看不见——成功的操作记账，被拒绝的不记。
- 代价：门户是第二个进程，运维多一个要看的东西；控制台仍是单一共享密钥，没有每人身份。
- 这次故意不做什么：不做真实建库、摄取、用户管理和授权签发；不改 8787/8790；
  不把任何东西默认绑到局域网；不引入前端框架或构建步骤。
- 用户怎样算成功：打开门户能看懂这是什么、有哪几个库、怎么申请接入，并能一键进控制台；
  在控制台输一次密钥就能看三个视图，数据是表格不是 JSON；密钥错了、服务挂了、
  写开关拦了，三种情况的提示不一样；试错密钥能在审计里查到。
- 建议：定论——门户与控制台必须分进程。理由见下。

## 假设与现状

- 关键假设：门户要给同事看就得能绑局域网，而管理台不能。共用进程就共用绑定地址，
  让门户可见等于把管理 API 一起暴露。
- 因此门户的隔离不靠路由表，靠**导入**：`kb_portal` 不导入 `kb_ops` / `kb_storage` /
  `kb_token` / `kb_ledger` / `kb_admin`，也没有任何指向登记表、库目录或审计文件的配置项，
  从 HTTP 请求到管理数据之间不存在代码路径。路由能被误加，导入不会被误加，
  所以判据盯的是导入。
- 现状依据：`scripts/kb_admin.py` 的 `_HTML` 与 `handle`；`kb_ops.registry_projection`
  的脱敏白名单；RT-056 定下的「默认关闭 + 默认回环 + 写动词占位」三条不变。

## 实现备注

- 新增 `scripts/kb_portal.py`（静态门户，stdlib，零数据访问）与
  `tests/test_rt058_kb_console.py`；改 `scripts/kb_admin.py`（401 审计、审计读审计、
  控制台页面重写、`/console` 与 `/` 同页）。
- `scripts/` 是 exact-only 区，新脚本补了一条 exact_set 规则；治理夹具的代表文件清单
  同步加了 `scripts/kb_portal.py`——RT-057 刚修过同类漏加，不能又犯。
- 规则没有与 RT-056 合并成一条：两者暴露面不同（门户可绑局域网、无数据访问；
  管理台默认回环、持有登记表与审计路径），合并会让这条边界在清单上消失。
- 改了 RT-056 的一条 UI 断言：页面标题从「知识库管理台」改为「知识库管理控制台」，
  取数方式也变了。那条判据要守的是「原生 HTML + fetch 现取」，按此重写，未削弱。

## 变更记录

- 用户能感到什么变化：有了一个能发给同事看的产品说明页，和一个输一次密钥就能用、
  数据以表格呈现的管理控制台；试密钥的行为从此留痕。

## 遗留事项

- 依赖 RT-057：治理夹具里 RT-055/RT-056 两条规则的代表文件在 RT-057 分支上修复，
  未合并前本分支的 `tests.test_governance_audit` 仍有 5 个失败。**RT-057 必须先合并。**
- 审计文件在暴力尝试下会无界增长（每次 401 一行）。当前靠文件权限与人工巡检兜底，
  应补速率限制或轮转。
- 单一共享管理密钥、无每人身份、无失败锁定；这是把控制台绑到局域网之前必须先解决的。
- 门户的库列表目前是配置里的显示名，不是从服务实时读的——门户无数据访问是刻意的，
  要实时就得由控制台侧提供一个免鉴权的公开摘要端点，需单独设计。
