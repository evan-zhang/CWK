# RT-018 需求契约：宿主机 Tenant Scheduler

> 状态：planned。本文冻结可编码与可黑盒验收的 Scheduler 契约。

## 1. 业务目标

在共享宿主机上稳定运行多个 tenant 的独立数据作业，同时保证任何单 tenant 故障不会形成全局阻塞、串租户状态、密钥泄漏或重复 writer。

## 2. 角色

- Scheduler：只负责计划、租约、资源、公平、retry 与状态推进。
- JobProvider：把某一类业务作业转换成稳定 JobSpec 并执行；拥有自身业务逻辑 adapter。
- Tenant Registry：tenant 状态、revision、quota/auth epoch 的权威源。
- Credential Broker：由 provider 按需获取密钥租约，Scheduler 不接触 material。
- 平台管理员：通过显式测试/未来 release composition root 配置调度；本 RT 不修改生产 cron。

## 3. 输入

### 3.1 ScheduleTick v1

- `tick_id`、`scheduled_at`、`deadline_at`；
- `provider_selector`：可信 composition root 已注册的 provider name 列表；
- `tenant_selector`：空表示从 Registry 读取全部候选，或显式 opaque tenant ID allowlist；
- `resource_budget`：全局及 resource class 的并发上限；
- `dry_run`：在 RT-026 前默认为 true；
- 不允许 credential、命令、路径、用户脚本或动态 module name。

### 3.2 Provider 输入

Provider 只能得到不可变 `TenantJobSnapshot`：tenant_id、tenant status、record revision、auth_epoch、quota snapshot、trigger/tick id 和 deadline；不得得到其他 tenant 数据或明文 credential。

## 4. JobProviderV1 ABI

每个 provider 必须公开：

```python
API_VERSION = "cwk.job_provider.v1"
PROVIDER_NAME: str
PROVIDER_VERSION: str
JOB_KINDS: tuple[str, ...]

def plan(snapshot: TenantJobSnapshot) -> Sequence[JobSpecV1]
def execute(spec: JobSpecV1, context: JobExecutionContextV1) -> JobResultV1
def recover(spec: JobSpecV1, context: JobExecutionContextV1) -> RecoveryDecisionV1
```

规则：

- Provider object 由可信调用者显式注入 registry；禁止文件系统扫描、entrypoint、env plugin 或任意 import string。
- `plan` 必须纯且确定性；相同 snapshot 产生相同 idempotency key。
- `execute` 不得修改 Scheduler 队列或另一个 tenant；只能返回严格结果。
- 未知 API/provider/job kind、重复 provider name 或 version mismatch 均 fail closed。

## 5. JobSpec 与状态机

`JobSpecV1` required：schema、job_id、job_kind、provider_name/version、tenant_id、tenant_record_revision、tenant_auth_epoch、trigger_id、idempotency_key、resource_class、priority、attempt、created_at、not_before、deadline_at、input_ref。

- `job_id/idempotency_key/input_ref` 均为 opaque grammar；input_ref 必须 tenant-scoped。
- 禁止 credential_ref/material、正文、标题、query、event body、URL、绝对路径、argv/shell、agent ID。
- 幂等键使用 domain separator + length-prefix/JCS；不得用可歧义字符串相加。

状态机：

```text
planned -> queued -> leased -> running -> succeeded
                  -> retry_wait -> queued
                  -> circuit_open -> retry_wait|permanent_failed
                  -> cancelled
                  -> permanent_failed
running -> recovering -> queued|succeeded|permanent_failed
```

终态不可覆盖。每次跃迁带 expected revision/CAS、actor、reason、timestamp 和前后状态。

## 6. 调度规则

- enqueue、lease、execute 前分别重读 tenant；只有 `pilot/active` 允许继续。
- `active` 对 PilotAdmission 调用 0 次。`pilot` 的 Provider 在构造期绑定
  `purpose=collector_run`，在获取 writer lease 后、执行 Worker 前调用一次，在写
  succeeded/run manifest 前再调用一次；两次都必须 valid+admitted 且 policy revision
  不回退、policy/snapshot 不漂移。第一次失败不调用 Worker，第二次失败丢弃未提交结果，
  进入稳定拒绝/恢复状态。
- 同一 tenant 任一时刻只有一个数据面 writer；重复 tick/双触发只能有一个获得 tenant writer lease。
- 跨 tenant 使用确定性 deficit round-robin 或等价可证明公平算法；优先级不能造成低优先 tenant 永久饥饿。
- 错峰 offset 由 tenant_id HMAC/稳定 hash 与 schedule window 计算，不能使用可预测密钥或当前进程随机值导致重启漂移。
- 全局并发只控制资源；业务队列、retry、cursor、manifest 全部 tenant-scoped。
- 配额分别覆盖 source IO、AI、DocDB/derived（首期只启用 collector resource class）；一个 class 用尽不隐式借用无上限资源。

## 7. Retry、熔断与恢复

- Retry policy 按 provider/job kind 冻结最大尝试、deadline、base/max backoff 与 jitter；manifest 记录策略版本，不预填未经测量的性能指标。
- 429、timeout、temporary IO 可 retry；contract/schema/security/credential disabled 为 permanent 或等待管理员，不进行高频重试。
- 熔断键至少为 tenant + provider + resource class；A 熔断不影响 B，也不能全局关闭 provider。
- 进程重启发现 stale `leased/running`：调用 provider `recover`，结合 durable result receipt 判定 succeeded 或重新 queued；不得盲目重复不可幂等副作用。
- retry 超过 deadline/attempt 进入 permanent_failed，并保留 opaque 审计；不得无限循环。

## 8. Manifest 与可观测输出

每次 tick/run 产出严格 `RunManifestV1`：tick/job/provider/tenant opaque IDs、状态跃迁计数、attempt、时间、resource class、result/reason code、版本和 receipt refs。

禁止出现 AppKey、credential_ref/material、完整异常、正文、标题、event body、query、URL、绝对路径、env、argv。租户只可读取自己的摘要；全局管理员查看跨 tenant 时也只得脱敏健康元数据。

## 9. 异常与安全规则

- tenant lock 已占用：第二触发返回 `already_leased`，不阻塞其他 tenant。
- tenant status 在排队后变 suspended/offboarded：execute 前取消，不获取 credential。
- provider import/ABI/plan/execute 异常：本 provider/tenant fail closed，异常类型归一为 reason code。
- A 队列/manifest 目录损坏或满盘：A circuit/permanent failure，B 继续；不得回退仓库级 queue。
- host clock rollback/forward：deadline/lease 同时使用 wall-clock receipt 与 monotonic runtime 检查；异常进入 safe recovery。
- Scheduler crash：持久状态可恢复，无两个 writer、无丢失已提交 success。

## 10. 验收标准

- AC-018-01：同 tenant 双触发只有一个 writer，另一触发获得稳定非泄漏结果。
- AC-018-02：A 的 429、deadlock、timeout、bad config、provider crash、disk full 不影响 B 成功。
- AC-018-03：重启后 queued/retry_wait/stale-running 正确恢复，已成功 job 不重复副作用。
- AC-018-04：状态矩阵严格；draft/profile_pending/suspended/offboarded 不由常态 Scheduler 启动或解析 credential。
- AC-018-05：显式 registry 拒绝动态/未知/重复/version-mismatch provider；未来 provider 无需改 Scheduler ABI。
- AC-018-06：有界 retry、tenant-scoped circuit、quota 与 fairness 可由确定性测试证明；无永久饥饿。
- AC-018-07：run/job/manifest/lock/retry 完全 tenant-scoped，无仓库级状态回退。
- AC-018-08：manifest/log/error/temp secret scan 为 0，错误不含绝对路径或其他 tenant 信息。
- AC-018-09：legacy nightly、cron、installer、统一 feature flag 零漂移；默认无生产调度。
- AC-018-10：RT-017 Worker 通过 provider ABI 被调用，不复制 Collector 逻辑；fake 双租户端到端可进入 VG-B。
- AC-018-10a：`active` PilotAdmission 0 次；`pilot` 正常/重试/cache-free run 恰好两次，
  deny/unavailable/expiry/wrong purpose/tenant/hash/revision 回退及第二次 snapshot 漂移都
  fail closed 且无半 manifest；`profile_pending` 仍不进入常态调度。

## 11. 测试场景

- 正常：2/10 tenant 错峰、多个 tick、重复 tick、不同 provider resource class、dry-run 与实际 fake execute。
- 竞态：双进程同 tenant、lease 过期、CAS 冲突、status/auth_epoch 变化、crash 每个状态边界。
- 故障：429、timeout、deadlock、disk quota、bad config、bad result、clock skew、restart。
- 恶意：provider name/path/import 注入、JobSpec forbidden fields、manifest log injection、symlink/hardlink/TOCTOU。
- 回归：RT-011～018、全量 unittest、Wiki lint/smoke、legacy nightly fixture（不得执行生产 nightly）。
