# RT-067 复盘

## 目标达成了吗

达成。2026-09-20 上线，检索（query）、问答（answer）、读原文（read）三条路径都会留下访问记录。

线上实测：带令牌放行、不带令牌被拒、库不存在被拒，各自都记上了端点、库、结果码、原因、
令牌指纹与主体；翻查整份审计文件，搜不到任何文档编号、查询词或令牌明文。

## 做对了什么

- **打点打在唯一的共同入口**（`kb_auth.authorize`），三条路径一次覆盖，将来新增端点也不会漏。
- **把"不该记什么"也写成判据**。审计是最容易慢慢长出内容字段的地方，所以除了断言该记的记上了，
  还加了字段白名单，以及带着"绝密查询词/绝密正文/可辨识文档编号"跑真实 HTTP 请求、
  再回头搜审计文件的穿透检查。反向验证里"顺手加个查询词字段"当场变红。
- **失败姿态想清楚了**：审计写不进去时请求照常放行（可用性优先），但首次失败往容器日志打一行，
  不做"以为在记其实没记"的静默失败。
- 文件会轮转，只留一代，不会把服务器的盘写满。

## 踩到什么

- **自己踩了自己记下的坑**：仓库代码更新后忘了同步 `rag-overlay`，结果 8790 跑的还是旧代码，
  第一轮验证只看到检索的记录，没有读原文和问答的。幸好验证方式是"看审计里有没有这三类记录"，
  而不是"服务没报错就算成功"——否则这个缺口会被当成已完成。
  同步时又发现 overlay 里 `app.py` 也早已漂移，一并对齐，现在 overlay 与仓库逐文件一致。
- 教训：**凡是改 `adapters/` 的 RT，部署步骤必须包含"同步 overlay + 逐文件比对"**，
  而不是只在需要时才想起来。已写进下面的留档。

## 留给下一次

- 部署 `adapters/` 改动的固定动作：更新仓库 → 同步 overlay → `cmp` 逐文件确认 drift=0 →
  渲染配置比对 → 重建 → 按基线探测 → **按本次改动的特征做针对性验证**（这次是"三类端点都要有记录"）。
- 审计只落本地文件，没有集中收集或告警；控制台也还看不到这份记录（界面 RT 可一并纳入）。
- 回滚材料：`ops/backup-rt067/`（两个 compose 覆盖文件 + overlay 旧文件）。
  关掉审计只需去掉 `RAG_AUTH_AUDIT_PATH` 重建，服务行为不受影响。
