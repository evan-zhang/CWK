# RT-Lite: RT-067 - 检索与问答的访问审计

> profile: Spec-Lite | execution_mode: collaborative

## 方案（给人看）

- 做什么：给 8787 与 8790 加一条访问记录——谁、什么时候、碰了哪个库、结果如何。
  只记这些，不记查询词、不记文档编号、不记返回正文。
- 为什么：这两个服务为防正文泄露完全不记请求，代价在 RT-062 兑现了——读原文的洞开着好几天，
  事后无法确认有没有被人用过。切到成员表判定之后，"谁在什么时候被拒"更值得留痕。
- 代价：多一个会增长的文件；审计本身也是一处可能泄露内容的地方，所以字段要锁死。
- 这次故意不做什么：不记请求内容、不做查询界面、不接外部日志系统、不改任何鉴权判定。
- 用户怎样算成功：出事后能回答"这段时间有没有人被拒、是谁、碰的哪个库"；
  同时翻遍审计文件也找不到一句查询词或一段正文。
- 建议：定论。默认关闭，配了路径才写。

## 打在哪

`adapters/kb_auth.py` 的 `authorize()` 是三条路径（检索 /query、问答 /answer、读原文 /read）
唯一的共同入口，记录点放在这里，不必在每个端点重复，也不会漏掉将来新增的端点。

## 记录的字段（白名单）

```
ts 时间 | endpoint 端点 | bank 库 | status 结果码 | reason 原因
token_id 令牌指纹 | principal 主体 | client 来源 IP
```

放行与拒绝都记。`reason` 用的是鉴权本来就有的原因码（`unknown_token`/`revoked`/`expired`/
`kb_not_in_scope`/`not_a_member`/`bank_inactive`/`no_principal`…），不新造词。

## 不能破坏的约定

- 审计写不进去时，**请求照常处理**；但不能静默——首次失败往 stderr 打一行（进容器日志），之后不再刷屏。
- 文件 `0600`、目录 `0700`；超过上限自动轮转一次，只保留一代，不无限增长。
- 令牌明文与摘要都不写；`doc_id` 不写。

## 验证

- `tests/test_rt067_access_audit.py`（15 条）：放行/各类拒绝都被记；未配路径时一字节不写；
  鉴权关闭时不写；文件 0600、目录 0700；路径坏掉时请求仍放行；
  **真实 HTTP 请求穿透检查**——带着"绝密查询词/绝密正文/可辨识文档编号"跑真的 /answer 与 /read，
  审计文件里搜不到它们；**字段白名单**；令牌与其摘要都不出现；轮转只留一代。
- **反向验证**：给审计加个查询词字段 → 白名单判据红；只记拒绝不记放行 → 5 条红；
  审计失败改成抛异常 → 请求可用性判据红；去掉轮转 → 2 条红。

## 变更记录

- 用户能感到什么变化：服务行为不变；管理员多了一份"谁访问了哪个库、结果如何"的记录。

## 遗留事项

- 审计只落本地文件，没有集中收集与告警。内部规模够用，日后要做趋势分析或异常告警再说。
- 控制台还不能看这份记录（它现在读的是管理台自己的审计）。界面 RT 可以把它一起纳进来。
