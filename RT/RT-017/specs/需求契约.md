# RT-017 需求契约：Per-tenant Collector Worker

> 状态：planned。本文是编码与独立黑盒验收的权威契约；任何未有实际 receipt 的条目均不得写成已通过。

## 1. 业务目标

让宿主机以一个 tenant 为最小故障与权限单元，只读采集该 tenant 可见的工作协同报告；跨 tenant 稳定事实写入一份不可变 canonical，用户视角与事件正文严格 tenant 隔离，并在 authority 未验证时 fail closed。

## 2. 角色

- 平台管理员：配置 tenant、binding 与 credential reference；不能把明文 AppKey 传给 Worker。
- Collector Worker：单次只处理一个 tenant，读取源端，不修改源端。
- CWork Source Adapter：把源端响应转换为候选四路 envelope，不拥有存储权限决策。
- Authority Adapter：验证外部权威 receipt；不能由采集观察自行签发授权。
- Canonical Version Provider：按 `report_key` 点查并公开当前 canonical SHA；不得枚举
  RT-014 私有 catalog。
- Pilot Admission Provider：Wave-0 neutral shared ABI；分别以 `collector_run` 或
  `profile_workflow` 在构造期绑定，只有 `pilot` tenant 强制准入。
- RT-014/015 stores：分别是 canonical、grant 与 tenant view 的唯一 writer。
- 独立验收者：只用公开 API/CLI、磁盘产物和恶意 fixture 验收。

## 3. 功能范围

### 3.1 必须实现

- `collect_once(tenant_id, run_request)` 每次只绑定一个 tenant；tenant 必须存在且状态允许本次作业。
- 通过 Credential Broker 获取短租约并以最小环境调用只读 Source Adapter；退出、异常和取消都释放租约。
- 四路输出均先严格验证，再按 `canonical → access observation → authority promote（若有）→ tenant view（若 active）→ staged evidence` 的安全序列落盘。
- 相同 report/version 被 A/B 采集时 RT-014 只保留一个 canonical object；A/B 的 view、event evidence、state、retry、manifest 完全分离。
- state cursor、run manifest、retry 与 cleanup receipt 持久化、幂等、可恢复。
- 本轮 bounded list 缺项只记录 `not_observed_in_page`，不得触发 revoke/delete/purge。
- legacy façade 保留并默认启用；多租户路径必须显式调用，且不回退仓库 `.env`。
- 在 `cwk_access_ledger.py` 的已预声明 evolution stage 内新增版本化 snapshot-only 公共
  只读 ABI `list_profile_eligible(*, snapshot)`（语义见 `技术方案.md` §2.1），供 RT-019
  Profile sampler 在 `profile_pending` 下合法读取候选语料。不得放宽 `list_query_eligible`，
  不得暴露正文/路径/credential。
- 上述 evolution stage 是不可拆分 Stage-01：同时包含 authority injection、cleanup v2、
  Profile eligibility、CanonicalVersionProvider 注入和 PilotAdmission；不得先签窄
  eligibility receipt 后再修改同一脚本。

### 3.2 明确不做

- 常态 Scheduler、cron、跨 tenant 公平性。
- 路由、知识空间投影、问答或沙箱传输。
- 生产权限能力不存在时的降级 active、宽限读取或自签 receipt。
- 附件下载、预览 URL 持久化；任何源端写操作。

## 4. 输入契约

`CollectorRunRequest v1` 至少包含：

- `tenant_id`：合法 opaque tenant ID；
- `run_id`：不可预测 opaque ID；
- `mode`：`sample_collect | incremental_collect | retry`；
- `requested_at`、`deadline_at`；
- `cursor_ref`（可空、tenant-scoped opaque ref）；
- `limits`：报告页数、报告数、事件数、字节数和超时的正整数上限；
- `actor`、`reason`：可审计且禁止控制字符；
- 不得包含 AppKey、agent_id、绝对路径、tenant root、raw payload 或任意 shell 参数。

状态矩阵：

- `profile_pending`：只允许有界 `sample_collect`；
- `pilot/active`：允许本 RT 的按需 `sample_collect/incremental_collect/retry`；常态调度由 RT-018 决定；
- `draft/suspended/offboarded`：全部拒绝且不得解析 credential。

对 `pilot`，Worker 必须使用构造期绑定 `purpose=collector_run` 的 shared provider 在
取得任何业务输入前与发布/提交前各获取并验证一次 snapshot；任一次 deny/unavailable/
expiry/hash/tenant/purpose/revision 失败或两次 policy 漂移都丢弃整次 run。
`profile_pending/active` 不因 PilotAdmission 增加依赖。

## 5. 输出契约

### 5.1 四路 envelope

- Canonical 与 TenantView 使用 RT-011 v1 schema；共享/overlay 字段遵守 verified extension allowlist。
- AccessObservation 固定 `initial_status ∈ {discovered, granted}`；Collector 不能产出 `active`。
- TenantEventEvidence 使用 `cwk.tenant_event_evidence.v1`：
  - required：`schema`、`event_key`、`report_key`、`parent_canonical_sha256`、`event_type`、`author`、`occurred_at`、`body`、`body_sha256`、`extractor_version`、`stage_state`、`event_sha256`；
  - `stage_state` 固定为 `staged`；`event_type` 只允许 `reply/comment/approval/node/status_change`；
  - `event_key` 是 tenant-scoped opaque key；由独立 secret-backed deriver 对 tenant + report + 原始 event identity 做 HMAC/domain separation，原始 source event ID 不落盘；
  - `body_sha256 = sha256(UTF-8(NFC(body)))`；`event_sha256 = sha256(b"cwk-tenant-event-v1\0" + JCS_UTF8(NFC(record_without_event_sha256)))`；
  - 禁止字段：tenant_id、source event id、整段 payload、agent/binding/auth epoch、credential、path、URL、attachment、token、cookie、authorization。

### 5.2 event body 策略

- body 必须是 NFC 文本、无 NUL/控制字符，编码后长度不超过 64 KiB；不得静默截断。
- 命中 HTML、URL/短链/presign、token/credential 模式、未知嵌套字段、歧义 author/time 或超长内容时，写仅含 opaque hash/reason 的 review 记录；正文不得落 staged 文件、日志或错误。
- staged evidence 不能进入 TenantView、query、router、index、AI 或 prompt。未来读取必须同时满足 active grant、未过期 lease、当前 visible-event 引用和读前/读后二次 ACL。

### 5.3 manifest 与 receipt

Collector run manifest 只允许计数、opaque key/hash、cursor token 的不可逆引用、开始/结束时间、provider/version、状态和错误 reason code。不得含正文、标题、作者、event body、URL、AppKey、credential material、绝对路径或原始异常文本。

staged purge receipt 必须绑定 `outbox_id/grant_key/report_key/event_key(s)/purged_body_count/auth_epoch/consumer_version/completed_at`，不含正文；只有所有目标不存在或已被安全覆写/移除并 fsync 后才能 ack `staged_event` consumer。

### 5.4 Profile eligibility 的 current-version 事实

`list_profile_eligible(*, snapshot)` 必须构造注入
`CanonicalVersionProviderV1.resolve_current(*, report_key)`。其返回对象字段恰好为
`schema,report_key,canonical_sha256,catalog_revision,catalog_head_sha256`；每个 SHA 必须
由 provider 通过 RT-014 public
`SharedEvidenceStore.read_version(report_key, canonical_sha256)` 复核。不得从 grant、
tenant view、catalog path/head 私有方法或对象枚举推断 current SHA。

若 snapshot 的 tenant status=`pilot`，还必须使用构造期绑定
`purpose=profile_workflow` 的 PilotAdmission provider 验证 valid+admitted；
`profile_pending/active` 仍按既有 eligibility 规则处理。provider missing/deny/过期/
revision 回退时不返回任何记录，也不产生持久化副作用。

## 6. Authority 契约

- `CWorkAuthorityProviderV1` 公开 `observe_visible(cursor)`、`verify_grant(report_key)`、`consume_revocations(cursor)` 三个只读能力；调用凭据只进入 Header，禁止 URL query、argv、env dump 或日志。
- Provider 结果严格分类为 `ALLOW / EXPLICIT_DENY / NOT_FOUND / TRANSIENT_UNKNOWN / AUTH_FAILURE / SCHEMA_ERROR`。只有被 capability receipt 证明为权威语义的 `ALLOW` 可生成 TTL 不超过 15 分钟的短 lease receipt，且不可续期为常驻授权；过期且权威复核失败立即回到 `conservative_unknown`/拒答。明确 deny/revoke 触发撤权，其余状态全部 fail closed。partial、重复/多余 ID、游标回退或未知枚举属于 schema/unknown，不得猜测。
- `AuthorityReceiptProviderV1.issue_or_fetch(observation) -> AuthorityResult` 返回 `verified(receipt)`、`not_authoritative` 或 `conservative_unknown`；不能返回布尔真值替代证据。
- `CWorkAuthorityAdapter.verify(receipt, purpose)` 只接受已冻结 schema、受信 signer/trust store、未过期、防重放且 binding 完全匹配的 receipt。
- 仅“使用 AppKey 可读”或列表出现不能证明撤权通道与 lease 权威性；此时结果必须是 `conservative_unknown`。
- `promote_to_active/refresh_lease` 只能通过 RT-015 的生产 adapter 注入点；禁止调用私有 test 注册函数。
- authority 失败不回滚已正确发布的 canonical，但 grant 保持 non-active，tenant view 延迟，staged body不可消费，并在 manifest 中记录安全 reason code。

## 7. 幂等与恢复规则

- `collector_job_key` 使用 domain separator + length-prefix 对 tenant、run mode、cursor snapshot、provider version 计算，不使用无分隔符字符串拼接。
- 相同 report/version 重放不得重复 canonical；相同 event/body 重放不得重复 staged evidence。
- 同 event 正文变化生成新不可变 event evidence version；旧件不覆盖。
- publish 后崩溃、observe 后崩溃、staged write 后崩溃均可重跑并收敛到同一 durable 结果。
- revoke 先由 Ledger 逻辑拒绝；随后 staged cleanup 幂等执行，成功才 ack；崩溃重跑不得复活 body。

## 8. 异常策略

- Credential 不可用/禁用：本 tenant fail closed，其他 tenant 不受影响，不回退全局环境。
- CWork 429/超时/坏 JSON：写 tenant retry（有界次数/截止时间），不污染 cursor；原始响应不进日志。
- canonical/hash/schema 失败：不发布 catalog，不写 view/event；输出 opaque review/retry reason。
- authority 未知/拒绝：grant 不 active，view 延迟，staged 保留但不可消费。
- 存储满盘/只读：停止本 tenant 新写，禁止半 manifest/半 catalog；其他 tenant 可继续。
- list 缺项：不撤权；只有 RT-015 权威 revoke/lease 过期路径可触发拒绝与 cleanup。

## 9. 权限与安全要求

- AppKey 不进入 argv、Git、Prompt、sandbox、manifest、日志、错误、临时文件或测试快照。
- 所有 tenant 路径由 InstanceLayout + dirfd/O_NOFOLLOW 派生；拒绝 absolute、`..`、symlink、hardlink、TOCTOU。
- staging/run/state/retry/lock 权限为目录 0700、文件 0600；原子写、CAS/锁与 fsync。
- 输出/错误不得泄漏另一个 tenant、对象存在性或宿主机绝对路径。
- Worker 只允许源端 GET/只读调用；测试必须断言无 mutation method。

## 10. 验收标准

- AC-017-01：A/B 同报告同版本只有一个 canonical object，view 与 event body 各自隔离。
- AC-017-02：四路输出严格 schema/语义验证；未知字段不会进入 canonical。
- AC-017-03：无 authority receipt 时 grant 不 active，event body 仅 staged 且不可被任何下游 reader 消费。
- AC-017-04：合法 authority receipt 可 promote/写 view；过期、错 tenant/report/grant/purpose/signer/replay receipt 全部拒绝。
- AC-017-05：bounded list 缺项不会 revoke/delete/purge。
- AC-017-06：断点续跑、重复运行和并发同报告写入幂等；无半成品 catalog/manifest。
- AC-017-07：revoke 后立即 fail closed，staged body crash-safe 清理并正确 ack；其他 tenant 不受影响。
- AC-017-08：argv/log/manifest/temp/error/fixture secret scan 为 0；路径攻击全部拒绝。
- AC-017-09：单 tenant 的 429、超时、坏响应、满盘、锁冲突不污染另一 tenant。
- AC-017-10：legacy façade 行为保持，nightly/cron/生产 feature flag 未改变。
- AC-017-11：`list_profile_eligible(*, snapshot)` 只放行 `{profile_pending, pilot, active}`
  且 grant active / lease 未过期 / auth_epoch 匹配；`draft/suspended/offboarded`、跨 tenant
  snapshot、过期 lease、epoch 漂移、revoked grant 全部排除或统一 `AccessDenied`。
  同一 fixture 下 `list_query_eligible` 在 `profile_pending` 仍拒绝（证明 query eligibility
  未被放宽），返回记录字段集合精确等于契约列表且不含正文/路径/credential/agent ID。
- AC-017-11a：eligible record 的 `canonical_sha256` 只能来自注入的五字段
  CanonicalVersionSnapshot，并经 RT-014 public `read_version` 验证；grant/view/private
  catalog 伪造、head/object 漂移、枚举与路径注入全部拒绝。
- AC-017-11b：`pilot` eligibility 的 `profile_workflow` 与 Worker 的 `collector_run`
  purpose 不可互换；Worker 启动/发布前双重准入，deny/unavailable/expiry/revision 回退/
  snapshot 漂移都产生零部分输出。`profile_pending/active` 无额外准入调用。
- AC-017-11c：authority injection、cleanup v2、Profile eligibility、CanonicalVersionProvider
  与 PilotAdmission 同属一个 Stage-01 evolution receipt；缺任一项或试图二次演进
  `cwk_access_ledger.py` 都失败。

## 10a. RT-017 拥有的 PR-001 receipt（生产者义务）

RT-017 是两份 PR-001 级 receipt 的**唯一生产者**；二者都不是 RT-017 的完成条件，
而是 RT-017 独立验收 PASS 之后的产出物。

| receipt | schema | 路径 | 任务 | 生产阶段 | 消费者 |
| --- | --- | --- | --- | --- | --- |
| `cwork-authority-source` 能力激活 | `cwk.pr001.capability_activation_receipt.v1` | `PR/PR-001-multitenant-knowledge-spaces/capability-receipts/cwork-authority-source/receipt.json` | A-07 | RT-017 独立验收 PASS 之后 | 仅 RT-026 |
| RT-017 安全门 | `cwk.pr001.security_gate_receipt.v1` | `PR/PR-001-multitenant-knowledge-spaces/security-receipts/RT-017/receipt.json` | D-07 | `rt_independent_acceptance` | RT-026（go/no-go）、G6（final acceptance） |

- **真实生产条件**（激活 receipt，逐条见闭包图 `production_conditions`）：真实权威
  ACL 快照 / 撤权事件流 API（有版本、cursor、deny/not-found 语义、SLA 与审计签名）；
  真实凭据经 production `CWorkAuthorityProviderV1` 构造函数注入且只走 header；对两个
  不同的非生产 AppKey 做过真实 A/B 可见性与撤权测试；production signer 与 trust
  anchor 已确认，全链路无 `FakeSigningAuthority` / test sentinel / 假 signer。
- **缺失即不签发**：上述任一条件缺失、未知或仅部分验证，RT-017 的正确产出是
  **完全不生成激活 receipt**。`conservative_unknown` 或 blocked 结论绝不得写成
  `capability_activated`；receipt 缺席就是正确的 fail-closed 输出。
- **独立验证**：两份 receipt 的 `verifier` 都必须是 E-02 的独立验收 Agent，
  且严格不等于实现 Agent（`producer`）。实现 Agent 的自测结论不能自封。
- **无环**：VG-B 是 RT-026 的同级独立输入，既不是激活 receipt 的前置条件，也不得
  出现在其 `evidence_refs` 角色中。顺序恒为 RT-017 独立 PASS → receipt → RT-026。
- **有界有效期与续签**：激活 receipt 的 `expires_at - created_at` 必须满足
  `0 < Δ ≤ 7776000s`（90 天，闭区间上界）。过期后禁止原地覆盖，须按
  `activation_history_rule` 归档旧 receipt 并基于**新的真实探测**续签。

## 11. 必须覆盖的测试场景

- 正常：双 tenant 同/不同 report、正文新版本、overlay-only diff、event 新版本、sample/incremental/retry。
- 异常：credential missing、429、timeout、bad JSON、partial page、schema/hash mismatch、disk full、lock contention、crash at each publish boundary。
- 权限：authority verified/unknown/rejected/expired/replayed/wrong binding；lease refresh；in-flight revoke。
- 恶意：tenant/path/report/event 注入、symlink/hardlink/TOCTOU、HTML/URL/token/超长 event、prompt injection、log injection、malformed Unicode。
- 回归：RT-011～016 定向测试、全量 unittest、Wiki lint/smoke；不得触发真实网络或生产密钥。
