# RT-017 技术方案：Per-tenant Collector Worker

> 状态：planned。RT-017 core 与 consumer wiring 尚未实现；Wave-0 已冻结并交付
> `CanonicalVersionProviderV1` 的 runtime/schema/test 三工件，其余接口名仍是实现目标。

## 1. 模块与所有权

- `cwk_tenant_collector.py`：单 tenant orchestration、状态机、四路发布与 recovery。
- `cwk_cwork_source.py`：只读 CWork API adapter、分页与响应到候选 envelope 的纯转换。
- `cwk_tenant_event_evidence.py`：event key、schema validator、tenant-scoped store、review 与 purge consumer。
- `cwk_cwork_authority.py`：source-specific authority capability probe、receipt provider、生产 verifier。
- `cwk_canonical_version_provider.py`：只按 `report_key` 点查 RT-014 current catalog，
  返回五字段 path-free snapshot，并经 public `SharedEvidenceStore.read_version` 复核对象。
- `cwk_collect_live.py`：RT-017 独占改造，保留 legacy façade，增加显式多租户 adapter 入口。
- `cwk_collection_state.py`：仅增加 tenant-scoped adapter；不再写仓库级多租户状态。

## 2. 不可拆分的 RT-017 Stage-01（RT-015 AccessLedger 兼容层）

为避免私有 test authority 被生产复用，采用构造注入：

```python
class AccessLedger:
    def __init__(self, layout, tenant_registry, shared_store,
                 *, authority_adapter: AuthorityAdapter | None = None): ...
```

- `None` 永远选择 RT-015 fail-closed default。
- `promote_to_active/refresh_lease` 使用实例 adapter；test-only 全局注册只保留旧测试兼容，不进入生产 factory。
- adapter 类型、receipt schema 和 purpose 仍由 RT-015 校验，RT-017 不能绕过 grant 状态机。
- 新增 `cleanup_outbox.v2`，只扩展 `staged_event` consumer；v1 文件不可重写，reader 兼容两版，新 revoke 写 v2。
- authority injection、cleanup v2、§2.1 eligibility、§2.2 CanonicalVersionProvider 与
  §2.3 PilotAdmission 必须在同一个 Stage-01 compatibility commit/migration note/
  evolution receipt 中完成，并跑 RT-015 全量定向测试。不得先落窄 slice 再二次改
  `cwk_access_ledger.py`。

### 2.1 `list_profile_eligible`（Wave-1 API blocker 收口）

RT-015 的公共 `list_query_eligible(*, snapshot)` 只放行 `pilot|active`，而 RT-019 的
Profile sampler 必须在 `profile_pending` 下工作。RT-019 **不允许**放宽 query eligibility，
也**不允许**直接扫描 ledger 私有 grant 目录。收口方案：由拥有 `cwk_access_ledger.py`
evolution stage 的 RT-017 新增一个版本化、snapshot-only 的公共只读方法。

```python
API_VERSION = "cwk.profile_eligibility.v1"

class AccessLedger:
    def list_profile_eligible(
        self, *, snapshot: AgentContextSnapshot
    ) -> tuple[ProfileEligibleRecord, ...]: ...
```

冻结语义：

- **snapshot-only**：唯一参数是可信 `AgentContextSnapshot`（与 `list_query_eligible` 同一
  类型与来源）。拒绝裸 `tenant_id=` kwarg、位置参数、path、credential、agent ID。
- **允许的 tenant 状态严格等于 `{profile_pending, pilot, active}`**。`draft/suspended/
  offboarded` 返回统一 `AccessDenied`，与 query 路径的错误形态、字段集合一致，不泄露
  tenant 存在性。`pilot` 必须经 §2.3 shared provider 命中准入。
- 其余授权条件与 query 路径**逐条相同**：grant 状态为 `active`、lease 未过期、
  `auth_epoch` 与 snapshot 匹配、grant 属于 `snapshot.tenant_id`、无 tombstone/revoke
  intent。任一不满足即排除该条，不降级、不宽限。
- **不放宽 query eligibility**：`list_query_eligible` 的实现、允许状态集与既有测试字节
  不变；两个方法共用同一 grant 校验 helper，只在"允许的 tenant 状态集"这一处分叉。
  必须有断言测试证明 `profile_pending` 下 `list_query_eligible` 仍拒绝。
- 返回 `ProfileEligibleRecord`（`cwk.profile_eligible_record.v1`，frozen dataclass）只含
  opaque 授权事实：`schema`、`report_key`、`canonical_sha256`、`grant_key`、`granted_at`、
  `lease_expires_at`、`auth_epoch`、`tenant_status`。
- **禁止字段**：正文/body、标题、绝对路径或任何 tenant root 派生路径、credential/token、
  agent ID、source event ID、URL、附件引用、其他 tenant 的任何数据。
- 结果按 `(report_key, canonical_sha256)` 稳定排序；不存在的 tenant 目录返回 `()`。
- 本方法只读：不写 grant、不改状态、不触发 promote/revoke/cleanup。
- 调用方需要的正文/元数据（分层所需的时间、source、author、report type）一律通过
  RT-014 public reader 按 `report_key + canonical_sha256` 回读，不由本方法提供。

RT-019 是本 ABI 的**唯一已知 consumer**，且只能通过该公开方法访问；RT-018 常态
Scheduler 仍不把 `profile_pending` 纳入调度（该状态的取样由 RT-017 有界按需入口触发）。

### 2.2 `CanonicalVersionProviderV1`

```python
class CanonicalVersionProviderV1(Protocol):
    API_VERSION = "cwk.canonical_version_provider.v1"
    def resolve_current(
        self, *, report_key: str
    ) -> CanonicalVersionSnapshotV1: ...
```

五字段 snapshot 固定为 `schema,report_key,canonical_sha256,catalog_revision,
catalog_head_sha256`。provider 按冻结的 RT-014 catalog-key 公式执行单 key 点查，验证
head/jsonl/current object，并调用 public `SharedEvidenceStore.read_version`；不接受
catalog key/path/object id，不枚举，不调用 `_read_head/_read_entries`。Null provider
返回稳定 `unavailable`。冻结 runtime/schema/test SHA 分别为
`4e6ec4ee88b5b23ebda160ccfb5dd60ee0c39092ca26e2247cf3caae67e1f518`、
`dca2aceaad46fba973eb51d3ee7c4faa2350dc5191ac1af711cdb66f6bc6a3b3`、
`aab334e40e36cdb2f48ec2178393921dc91dae585675d28a952065250434dc06`。

### 2.3 shared PilotAdmission

RT-017 零漂移消费 Wave-0 neutral ABI。Worker 构造注入 `purpose=collector_run`，
`list_profile_eligible` 构造注入 `purpose=profile_workflow`；方法签名始终只有
`snapshot(*, agent_snapshot)`。仅 `pilot` 调用并要求 valid+admitted；Worker 在启动与
发布前各重验，eligibility 在返回前验证。Null/deny/expiry/hash/revision/purpose/
tenant 错误均 fail closed；`profile_pending/active` 不调用 provider。

## 3. 公开 ABI

```python
class CWorkSourceV1(Protocol):
    API_VERSION = "cwk.cwork_source.v1"
    def discover(self, *, lease, cursor, limits) -> SourcePage: ...
    def fetch_report(self, *, lease, report_ref) -> SourceReport: ...

class AuthorityReceiptProviderV1(Protocol):
    API_VERSION = "cwk.authority_receipt_provider.v1"
    def capability(self) -> CapabilityResult: ...
    def issue_or_fetch(self, *, observation, lease) -> AuthorityResult: ...

class CWorkAuthorityProviderV1(Protocol):
    API_VERSION = "cwk.cwork_authority_provider.v1"
    def observe_visible(self, *, cursor) -> AuthorityPage: ...
    def verify_grant(self, *, report_key) -> AuthorityDecision: ...
    def consume_revocations(self, *, cursor) -> RevocationPage: ...

class TenantCollectorWorker:
    def collect_once(self, request: CollectorRunRequest) -> CollectorRunReceipt: ...
    def recover(self, *, tenant_id, actor, reason) -> RecoveryReceipt: ...

class TenantEventEvidenceStore:
    def stage(self, *, tenant_id, envelope) -> StageReceipt: ...
    def purge_cleanup_task(self, *, tenant_id, task) -> PurgeReceipt: ...
```

Source Adapter 不接收 tenant root 或明文 credential；Worker 从 Credential Broker lease 构造最小调用上下文。所有 dataclass frozen，payload 在写前执行 schema + deep-forbidden + 语义 validator。

`CWorkAuthorityProviderV1` 的公开 ABI 冻结为三个方法且只暴露上表参数：`observe_visible(cursor)`、`verify_grant(report_key)`、`consume_revocations(cursor)`。lease、分页 limit、超时与其他 provider 配置一律在构造期注入具体实现（不出现在方法签名里），分页推进与 backpressure 通过返回值的 `next_cursor/has_more/page_limit` 语义表达。cursor 回退、跳跃或 schema 不明均 fail closed。调用方不得依赖任何未在此冻结的关键字参数。

## 4. 数据布局

```text
tenants/<tenant_id>/
├── state/collector-v1.json
├── runs/collector/<run_id>/manifest.json
├── retries/collector/<retry_id>.json
├── locks/collector.writer.lock
└── staging/events/
    ├── evidence/<event_key>/<event_sha256>.json
    ├── review/<review_id>.json
    ├── purge-receipts/<outbox_id>.json
    └── locks/<event_key>.lock
```

- 路径 leaf 全部来自 opaque grammar；禁止 title/report id/event id 直接做目录名。
- staged evidence 文件含 body，因此只在 tenant 私有宿主机目录，0600；manifest/review 不含 body。
- state 与 cursor 只保存源端 opaque continuation 的加密/secret reference 或不可逆 hash；若 continuation 本身包含 token，不得落普通 state。

## 5. 四路拆分流水线

```text
credential lease
  → read-only discover/fetch
  → strict decode + field allowlist
  → canonical candidate / tenant overlay / access observation / event candidate
  → schema + semantic validation
  → RT-014 publish canonical
  → RT-015 observe(granted/discovered)
  → optional authoritative promote + tenant view upsert
  → stage allowed event bodies (always non-queryable)
  → atomically persist cursor + manifest
```

仅在 canonical publish receipt 已验证后才能写引用它的 view/event。Cursor 最后提交；中途崩溃重放依靠下游幂等收敛。

## 6. Event evidence 设计

- 原始 event identity 只在内存中输入 `EventKeyDeriver`；`event_key = "ev_" + base32(HMAC-SHA256(instance_event_key_secret, b"cwk-event-key-v1\0" + LP(tenant_id)+LP(report_key)+LP(source_event_id)))[:26]`。其中 `base32` 固定为 RFC 4648 小写、去 padding、字符集 `[a-z2-7]`。
- `LP(x) = uint32_be(len(UTF8(NFC(x)))) || UTF8(NFC(x))`，消除拼接边界歧义。
- event body 不允许 URL/HTML/token；校验失败只记录 `review_id/reason/event_key/body_sha256`，不回显 body。
- 对同 event_key 的不同 body_sha 生成不同 immutable version；当前 pointer 原子更新，但旧版本只受保留/撤权策略清理，不能覆盖。
- 任何读取 API 默认不存在；本 RT 仅提供 stage、integrity-check、purge。下游读取能力若未来新增，必须另立版本并执行 active grant + visible-event + 双 ACL。

## 7. Authority 设计

`CapabilityResult.status ∈ {verified, conservative_unknown, unavailable}`。`verified` 必须附可机读证据位置、接口版本、trust anchor ID、支持的 receipt type 与撤权/lease 语义；不含 secret。

`CWorkAuthorityAdapter` 只验证来自被探针确认的权威接口的签名/证明；Collector 本身不能签发 receipt。若源端没有签名 receipt，可由宿主机受信 adapter 在实时调用权威 permission API 后生成本地 attestation，但必须：

- trust key 来自 secret backend，不写代码/配置；
- attestation 绑定本次响应 hash、tenant credential ref hash、grant identity、purpose、issued/expires/nonce；
- verifier 与 signer 分离，重放缓存持久化；
- capability 未经真实环境验证时仍标记 unknown，不得用于 G7。

Provider 决策固定为 `ALLOW / EXPLICIT_DENY / NOT_FOUND / TRANSIENT_UNKNOWN / AUTH_FAILURE / SCHEMA_ERROR`。只有 capability receipt 已证明语义的 `ALLOW` 进入 attestation；deny/revoke 立即调用 RT-015 撤权，其他状态 fail closed。HTTP client 只允许 Header credential，禁止复用把 AppKey 放入 URL query 的 legacy client。

## 8. 状态机与 retry

Run：`created → credential_acquired → fetching → publishing → committing → succeeded`；任意阶段可到 `retryable_failed | permanent_failed | cancelled`。重启发现 `credential_acquired/fetching/publishing/committing` 的 stale run 时先 integrity recovery，再重放；不从未提交 cursor 向前跳。

Retry 记录只保存 reason code、attempt、not_before、deadline、provider/version、opaque run/job key。次数与 backoff 有界；RT-018 可消费，但 RT-017 也能按需执行单 tenant retry。

## 9. 安全与故障隔离

- 每 tenant writer lock；共享 canonical 并发由 RT-014 CAS 处理。
- credential lease 以 context manager 生命周期注入最小 env；异常消息统一 redaction。
- 任何 source mutation method/HTTP verb 在 adapter allowlist 外即 contract error。
- nofollow dirfd、原子写、fsync、0600/0700；不使用 CWD、PYTHONPATH、用户路径。
- 共享存储失败时不提交 cursor；tenant state 坏损不会写另一个 tenant。

## 10. 测试策略

- 单元：schema、normalizer、event key/hash、authority result、state machine、redaction、bounded list 语义。
- 组件：fake Source、fake Credential Broker、RT-014/015 public API、crash injection 每个边界。
- 集成：A/B 同报告、overlay/event 差异、并发、revoke cleanup、重启续跑、unknown authority。
- 恶意：路径/Unicode/HTML/URL/token/prompt/log injection、错 receipt、replay、TOCTOU、disk full。
- 回归：RT-011～016、Wiki lint/smoke、legacy façade；网络与生产配置必须禁用。

## 10a. PR-001 receipt 生成机制（A-07 / D-07）

两份 receipt 都由**独立验收 Agent**在 RT-017 独立验收 PASS 之后写入，均为
evidence-only 变更，不触碰 runtime。

- **写入顺序**：先冻结被测候选 commit → 独立验收执行 → 得到 PASS → 在随后的
  evidence-only commit 中写 receipt。receipt 的 `tested_subject_commit` 必须是该
  evidence-only commit 的**祖先**，并与 receipt 自身 `evidence_refs`/`artifacts`
  指向的产物一致。这既排除自引用哈希环，也排除"用不相干 commit 的证据充数"。
  该字段**不要求**等于 RT-026 的最终 HEAD——下游合并会合法推进 HEAD。
- **哈希**：`receipt_sha256` = SHA-256(domain separator
  `cwk-capability-activation-receipt-v1\0` ‖ 去掉 `receipt_sha256` 字段后的 JCS
  bytes)。安全门 receipt 用 `cwk-security-gate-receipt-v1\0`，两者不可互换。
- **evidence_refs / artifacts**：每条必须是仓库相对普通文件，禁止绝对路径、`..`、
  任一路径分量为 symlink、hardlink、目录与特殊文件；逐条 sha256 与磁盘内容匹配。
- **报告引用是单向的，且两类报告的时序相反**：
  - `reports/独立验收报告.md` 被 receipt 以 `independent_acceptance_report` 角色
    **按 sha256 绑定**，因此它必须在 receipt 签发**之前**冻结，之后**永不再编辑**；
    它**不引用** `receipt_sha256`，也不引用 receipt 路径。
  - 只有**不被绑定**的 `reports/交付验证报告.md`（交付/状态件）可以在 receipt 写入
    **之后**追加其路径与 `receipt_sha256`。
  receipt 不反向哈希报告。若允许被绑定的报告在 receipt 之后再编辑，报告的 sha256
  就会与 receipt 内记录的值不符，等于自毁该 receipt——这正是要避免的互哈希环。
- **续签（仅激活 receipt）**：到期后不得原地覆盖。旧 receipt 原字节移入
  `capability-receipts/cwork-authority-source/archive/<旧 receipt_sha256>.json`
  （文件名即其自身哈希），新 receipt 的 `sequence` 递增 1、
  `previous_receipt_sha256` 指向该归档项，且必须基于**新的真实探测**证据。
- **不生成的情形**：真实条件不满足时不写文件。RT-026 见不到 receipt 即判 NOT_RUN /
  NO_GO，这是设计意图，不是缺陷。

## 11. 回滚

删除/停用多租户 Worker 调用入口即可回到 legacy façade；不删除已发布 canonical、grant、墓碑或审计。RT-015 兼容构造参数默认 fail closed，旧调用者无需变更。cleanup v2 reader 必须继续读 v1，回滚不得把 v2 任务视为已完成。
