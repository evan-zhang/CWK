# RT-015 技术方案：Access Ledger 与 Tenant View Store

> 目的：把 PRD FR-08、DESIGN §5 C-08 / §10 描述的“逻辑授权 SoR + 立即
> 生效的撤权 + tenant-only overlay”落成宿主机内部可独立测试的库函数，
> 不新增运行时入口、不触碰任何已冻结的 RT-011~014 模块。

## 1. 组件拓扑

```
┌────────────────────────────────────────────────────────────┐
│                     RT-015 module layer                    │
│                                                            │
│   ┌───────────────────┐          ┌──────────────────────┐  │
│   │ cwk_access_ledger │◄────────►│ cwk_tenant_view      │  │
│   │  (grant SoR +     │  reuses  │  (overlay-only)      │  │
│   │   revocation)     │          │                      │  │
│   └────────▲──────────┘          └──────────▲───────────┘  │
│            │                                │              │
│  reads     │ HMAC verify (fake / fail       │ writes /      │
│  RT-011    │ closed)                        │ reads         │

└────────────┼────────────────────────────────┼──────────────┘
             │                                │
     ┌───────┴────────┐                ┌──────┴──────────┐
     │ RT-013         │                │ RT-014          │
     │ AgentContext   │                │ SharedEvidence  │
     │ Snapshot       │                │ Store           │
     └───────▲────────┘                └──────▲──────────┘
             │                                │
             │                                │
     ┌───────┴────────┐               ┌───────┴──────────┐
     │ RT-012         │               │ RT-012           │
     │ TenantRegistry │               │ InstanceLayout   │
     │ .bump_auth_… │               │ .registry_fd /   │
     └────────────────┘               │ .child_fd        │
                                      └──────────────────┘
```

RT-015 **不引入新写路径**到 RT-011~014 的存储；它只：

- 在 `registry/access-ledger/<tenant_id>/…` 下建立自己独占的子结构；
- 在 `tenants/<tenant_id>/views/<view_key>.json` 中写 overlay 记录
  （目录已由 RT-012 `TENANT_CHILDREN` 预建，RT-015 只写 leaf 文件）；
- 通过 `SharedEvidenceStore.read_version` 校验 canonical 引用；
- 通过 `TenantRegistry.bump_auth_epoch` 请求 CAS 递增 `auth_epoch`；
- 通过 `AgentContextSnapshot` 消费身份，绝不接受裸 `tenant_id/agent_id`。

## 2. 磁盘布局

```
CWK_INSTANCE_ROOT/
├── registry/
│   └── access-ledger/
│       └── <tenant_id>/                (0o700, RT-015 独占)
│           ├── grants/<grant_key>.json         (0o600, CAS)
│           ├── events/<grant_key>.jsonl        (0o600, CAS append)
│           ├── revoke-intents/<txn_id>.journal (0o600, exclusive)
│           ├── revoke-receipts/<txn_id>.receipt(0o600, exclusive)
│           ├── tombstones/<grant_key>.json     (0o600, immutable)
│           ├── cleanup-outbox/<outbox_id>.json (0o600, CAS)
│           └── locks/                          (0o700, flock anchors)
└── tenants/
    └── <tenant_id>/
        └── views/<view_key>.json               (0o600, CAS)
```

- `grant_key = view_key = "g_" + base32_lower(
   sha256(b"cwk-access-ledger-grant-key-v1\0" + tenant_id \0 + report_key)[:16])`。
- 无 `source_namespace` / `report_id` 在路径中；对外只有 opaque
  `g_<26 base32>`；无 hash-existence 探测。
- 每个 tenant 独立子树；`_open_child_dir_nofollow` 全程 `O_NOFOLLOW`。
- 所有子目录在首次写入时按需创建 (`_tenant_fd(create=True)`)；
  frozen 子结构由 `_TENANT_SUBDIRS` 常量列出。
- `locks/grant.<grant_key>.lock` 是 per-grant 单写锁；
  `locks/outbox.<outbox_id>.lock` 是 per-outbox 单写锁。

## 3. 数据契约

见 `PR/PR-001-multitenant-knowledge-spaces/contracts/rt015/schemas/`
与 `../需求契约.md § 二`。所有 schema 通过 RT-011
`_validate_schema` + `_iter_deep_forbidden` 校验，不重实现 JSON Schema
引擎。

- Grant 记录：`{schema, grant_key, tenant_id, source_namespace,
  report_id, grant: RT-011 access_grant.v1, record_revision,
  created_at, updated_at}`；每次修改 bump `record_revision`。
- Event log：`.jsonl`，每行 `cwk.rt015.state_transition_event.v1`。
  `actor / reason` 严格 `\A[\x20-\x7e]+\Z`；`from_status="_initial_"`
  用于首个 event，`to_status` 拒绝。
- Revoke intent：`{txn_id, grant_key, prior_status,
  prior_record_revision, tenant_auth_epoch_before, actor, reason,
  authority_receipt_id, intended_at}`。
- Revoke receipt：`{txn_id, grant_key, tenant_auth_epoch_before,
  tenant_auth_epoch_after, record_revision_after, tombstone_sha256,
  cleanup_outbox_sha256, revoked_at, actor, reason}`。
- Tombstone：`{grant_key, tenant_id, source_namespace, report_id,
  revoked_at, tenant_auth_epoch_at_revoke, revocation_receipt_id}`。
- Cleanup outbox：`{outbox_id, grant_key, tenant_id, source_namespace,
  report_id, tenant_auth_epoch_after, revocation_receipt_id, consumers,
  created_at}`；`outbox_id` 由 `sha256("cwk-access-ledger-outbox-v1\0" +
  txn_id)[:16]` 决定 → 幂等。
- Authority receipt：`{receipt_id, signer_id, receipt_type, tenant_id,
  source_namespace, report_id, grant_key, roles, visibility_scope,
  permission_source, issued_at, lease_expires_at, signature}`。签名
  通过 HMAC-SHA256(secret, `canonical_json_bytes(receipt \ signature)`)
  验证；`signer_id` 只在 module-private `_TEST_AUTHORITY_SIGNERS` 中
  存在（测试注册），常量时间比较。

## 4. 状态机与不变量

Access grant 状态严格遵循 RT-011 冻结 v1：

```
discovered ─► granted ─► active ─► revalidation_due ─► active | revoked
                                        │
                                        └► revoked ─► purge_pending ─► purged
```

不变量：
- 只有 `active` + 未过期 lease + snapshot.tenant_auth_epoch ==
  live.tenant.auth_epoch + snapshot.tenant_status ∈ {pilot, active}
  == live.tenant.status 才允许 read；其余任何情况一律
  `AccessDenied`。
- 观察永远不能升到 `active`。
- 撤权先 fail closed（intent journal 存在 → 强制 deny），再依次
  mark → epoch → tombstone → outbox → receipt → clear journal。
- Tombstone 一旦存在，`observe / promote / refresh_lease /
  mark_revalidation_due / read_view / upsert_overlay` 全部拒绝。
- Revoke 是不可复活的：`purge_pending → purged` 是唯一后续；
  RT-015 不提供 `unrevoke` / `reactivate`；`recover()` 只向前推进。
- `record_revision` 严格递增；CAS 用 SHA-256 复核 on-disk。
- 每 grant 独立 `flock`，避免多写者。
- `canonical_json_bytes(payload) == raw` 保证 JCS 反向复核，防篡改。

## 5. 撤权流水线（crash-safe）

1. `_write_intent`：`revoke-intents/<txn>.journal`（`write_atomic
   exclusive`）。
   - **不变量**：从写入 intent 起，`_intent_exists_for` 立即返回 True，
     `check_query_eligibility` 一律 `AccessDenied(revocation_in_progress)`。
2. `_complete_revocation` (idempotent)：
   1. 若 grant 尚未 `revoked` → CAS 更新为 `revoked`，写 event。
   2. 若 tenant.auth_epoch == intent.before → `TenantRegistry.bump_auth_epoch`
      （由 RT-012 CAS，含 `_tenant_record_lock`）。
   3. 写 tombstone（幂等：若存在则 SHA 一致才通过；否则 `corrupt`）。
   4. 写 cleanup outbox（`outbox_id = stable(txn_id)` → 重跑同名）。
   5. 写 receipt。
   6. Unlink journal + fsync 父目录。
3. `recover(actor, reason)`：
   - 扫描 `registry/access-ledger/`（跳过非法 tenant_id、非 dir、symlink）。
   - 对每个 tenant：
     - `recover_orphans` 每个子目录（`.cwk-tmp-*` 清理）；
     - 扫描 `revoke-intents/*.journal`：若同 txn receipt 存在 → 只
       unlink journal；否则加锁 → `_complete_revocation` 再 unlink。
   - 幂等；失败记录 `inconsistencies`（带 opaque 前缀），不阻塞其他 tenant。

## 6. Tenant View 双 ACL

- `upsert_overlay`:
  1. RT-011 `validate_tenant_view`（frozen v1 schema，防 body 泄漏）。
  2. `view_envelope.tenant_id == snapshot.tenant_id`（防跨租户）。
  3. `check_query_eligibility` 前置（`AccessDenied` → `ViewDenied`）。
  4. `SharedEvidenceStore.read_version(report_key, canonical_sha256)`
     校验 canonical 存在且完整；`not_found` → `CanonicalMissing`。
  5. `check_query_eligibility` 二次 recheck（防 in-flight revoke）。
  6. CAS 写 `tenants/<tenant>/views/<view_key>.json`（envelope schema +
     RT-011 view schema 双重校验）。
- `read_view`:
  1. 前置 `check_query_eligibility`。
  2. `read_file` view leaf + JCS/schema 校验（防 tamper）。
  3. `SharedEvidenceStore.read_version` 再次校验 canonical。
  4. 后置 `check_query_eligibility`（严格双 ACL，覆盖 in-flight
     revoke 的窗口）。
- `purge_for_revoked_grant`:
  1. 校验 tombstone 存在 或 grant.status ∈ {revoked, purge_pending,
     purged}；否则 `purge_refused`。
  2. Unlink view leaf 幂等。

## 7. Authority adapter

- `AuthorityAdapter` 基类：`verify(receipt, *, purpose)` 应 raise
  `AuthorityRejected` on failure。
- 默认 `_FailClosedAuthority`：**永远** raise。
- 测试可 register `FakeSigningAuthority`：HMAC-SHA256(secret,
  `canonical_json_bytes(receipt \ signature)`) 与 `receipt.signature`
  常量时间比较；额外检查：purpose ↔ receipt_type、`lease_expires_at`
  > now。
- 注册/注销受 module-private `_TEST_AUTHORITY_TOKEN` 保护；生产代码
  无法引用 sentinel。

## 8. Log injection 防护

- 所有 mutation API 首先 `_validate_actor_reason` → 严格可打印 ASCII
  + 长度限制 → 违反 `LogInjectionDetected`。
- Schema 层再 `\A[\x20-\x7e]+\Z` 校验（避免绕过 API 直接构造 event）。
- `evidence_refs` 用受限字符集（`[a-z0-9._\-:/+=]`）+ maxLength=256；
  非法项静默丢弃（不影响事件写入，但绝不写入原样内容）。

## 9. 错误 opacity

- `AccessLedgerError.__str__ = "[<code>] <msg> (grant_key=<opaque>)"`；
  从不含绝对路径、正文、URL、`agent_id`。
- `TenantViewError` 同上。
- `AccessDenied.reason` 是 module-private 诊断字段（内部调试用）；
  `__str__` 只写 "access denied"。测试通过 `.reason` 断言路径覆盖，
  但生产日志只序列化 `code`/`grant_key`。

## 10. 与后续 RT 的接口

- RT-016（legacy 迁移）：调用 `observe` 输入 legacy raw 推断的
  `AccessObservation`；不能提升到 `active`；不能写 tenant view 除非
  同时拿到 fake authority receipt（本地测试）。**timeline payload 层
  不属于 RT-015 契约范围。**
- RT-017（per-tenant collector）：调用 `observe`；
  `evidence_refs` 里附 opaque source URI（受字符集限制）。
- RT-019/020/021/022（profile / router / projector / broker）：调用
  `check_query_eligibility / list_query_eligible / read_view /
  iter_cleanup_outbox / ack_cleanup_task`；所有查询必须持有
  `AgentContextSnapshot`。
- RT-024（audit / metrics）：从 event log + tombstone + receipt
  重放；不必访问私有属性。

## 12. 回滚

- 删除 RT-015 新增文件 → 回退整套 RT-015 能力；未修改任何
  RT-011~014 冻结物。
- 已写入的 tombstone/cleanup outbox 保留（这是设计目标）；后续如
  需彻底清空 tenant，需通过 RT-025 恢复流程。
