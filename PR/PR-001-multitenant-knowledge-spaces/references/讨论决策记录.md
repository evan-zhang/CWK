## 1. 背景

CWK 已在单用户场景完成工作协同汇报采集、raw 原文归档、评论与审批时间线、Wiki 派生、实体约束检索、原文证据回读和 nightly 增量运行。下一阶段目标是让同一 Gateway 中不同用户的 Agent，各自使用本人的工作协同身份，查询本人有权访问的内容，并支持用户专属的知识组织方式。

讨论从“每个 Agent 是否重复安装”逐步收敛到以下产品形态：

```text
一台 Gateway
├── 一套共享 CWK 引擎
├── 宿主机上的多租户采集与安全服务
├── 一份去重后的公司级原始证据对象层
├── N 份租户访问关系、状态和知识方案
└── N 个只读查询沙箱/Agent
```

## 2. 用户原始诉求摘要

### U-01：同一 Gateway 内多 Agent、多用户

用户希望一台 Gateway 中存在多个相互独立的 Agent，每个 Agent 属于不同真实用户、拥有独立 workspace，并使用自己的工作协同 AppKey 采集、查询自己的内容。

### U-02：本地 Agent 与沙箱 Agent 采用统一模型

用户倾向于不再分别维护“本地 Agent 方案”和“沙箱 Agent 方案”，而是统一按沙箱化、多租户边界设计。

### U-03：最关键能力是自然语言提问

用户明确表示，是否能让用户对自己的工作协同内容稳定提问和查询，是决定是否推进生产化改造的核心条件。

### U-04：实体抽取不能无限复杂

用户担心实体定义过细、过复杂后不可控，希望抽取方案在首次使用时由 AI 基于用户的一部分历史汇报形成草案，再由用户确认。

### U-05：用户与 AI 共创知识方案

用户提出以下首次启用流程：

1. AI 先读取约 100–200 篇汇报；
2. AI 生成抽取与知识库组织方案；
3. 用户通过对话确认和修订；
4. 全量知识库按确认后的方案执行。

### U-06：同一用户需要多个专项知识库

用户希望将 TBS、SFE 等专项信息组织为相互独立、内部更集中、可单独查询的知识空间，并允许分类器将同一篇汇报路由到一个或多个空间。

### U-07：低价值内容不应持续消耗处理资源

员工报销、常规付款等内容通常不值得精编、索引和持续跟踪。用户希望系统识别“有价值”和“低价值”内容，低价值内容可以退出知识处理链路。

### U-08：共享汇报本体只保存一份

用户进一步指出：同一篇工作协同汇报被多个用户看到时，不应为每个用户复制一份 raw。应把工作协同汇报本体抽离为共享对象，只保存一次，再保存各用户的访问和关注关系。

## 3. 已确认的产品与架构决策

### D-01：一次安装，多租户使用

- CWK 引擎、依赖和查询 Skill 在 Gateway 机器安装一次。
- 每个 Agent 对应一个独立 tenant，不复制整套代码。
- 版本升级和回滚由宿主机统一完成。

### D-02：统一采用沙箱化运行模型

- 普通用户 Agent 在沙箱中运行。
- 采集、密钥使用、调度和共享证据读写在宿主机执行。
- 沙箱不持有 AppKey，不直接读共享对象目录，只通过受控查询入口读取本租户数据。
- 非沙箱 Agent 也必须走相同租户绑定和权限校验；workspace 不是安全边界。

### D-03：每个租户使用本人的工作协同身份

每租户独立拥有：工作协同身份与密钥引用、采集状态、锁、日志、重试队列、调度、访问关系、知识方案和专题空间。

### D-04：共享 raw 本体，租户数据独立

- 同一汇报的同一版本只保存一个不可变正文对象。
- 推荐以 `source_namespace + report_id + content_sha256` 标识版本。
- 1000 个用户看到同一版本时，正文只存一份，另存 1000 条轻量访问关系。
- 不同版本必须分别保存，不能覆盖历史。
- 物理去重不等于权限共享。

### D-05：共享内容与用户视角分层

共享候选字段：标题、正文、汇报人、创建时间。评论、审批节点和附件元数据在双身份验证及版本化扩展清单批准前全部属于 tenant overlay；临时下载/预览 URL 永远不允许进入 canonical。

租户字段：收件/发件来源、未读/待办状态、用户角色、允许操作、可见范围、个人关注、路由结果，以及可能因身份不同而变化的评论、审批和附件权限覆盖。

### D-06：访问关系是强制门禁

```text
可信 Agent 身份
→ 固定 tenant_id
→ ACL 过滤候选 report_id
→ 查询租户知识空间
→ 再按 ACL 回读共享 raw
```

- Agent 或用户不能传入、覆盖或猜测其他 tenant_id。
- 仅知道 report_id 或物理路径不能直接读取正文。
- 权限撤销后，必须把访问关系标记为 `revoked`、提升 `auth_epoch` 并保留不可查询的 ledger/撤权墓碑；同时清除该租户的索引、缓存、投影和临时副本。不得删除授权历史，也不得通过回滚恢复已撤权 grant。

### D-07：首次启用由 AI 与用户共创知识方案

- 按时间、来源、发送人、类型、评论/审批活跃度分层抽取 100–200 篇。
- AI 生成专题空间、实体颗粒度、别名、合并/拆分、关注项和冷归档规则草案。
- 用户只需确认会改变召回范围的高影响规则。
- 再用未参与建模的 20–30 篇 holdout 样本预览。
- 用户确认后生成带版本和 SHA-256 的 `knowledge-profile`。

### D-08：事实层保持统一

用户不能任意改变原文、时间、人员、事实、决策、行动、风险、评论/审批事件和逐字证据引文的基础契约。用户可配置的是实体治理、专题空间、路由、关注、排序、忽略和提醒。

### D-09：一名用户可拥有多个逻辑知识空间

- TBS、SFE、云端虾、通用、待确认、冷归档等均可成为空间。
- 空间可有独立摘要注释、实体视图、索引、日报、风险和行动视图。
- raw 不复制。
- 一篇汇报可多标签进入多个空间，不能强制单选。

### D-10：路由器采用多标签和三态处置

```json
{
  "disposition": "index | archive_no_index | review",
  "space_ids": ["sp_5a92f7c1b3", "sp_7d11ac90ef"],
  "confidence": 0.93,
  "reason_codes": ["confirmed_entity:tbs"],
  "profile_version": "v1"
}
```

- 确定性规则优先，其次是用户确认的实体与别名，最后才是 AI 建议。
- 低置信结果进入 `review`，不得直接丢弃。

### D-11：低价值内容冷归档，不默认物理删除

冷归档内容可不做 AI 精编、不进 Wiki/搜索/日报/行动中心，但保留 raw、基础元数据、哈希和路由理由。正文、评论、审批或状态变化后必须重新路由。物理删除需要单独的保留策略和授权。

### D-12：所有配置和决策可审计、可回滚

必须记录 profile 版本/哈希、AI 建议、用户确认或拒绝、路由原因、实体规则来源、影响范围、重建记录和回滚链路。

## 4. 讨论中形成的关键技术判断

1. 当前 CWK 的自然语言查询已经足以作为多租户改造基线，但不是“任意问题都稳定命中”的承诺。
2. 宿主机查询服务比把共享 raw 整体只读挂载到沙箱更安全：它可以在读取正文前强制执行 Agent→tenant 绑定和 ACL。
3. 如果工作协同只提供个人 AppKey，发现和权限校验仍需每租户执行；物理正文可以去重，但不能宣称“公司只采集一次”。真正单次采集依赖公司级变更流和权威访问关系接口。
4. 评论、审批和附件是否可以共享，不能凭假设决定，必须使用两个身份对共同可见汇报做差异验证。
5. 用户知识空间是逻辑投影，不是完整 raw 副本。
6. 首期不需要向量数据库；现有确定性索引、实体硬范围和证据回读可继续使用。

## 5. 明确不做

- 不在每个沙箱重复安装完整采集系统。
- 不允许用户自己指定 tenant 或 raw 路径。
- 不把不同 workspace 当作权限隔离。
- 不自动物理删除低价值汇报。
- 不允许用户任意修改基础事实 Schema。
- 不未经确认自动合并高影响实体。
- 不让 Agent 自动回复、审批或修改工作协同状态。
- 不在本轮直接切换现有生产 nightly 或迁移真实密钥。

## 6. 待外部验证/决策

1. `report_id` 是否公司级全局唯一；若否，必须带来源命名空间。
2. 同一汇报在两个用户 AppKey 下的正文是否逐字一致。
3. 回复、审批节点、附件元数据和临时下载链接是否因用户不同而变化。
4. 是否有公司级增量变更流、批量访问关系接口和权限撤销事件。
5. 权限撤销目标 SLA、冷归档保留期限和离职删除/转移流程。
6. transport 政策已确定：首期强制 **OpenClaw 受控 Tool**，**UDS + peer credential** 仅作后备，loopback HTTP + 用户自报 `agent_id` 永久禁止；RT-011/G1 冻结该政策、ADR 与保守默认。
   - 待验证的外部能力：目标 Gateway 是否能提供不可伪造元数据、peer credential、限流与 SLA，由 RT-023/VG-D/G5 真实验证；失败必须阻塞试点，不能重新开放 transport 选型。
7. 租户密钥托管与轮换机制。

以上开放项必须由开发计划中的门禁闭合：1～3 由 RT-011/G1 探针并在 RT-016、RT-017 持续验证；4 由 RT-015、RT-022、VG-D；5 与用户离职/转移流程由 RT-026 后的发布活动；6 由 RT-023、RT-024、VG-D；7 由 RT-013，恢复侧由 RT-025。未知状态只能采用 tenant overlay 或 fail closed，不能放宽权限。
