## 1. 交付目标与执行规则

本计划把 PRD 与 DESIGN 拆成四条可独立验证的能力链：

1. **租户安全链**：实例布局、可信 Agent 绑定、凭据边界、访问授权与撤权；
2. **共享证据链**：公司级不可变 Canonical Evidence Store、版本目录与 legacy 影子迁移；
3. **用户知识链**：Knowledge Profile 共创、三态多标签路由、多知识空间投影；
4. **安全查询与运行链**：宿主机调度、Query Broker、沙箱传输、审计、备份恢复与试点切换。

执行规则：

- 每个 RT 必须有独立实现 Agent、独立验收 Agent、需求契约、技术方案、测试与交付验证报告。
- 验收 Agent 只依据公开 CLI/API、产物、负向测试和 receipt 验证，不依赖实现内部函数。
- 验收失败时回到同一实现 Agent 修复，再由同一独立验收 Agent复测；通过后才能合并并进入依赖 RT。
- RT-011 冻结 v1 schema；后续 RT 只能新增版本，不得私自改写已冻结字段语义。
- 所有开发使用临时 `CWK_INSTANCE_ROOT`、fake CWork、双租户恶意夹具；禁止读取真实 AppKey 或修改现有 nightly/生产镜像。
- 任何未知权限、身份、字段归属或撤权状态一律 fail closed。
- 性能与配额不预设虚构数字；RT-024 分别测量 Broker core 与真实沙箱端到端 P50/P95、容量和配额，RT-025 通过 clean-room 恢复实测 RTO/RPO，RT-026 只消费两类基线。

### 2.1 统一 gate receipt 契约（消除"消费者无输入"阻断）

五个 gate 的 receipt 只有一种机读格式和一条精确路径，冻结在中央契约目录
`contracts/gates/`：

| 文件 | 作用 |
| --- | --- |
| `contracts/gates/verification_gate_receipt_v1.schema.json` | `cwk.pr001.verification_gate_receipt.v1`，VG-A～E 唯一 receipt 格式 |
| `contracts/gates/gate_registry_v1.json` | 冻结配置：feeder RT、精确 `receipt_path`、consumer allowlist、每 gate `allowed_prerequisite_ids` |
| `contracts/gates/gate_registry_v1.schema.json` | registry 自身 schema |

- **精确路径**：`gate-receipts/VG-{A..E}/receipt.json`，每个 gate 恰好一份。
- **producer**：gate 自己，且只能在 feeder RT 独立 PASS 之后运行。冻结映射
  VG-A=RT-015、VG-B=RT-018、VG-C=RT-021、VG-D=RT-023、VG-E=RT-025。
- **consumer**：只有 RT-024 与 RT-026，且**只消费、不创建、不补写、不猜测**；
  禁止从 Markdown 叙述推断结论。
- **registry 不含状态**：它是冻结配置，没有 `status`/`conclusion`/`verdict`
  （schema 的 `forbiddenEntryKeys` 结构性禁止）。运行态判定规则唯一：
  `receipt_path` 不存在 ⇒ NOT RUN；存在 ⇒ 状态就是该 receipt 内的
  `status`/`conclusion`。这样跑 VG 不需要改中央 registry。
- **反环（id 空间）**：`prerequisite_refs[].ref_id` 的 pattern 只允许
  `RT-011～RT-025`、`G0～G5`、`VG-A～VG-E`，`G6`/`G7`/`RT-026` 在语法层被排除。
- **反环（秩约束）**：上述 pattern 只界定 id 空间，仍会放行 `VG-B → VG-C`、
  `VG-A → RT-025`/`G5` 这类前向引用。因此每个 gate 在 registry 冻结穷举的
  `allowed_prerequisite_ids`，由三条秩规则推导：①不得引用序号高于自身
  `feeder_rt` 的 RT；②只允许波次顺序中严格更早的 VG，禁自身与后续；
  ③只允许该时点已在上游的 G，**消费本 gate 的 G 必须排除**（G3 消费 VG-A、
  G4 消费 VG-C、G5 消费 VG-D）。另外 `uniqueItems` 只对整个对象去重，故
  **`ref_id` 在单份 receipt 内必须唯一**是独立语义规则：同一 `ref_id` 配不同
  `ref_sha256` 也非法。上限速查：VG-A=RT-015/G0～G2/无 VG；VG-B=RT-018/G0～G3/VG-A；
  VG-C=RT-021/G0～G3/VG-A～B；VG-D=RT-023/G0～G4/VG-A～C；VG-E=RT-025/G0～G5/VG-A～D。
- **VG-A 现状**：机器 receipt 已在 Wave-0 就地生成
  （`gate-receipts/VG-A/receipt.json`），依据是两份已完成独立验收的叙述记录
  加一次新鲜 VG-A 测试运行（75 tests / 0 failed / Python 3.11.14）。
  它固定 `status=pass`、`synthetic=true`、`conclusion=conservative_unknown`——
  **只表示 synthetic gate 通过，不表示真实 authority 可用**。
  它**不能**推迟到 RT-026 去转换：RT-026 要求 VG-A machine receipt 作为前置输入，
  由 RT-026 生成即构成 `VG-A → RT-026 → VG-A` 新环。
- **VG-B～VG-E 现状**：此刻无 receipt 文件 ⇒ 按解析规则为 NOT RUN。这是**当前观测**，
  不是冻结约束：owner RT 独立验收 PASS 后可随时生成各自 receipt，契约测试自动接管
  校验，无需改动中央契约或测试。
- **synthetic 闭合路径（不是死角）**：VG-A 永久 synthetic，因此"任一 hard gate 为 synthetic
  ⇒ 无条件 NO_GO"若无出口就会让 `READY_FOR_G7_REVIEW` 永不可达。
  `contracts/gates/synthetic_closure_map_v1.json` 冻结出口：VG-A 的
  `rerun_allowed=false`、`closure_mode=capability_activation_receipts`，缺口只能由
  **RT-017** 的 `cwork-authority-source` 与 **RT-023** 的 `gateway-identity-transport`
  两份 activation receipt（`capability-receipts/<capability_id>/receipt.json`，
  与 §5.1 SG-00 对应）以合取条件闭合：`status=pass` ∧ `synthetic=false` ∧
  `owner_rt_independent_pass=true` ∧ `conclusion=capability_activated` ∧ hash/artifact
  重算一致；任一不成立即 OPEN ⇒ NO_GO。闭合后 VG-A 仍作为 scoped evidence 与显式生产
  caveat 列出，其 receipt 永不重写。VG-B～VG-E 只能靠**非 synthetic 重跑**（归档旧
  receipt 后发布新 current receipt，永不就地修改），不得借用 VG-A 映射。
- **VG 链可机读遍历**：VG-B～VG-E 每份 receipt 带单调整数 `sequence`（首跑=1，
  archive + current 恰好占满 `1..N`，current 在链尾）与 `supersedes_receipt_sha256`。
  校验器走唯一前缀链，拒绝 gap/fork/orphan/cycle；归档文件名必须等于其自身重算 hash；
  current 必须链接最新归档项。`created_at` 递增只是**辅助**证据，不是唯一排序证明。
  **VG-A 是 pinned legacy exception**：由静态哈希
  `7058a91a1a5d48a8daca2967b77e7cb64cea578fb66ee3b69f3c12ff3e918657` 钉住，无 `sequence`、
  无 supersedes、archive 必须缺席或为空；任何替代 VG-A current 或 VG-A 轮换尝试直接拒绝。
- **activation receipt 有界 TTL 且可续签**：闭包图为每个 capability 冻结

## 24. Gate、Migration 与 Verification 三轴映射

三条轴不可合并：`G0～G7` 是发布门禁，`M0～M5` 是迁移阶段，`VG-A～VG-E` 是波次集成 receipt。

发布门禁的**机器权威**是 `../contracts/gates/release_gate_registry_v1.json`（七条目，配置非状态）
与两份 receipt schema；本节是**派生说明**，冲突以 registry 为准。receipt 落在**独立根**
`release-gate-receipts/`（G1～G6 为 `receipt.json`，G7 为 `authorization.json`），
该根**当前不存在**，因此 **G1～G7 七个条目全部 NOT_RUN**。

发布门禁：

- **G0**：RT-011 之前的**文档评审**门禁。它**不是** registry 的第八个条目——其证据是叙述性
  Markdown，没有 feeder RT、没有测试证据、没有 artifact 哈希集、没有环境绑定，建模成机器条目
  等于让一份 Markdown 冒充可验证门禁。它只作为 ref_id `G0` 出现在 G1 的前置集里，
  满足条件被冻结为 `bootstrap_gate.final_wave0_review_report_path`
  （`../reviews/审核报告-wave0-final.md`）。**该报告当前不存在，故 G1 恒为 NOT_RUN。**
  第四轮报告 `../reviews/审核报告-r4.md` 写在本轮契约整改之前，只保留用于溯源，
  **明确不足以满足 G0**：让一份已被取代的评审去放行 G1，正是这条规则要防的事。
  该报告只能由独立评审者产出，不得作为实现工作的副产物被创建。
- **G1**：RT-011 冻结 v1 契约、安全默认、身份/传输 ADR 与能力探针；真实 transport 合规留到 G5。精确前置集 `{G0, RT-011}`。
- **G2**：RT-012～RT-013 的路径、tenant、binding、credential 测试通过。精确前置集 `{G1, RT-012, RT-013}`——链上每一环只引用其直接前驱释放门禁，G0 的传递性由 G1 承担。RT-012/RT-013 的本轮权威证据只能分别是 Stage-09/Stage-10 候选 commit 的新 `cwk_acceptance_v1` 报告；两份旧报告都是禁止引用的溯源记录，不得用 full-regression 标志或附加 artifact 绕过重新验收。
- **G3**：RT-014～RT-016 的共享对象、授权基础与 legacy 数据级迁移对账通过；VG-A 是前置 receipt，不能替代 RT-016。精确前置集 `{G2, RT-014, RT-015, RT-016, VG-A}`。**范围上限＝数据/迁移级对账**：VG-A 的 receipt 恒为 `synthetic=true`、结论上限 `conservative_unknown`，该上限传染性地压住 G3，因此 G3 绝不构成查询级、运行时级或生产授权级结论。
- **G4**：RT-019～RT-021 + VG-C 的 Profile、路由、多空间及派生清理通过。精确前置集 `{G3, RT-019, RT-020, RT-021, VG-C}`。
- **G5**：RT-022～RT-023 + VG-D 的 Broker、可信 transport、双 ACL、撤权和沙箱越权测试通过。精确前置集 `{G4, RT-022, RT-023, VG-D, CAP:gateway-identity-transport}`。**注意能力激活 receipt 的方向**：它由 RT-023 在其独立 PASS **之后**签发，是 RT-023 的**产出物**；它是 G5 的前置，**绝不是 RT-023 的前置**，反过来就是环。

**前置集是精确相等，不是子集**：每份 release receipt 的 `prerequisite_refs[].ref_id` 多重集必须与 registry 中 `required_prerequisite_ids` 完全一致——少一个会放过被削弱的 gate，多一个会放过被灌水的 gate，两者同样非法。每一项都必须携带**重算**出的引用哈希。

**消费某个 VG 的 release gate 不在该 VG 的上游**：G3 消费 VG-A、G4 消费 VG-C、G5 消费 VG-D、G6 消费全部五个，因此它们分别被排除在对应 VG 的 `allowed_prerequisite_ids` 之外。这与 `gate_registry_v1.json` 的 `release_gate_consumers` 互为精确逆关系，两个文件双向对账。
- **G6**：在 RT-024～RT-026 各自独立 PASS、VG-A～VG-E 全部 PASS、完整回归与恢复演练完成之后，由**新鲜**最终独立验收者签发。G6 消费 RT-026 的 go/no-go 报告与全部前置 receipt；RT-026 自身**不得**把 G6 作为输入或完成前置（否则构成自依赖环）。G6 的精确前置集**重新绑定 G1～G5 全部五个**而不是只引 G5——链式传递会让一个已被撤销或过期的中段门禁悄悄留在结论里，逐个重算哈希才能发现。"新鲜"是**重算**出来的而非自报：校验器扫描磁盘上全部 RT 验收、VG、上游 release gate 与 SG receipt，只要该 verifier 身份出现在任何一份的 producer/verifier 位上即判定不新鲜。G6 结论上限是 `READY_FOR_G7_AUTHORIZATION`，**仍然不是部署授权**，且必须带 `expires_at`（≤30 天）。
- **G7**：G6 签发之后由用户另行授权的 release readiness，才允许部署、注入真实密钥或切换 cron。它**不是一次验证通过**：文件名是 `authorization.json` 而非 `receipt.json`，schema、domain separator 与自哈希字段名都与 G1～G6 不同，因此跨族重放在哈希与字段名两处同时失败。**唯一机器前置恰为 `{G6}`**，不重新消费 RT/VG/G1～G5——授权者只能回答"是否批准部署这个已被验证的候选"，不能回答"这个候选是否已被验证"。必须由**外部信任根**签发：任何项目内 agent / 实现 agent / 验收 agent / go-no-go 评估者 / 测试签名者签的 G7 一律 INVALID。授权范围被钉死在 M4 受控试点（封闭动作枚举、只带租户计数不带租户标识、窗口 ≤30 天、nonce 反重放、恒可撤销且撤销是 append-only 的新签名条目）。**AUTHORIZATION IS NOT EXECUTION**：它只允许操作者执行所列动作，自身不启用任何东西，执行代码必须在每次动作发生时重新校验。
- **RT-026 与 G6/G7 的顺序不可颠倒也不可合并**：`RT-026 独立验收 PASS → 产出终态 → 提交 G6 最终验收 → G6 之后再由用户显式授权 G7`。RT-026 输出的 `READY_FOR_G7_REVIEW` 是一个**已被承认的 v1 命名失误**（名字提 G7、含义指 G6），其规范含义恰为 `READY_FOR_G6_FINAL_ACCEPTANCE`——"可**提交**进入 G6 最终验收"。保留而不改名是因为它已冻结在 `synthetic_closure_map_v1.json` 与可执行断言中，改名等于对冻结契约做无版本破坏。该结论**不授权任何东西**：不签发 G6、不跳过 G6、不请求 G7、也不使 G7 变得可达；渲染成 `G7_AUTHORIZED`/`RELEASE_APPROVED`/`GA_READY` 一律禁止。

迁移阶段：

- **M0**：RT-011 契约与探针。
- **M1**：RT-012～RT-015 租户、身份、共享证据与授权基础。
- **M2**：RT-016 影子导入共享对象。
- **M3**：RT-016 完成数据级 crosswalk 对账；RT-026 在 Broker 可用后完成 legacy/new 查询 diff，二者共同闭合 M3。
- **M4**：仅在 RT-026、VG-A～E、G6 均通过且获得 G7 授权后，对 allowlist 的 2～3 个真实 tenant 启用独立试点 Broker/调度。
- **M5**：真实试点通过后才进入扩大切换与回滚窗口；不属于本开发计划自动执行范围。

VG-A～VG-E 的定义见 §2、§8、§12、§16、§19、§22；它们只证明跨 RT 集成，不替代任何 G 或 M 的业务/发布决策。
