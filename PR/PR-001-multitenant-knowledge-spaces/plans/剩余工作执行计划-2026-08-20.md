## 2. 协作与控制面

1. 每个 RT 使用独立实现会话；高风险实现默认由 Claude Code Opus 在隔离 worktree 完成。
2. 每个候选由未参与实现的 Codex 会话按公开 CLI/API、产物、负向测试与 receipt 独立验收。
3. 主控只在核对 exact candidate SHA、diff 范围、测试、secret hygiene 和默认关闭状态后合入。
4. 验收失败回到同一实现会话做最小修复，再交同一验收会话复测；安全门禁最终再用新鲜验收者复核。
5. 实现者不写 `PASS`；未执行的报告必须明确 `planned / not yet verified`。
6. 并行只允许发生在依赖满足且代码所有权不冲突的目录或模块。

### 4.3 CWork authority

- RT-017 拥有 `AuthorityAdapterV1`、批量关系复核、lease refresh/revoke observation 与签名 authority receipt seam。
- `CWorkAuthorityProviderV1` 的只读 ABI 固定为 `observe_visible(cursor)`、`verify_grant(report_key)`、`consume_revocations(cursor)`；cursor 回退、跳跃或 schema 不明均 fail closed。
- Adapter 只能消费当前 tenant 的 Credential Broker lease；不得接受请求体 tenant/agent/AppKey。
- 只有经过 RT-015 verifier 的 authority receipt 能把 `granted/revalidation_due` 推进为 `active` 或 `revoked`。
- grant/refresh receipt TTL 不得超过 15 分钟，不可续成常驻授权；过期且无法完成权威复核时立即回到 `conservative_unknown`/拒答。
- provider unavailable、响应不完整、签名/时效/subject 不符时保持 `conservative_unknown` 并 fail closed；bounded list 缺项不是撤权。
- 无真实 authority endpoint 时可以完成 fake adapter 的代码与验收，但真实试点和相关 SLA 继续 blocked。

### 4.5 Sampling 与 Profile

- `sample_manifest_v1` 是一份不可变联合 manifest，同时包含 `samples` 与 `holdout`；两集合必须 disjoint。
- `sample_manifest_ref` 与 `holdout_manifest_ref` 必须是同一个 opaque ref，均指向整份联合 manifest；validator 必须验证同一文件与 SHA，禁止指向另一批数据。
- 至少需要 120 篇 active-grant 候选，才能形成最小 100 train + 20 holdout。少于 120 时作业进入 `insufficient_authorized_sample`，不静默缩样、不重复使用样本、不伪造 proposal。
- AI 只在 zero-tool sandbox 读取 evidence bundle；任何禁止字段、坏 JSON、错误 evidence ref 或未覆盖 chunk 都使 proposal fail closed。

### 4.6 RouteDecision 与幂等键

- RT-020 新增 RouteDecision v2 或等价强语义 validator；v1 不改写。
- v2 必须要求非空 `evidence_refs`；`disposition=index` 必须至少包含一个当前 active opaque `space_id`；任何物理删除动作非法。
- 本计划中的 `base32(x)` 一律指 RFC 4648 base32：ASCII 小写、去除 `=` padding，字符集严格为 `[a-z2-7]`；禁止直接使用库函数默认的大写输出。
- `LP(x) = uint32_be(len(UTF8(NFC(x)))) || UTF8(NFC(x))`。
- `route_job_key = "rj_" + base32(sha256(b"cwk-route-job-v1\0" || LP(tenant_id) || LP(report_key) || LP(canonical_sha256) || LP(profile_sha256)))[0:26]`。
- `projection_key = "pj_" + base32(sha256(b"cwk-projection-job-v1\0" || LP(route_job_key) || LP(space_id) || LP(projector_version)))[0:26]`。
- 禁止无边界字符串拼接；测试向量由 RT-020 冻结并供 RT-021 复用。

### 4.7 Knowledge Space

- 首期空间不嵌套；每 tenant 最多 32 个空间。
- 状态固定为 `active | disabled`；disabled 不参与新路由/查询，但不删除 raw/grant/history。
- 创建主体仅允许已确认 Profile activation 或宿主机 admin；沙箱不能直接创建。
- slug 使用 lowercase ASCII `^(?=.{1,32}$)[a-z](?:[a-z0-9-]*[a-z0-9])?$`，禁止尾部 `-`，tenant 内唯一；保留词固定为 `all/shared/raw/system/archive/review`；rename 追加审计且不改变 opaque `space_id`。
- 所有持久化 membership/index/cache/audit 仅使用 opaque `space_id`。

### 4.8 QueryRequest 与预算

- RT-022 新增 QueryRequest v2 或强语义 validator；v1 不改写。
- 缺省 `space_selector` 表示 active profile 的默认 active space 集；显式空数组非法。请求中的 slug 非法。
- 缺省 `include_dispositions=["index"]`；显式空数组非法。
- `time_filter.from <= time_filter.to`；相反区间直接 contract error。

- tenant/agent/path/credential/profile version/epoch 不得由请求体提供；错误对存在/不存在对象保持等价且不回显路径。

**结论上限**：`READY_FOR_G7_REVIEW`，其**规范含义恰为 `READY_FOR_G6_FINAL_ACCEPTANCE`**：
"该候选包可以被**提交**进入 G6 最终验收"。这是一个**已被承认的 v1 命名失误**——名字提 G7、
含义指 G6——保留而不改名，是因为它已冻结在 `synthetic_closure_map_v1.json` 与多处可执行断言中，
改名等于对冻结契约做无版本破坏。因此：面向人的文档必须把它注解为"可提交 G6 最终验收"，
**不得**渲染成 `G7_AUTHORIZED` / `RELEASE_APPROVED` / `GA_READY`。达到该结论**不授权任何东西**，
也不使 G7 变得可达。正确顺序恒为：

```
RT-026 独立验收 PASS
    -> 产出终态 READY_FOR_G7_REVIEW（＝可提交 G6，非授权）
    -> G6 最终验收：由新鲜最终独立验收者签发，RT-026 不签发、不代签、不推断
    -> G7 release readiness：必须在 G6 之后，且必须有 Evan（用户）显式授权
```

#### synthetic gate 的闭合规则（fail-closed，但不是死角）

只要任一被消费的 VG receipt 带 `synthetic=true` 或 `conclusion=conservative_unknown`
（VG-A 即是，且**永久**如此），该限制必须作为**生产 blocker / scoped evidence 显式列出**，
不得被 RT-026 的整体结论掩盖。但"显式列出"不等于"永久无条件 NO_GO"——若没有声明出口，
`READY_FOR_G7_REVIEW` 在 RT-017/RT-023 交付真实能力之后仍然永不可达，那是设计死角。
出口由 `contracts/gates/synthetic_closure_map_v1.json` 冻结，RT-026 机读消费：

1. **VG-A 永不升级、永不重跑、永不重解释。** 已签发 receipt 不得就地编辑或重签；
   任何下游（RT-024/RT-026/G6/G7）都不得把 `synthetic=true`/`conservative_unknown`
   读成更强结论——**能力缺口闭合之后也不行**；VG-A 的 `rerun_allowed=false`，
   receipt 永久冻结、archive 恒空。
2. **缺口只能由单独 owner 的 capability activation receipt 闭合**，
   格式 `cwk.pr001.capability_activation_receipt.v1`，与 §5.1 的 **SG-00** 逐条对应：

   | capability | owner | 路径 |
   | --- | --- | --- |
   | `cwork-authority-source`（CWork 权威 ACL / 撤权源） | **RT-017** | `PR/PR-001-multitenant-knowledge-spaces/capability-receipts/cwork-authority-source/receipt.json` |
   | `gateway-identity-transport`（Gateway 可信身份 / 受控传输） | **RT-023** | `PR/PR-001-multitenant-knowledge-spaces/capability-receipts/gateway-identity-transport/receipt.json` |

   两者都**不在** `gate-receipts/` 下，domain separator 也与 VG receipt 不同，
   两族 receipt 无法互换或冒充。
3. **闭合是合取**：`status=pass` ∧ `synthetic=false` ∧ `owner_rt_independent_pass=true`
   ∧ `conclusion=capability_activated` ∧ `receipt_sha256` 重算一致 ∧ 全部
   `artifacts[].sha256` 与磁盘一致。任一缺失/失效（含 receipt 不存在、schema 不合法、
   自身 synthetic、owner 不符、hash 或 artifact 漂移）⇒ 缺口 **OPEN** ⇒ **NO-GO**。
4. **闭合之后**，VG-A 仍以 scoped evidence + 显式生产 caveat 出现在 go/no-go 报告里，
   只是不再单独构成**永久** blocker。
5. **VG-B～VG-E** 若出现 synthetic receipt，不得借用 VG-A 的映射，只能靠**非 synthetic
   重跑**，或先修订本节与 closure map 显式映射其自己的真实 activation receipt。
   重跑遵循 current/archive 规则：先把被取代 receipt 按字节归档到
   `gate-receipts/VG-{X}/archive/{被取代 receipt_sha256}.json`（append-only、文件名即其
   自身域分隔 hash），再发布 `created_at` 严格更晚的新 current receipt；已签发工件永不
   就地修改。
6. **RT-026 只聚合**：不得创建、补写、猜测任何 activation receipt，不得轮换或归档任何
   gate receipt，不得修改 closure map。文件不存在 = NOT RUN = fail closed，
   永远不能解释为"已激活"或 `N/A`。

**当前评估（现状陈述，不写进机读契约）**：两份 activation receipt 此刻**都不存在**，
故 VG-A 缺口为 OPEN，go/no-go 今天的正确结论是 **NO-GO**。closure map 本身不记录这一观测，
以免 activation receipt 落地当天即陈旧。

### 5.1 Security Gate（SG-00～SG-10）所有权与 RT-026 crosswalk 矩阵

> **本矩阵是派生文档，不是事实来源。** SG-00～SG-10 的**机器权威**是
> `contracts/security/` 下的三个文件：
> `security_gate_registry_v1.json`（冻结 registry）、
> `security_gate_registry_v1.schema.json`（证明 registry 是 config-not-state）与
> `security_gate_receipt_v1.schema.json`（唯一 receipt schema），
> 说明见 `contracts/security/README.md`，可执行校验见
> `tests/test_pr001_security_gate_contracts.py`。
> **两者冲突时以 registry 为准**；下表若与 registry 不一致，应视为本文档待修。

本矩阵是 **RT-026 go/no-go 的第 3 号输入**（见 §4.11 清单），不只是中央计划的说明文字。
硬规则：

1. **RT-026 只聚合，不制造证据。** 它按 registry 声明的 `receipt_path` 逐条读取 owner
   产出的 receipt，校验存在性、claim 集合、覆盖范围与 SHA，然后汇总。RT-026
   **不得**自己补写、推断或代替任何 SG 的 owner 证据。registry 中**不存在**任何
   `status`/`conclusion`/`passed` 等可变字段：状态只能由 receipt 是否存在以及
   receipt 自身的 `status`/`conclusion` 推导。
2. **每个 SG 必须有具名 owner 证据路径**；owner 未交付即该 SG 为 `NOT RUN`，
   go/no-go **fail closed**，不得因为"另一个 RT 大致覆盖了"而放行。反向亦然：
   `security-receipts/` 下出现任何 registry **未声明**的额外 receipt 是硬失败。
3. **路径/symlink/hardlink/TOCTOU 适用性必须显式判定**：要么给出与该 RT **实际文件面**
   相称的 receipt，要么写明 `N/A + reason_code + 理由 + 静态证据`，且**只有 registry 的
   `na_permitted_claim_ids` 明确允许的 claim 才可标 N/A**（当前仅 RT-022 的
   `SGC-022-02`）。**漏项 ≠ N/A**，漏项一律按未覆盖处理。
4. **六类不是四类**：`path_traversal`、`symlink_component`、`symlink_leaf`、
   `hardlink`、`toctou`、`special_file`。`symlink` 拆成 component 与 leaf，因为
   `O_NOFOLLOW` 只防末段；`special_file`（FIFO/设备/socket）与 `hardlink` 分开，因为
   `O_NOFOLLOW` 不拒绝 FIFO。塌缩成一句"已覆盖路径攻击"的 receipt fail closed。
5. **反自依赖**：RT-017～RT-025 在 `rt_independent_acceptance` 阶段签发；RT-026 自己的
   SG-03/SG-10 receipt（`preflight-security`，任务 T026-14）由**独立预检验证者**在
   实现候选 commit 冻结之后、只读 go/no-go 评估器之前签发。评估器所在的
   `go_no_go_evaluation` 阶段**被刻意排除在 `write_phase_allowlist` 之外**，且评估器
   注入自己的 `go_no_go_evaluator_identity` 并重算排除性，因此评估器消费该 receipt
   但**不是它的署名作者**，RT-026 从不依赖自己的输出。
   **该结论的作用域**：这是**接口级署名排除**，不是 OS 级写拒绝。allowlist 是
   声明阶段检查，身份比对是字符串比对，两者都不能证明内核拒绝了该进程的写入。
   OS 级只读执行（可信启动器、启动器签发的运行证明、前后精确成员清单、真实写拒绝
   证据）归口 **AC-026-11**（任务 T026-15a～d），Wave-0 **未**证明。
