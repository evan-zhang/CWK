# 交接包撰写

把**当前这个会话**做过的事整理成一份下一个人拿着就能继续干的文档。

交接包不是工作日志，也不是 RT 的复盘（那是 `retrospective.md` 的活）。它回答的是
**「你现在接手，需要知道什么才不会走弯路」**。

## 调用边界

- **仅用户驱动**：只有用户明确说「帮我做好交接工作」「写个交接包」「交接一下」
  或等价指令时才执行。RT 收口、会话变长、上下文将满时**都不得自动触发**。
- **不替代 RT 复盘**：`retrospective.md` 由独立复盘 Agent 在 RT 关闭前产出，评的是
  这个 RT 做得怎么样；交接包评的是「下一个人怎么接着干」。两者可以互相引用，不能互相替代。
- **一次会话一份**：不要为同一会话反复生成多份。已有交接包需要更新时，改它，不要新建。

## 五步流程

### 第 1 步 · 判断本次会话和 RT 有没有关系

**要做的是「判断」，不是「找到一个 RT」。** 很多会话压根不在做某个 RT——轻量车道的
修补、台账整理、工具改进、纯讨论，都不挂 RT，这是**正常状态而非缺陷**。

- **会话确实在某个 RT 里进行**（分支是 `feature/RT-XXX-*`、在改某个 RT 的文档、
  用户明确说在做某个 RT）→ 关联上，写进 `rt` 字段
- **不在**、或只是顺带提到某个 RT → `rt: none`，别硬凑

判断有困难时按以下顺序探测（**探测结果要在正文里写出依据**）：

```bash
# ① 分支名（最强信号）
git branch --show-current                      # feature/RT-XXX-* → 就是它

# ② 活跃 RT（注意 status 后面常带行内注释，要容忍）
grep -l "^status:[[:space:]]*\(in-progress\|intaking\|decided\|reviewing\)" RT/*/meta.yaml

# ③ 本会话动过的 RT 目录
git log --oneline -20 --name-only | grep -oE "RT/RT-[0-9]+" | sort -u

# ④ 最近提交信息里的 RT 标记
git log --oneline -10 | grep -oE "rt[0-9]+|RT-[0-9]+"
```

三种结果的写法：

| 情形 | frontmatter `rt` 字段怎么填 |
|---|---|
| 明确在某个 RT 里进行 | `RT-143`（单值） |
| 横跨多个 RT | `[RT-143, RT-152]`（列表），正文说清主次 |
| **不属于任何 RT** | `none`，并在 `scope` 里一句话说清这是什么性质的工作 |
| 会话前半段在做某 RT、后半段不挂 | 填那个 RT，并在字段注释或 `scope` 里说明后半段的性质 |

⚠️ **`none` 是一等公民，不是降级选项。** 硬凑一个「看起来相关」的 RT 编号，会把
接手的人引到不相关的 RT 目录里去翻——那比留空更浪费时间。
判断标准很简单：**接手的人去读那个 RT，能读到有用的上下文吗？** 不能就填 `none`。

### 第 2 步 · 查一遍和待办体系有没有关系

**同样是「查一遍」而不是「必须查出东西」。** 有关联就写清楚，确实没有就留空——
纯工具改进、纯讨论类的会话没有台账关联是很正常的。

两个方向都查一下：

```bash
# 本次工作涉及/发现/解决了哪些台账条目
grep -n "^### DI-" RT/_deferred-items.md | tail -20      # 看最新条目
grep -c "^### DI-" RT/_deferred-items.md                 # 总条数（写进正文当基线）

# 相关 RT 的当前状态
grep "^status:" RT/RT-XXX/meta.yaml
```

在 frontmatter 的 `related_items` 里列出关联条目，并在正文里对每条说清**关系类型**：

- `发现` —— 本次工作新发现的问题（已登记为 DI-0XX / 尚未登记）
- `认领` —— 本次工作认领并处理的
- `结清` —— 本次工作做完的
- `受阻于` —— 本次工作被它挡住的
- `同族` —— 同根因、建议一起做的

确实没有关联时，`related_items` 写 `[]`，并在正文一句话说明（例如「本次是纯工具
改进，未触及任何台账条目」）。校验器对空关联只给 WARN 不拦。

⚠️ **若本次工作产生了新问题但还没登记进台账**，交接包里要显式写「**尚未登记**」，
不要写成好像已经在台账里了。参考 `docs/handover/H002-deferred-items-ledger.md`
里记的那起事故：有人宣称转出、台账一个字没写。

### 第 3 步 · 落笔前重新核实现状（**最容易出错的一步**）

交接包最常见的失效是**拿几天前的记忆当现状写**。落笔前必须重跑一遍关键事实：

- 引用的 `file:line` —— **行号会漂移**，实际去看现在长什么样，优先给关键词/符号名
- 引用的 commit hash —— `git log --oneline -1 <hash>` 确认存在且内容对得上
- 声称"已解决/已存在"的问题 —— 能跑命令验证的就跑一遍
- 目录结构、文件是否还在 —— 项目可能已被重构

**把核实结果与工作发生时的差异单独成节**（模板里的 §6）。如果没有差异，也要显式写
「落笔前已复核，无变化」。

### 第 4 步 · 按模板撰写

**先定类型**（frontmatter 的 `kind`）：

- `session` —— 工作过程交接：「我做了什么、下一个人接着做什么」。**默认选它**，
  八节缺一不可。
- `operations` —— 运维手册交接：「这个系统怎么运维」（怎么部署、怎么健康检查、
  出事怎么办）。结构由内容决定，**不套用八节**——强行套会把一份好用的手册改坏。


模板：[templates/handover-template.md](templates/handover-template.md)
格式规范（frontmatter 字段与必需章节的完整定义）：
[references/format-contract.md](references/format-contract.md)

**落点**：`docs/handover/H<三位序号>-<主题>.md`，例如
`docs/handover/H004-search-subsystem-rework.md`

命名三条：

1. **`H` + 三位序号**开头——`H` 表交接文档，序号让人一眼看出顺序与总量，也便于口头
   指代（「看 H002」）。
2. **不带日期**——序号已给出顺序，日期在 frontmatter 的 `created` / `last_verified`
   里，不会丢；文件名短了更好读。
3. **不带 `handover`/`handoff` 字样**——目录名已经表达了。

**取号前必须先查号（不可跳过）**：

```bash
bash .aodw-next/skills/handover-pack/scripts/next-number.sh
```

⚠️ **为什么要有这一步**：本仓库刚因人工取号出过两次事故——DI-013/014 在分支上占了号，
合并时整块丢失，4 天后才靠翻 git 历史找回；DI-013 与 DI-047 是同一问题隔 9 天被登记
两次。取号脚本会**同时扫工作区与全部分支**（含未合并的），把这两类坑一并挡掉。

写作要求见 `docs/handover/README.md` 的「写交接文档的约定」，核心四条：
带 frontmatter、落笔前重核现状并单列差异节、引用要能复算、文件名不带 handover 字样。

### 第 5 步 · 机械校验（**不可跳过**）

```bash
# 从 AODW 源跑（任何装了 .aodw-next/ 的项目都可用，推荐）
python3 .aodw-next/skills/handover-pack/scripts/validate.py docs/handover/<你的文件>.md

# 若本项目已用 install-skills.sh 安装到宿主 skill 目录，这条也等价
python3 .agent/skills/handover-pack/scripts/validate.py docs/handover/<你的文件>.md
```

校验器检查：frontmatter 必需字段齐全、`rt` 字段格式合法、必需章节都在、
引用的 commit hash 真实存在、文档内链接指向的文件真实存在。

**校验不过就不算写完。** 这条是本 skill 唯一的机械落点——没有它，格式规范会变成
又一份没人遵守的文档。

> 拿模板本身去跑校验会报 3 条 FAIL（`YYYY-MM-DD`、`RT-XXX` 都是占位符）——这是预期的，
> 模板就是给人填的。填完就该全过。八个必需章节模板已齐，不会报缺章节。

写完后还要做两件人工检查（脚本查不了）：

1. 把 §5「下一步」的每一条读一遍，问：**接手的人照着这条能直接动手吗？**
   不能就补具体到文件/命令的信息。
2. 把 §6「现状变化」读一遍，问：**如果我是接手的人，读完这节会不会被误导？**

### 第 6 步 · 关会话前跑闭合检查（**最容易忘的一步**）

```bash
bash .aodw-next/skills/handover-pack/scripts/check-closure.sh docs/handover/H0XX-*.md
```

它比对交接包引用的最新 commit 与当前 HEAD，列出还没被记进去的提交。

⚠️ **为什么单列一步**：交接包写完后往往还会继续干活（用户提新需求、顺手修个问题），
它立刻就不再覆盖 HEAD。这个坑在 handover-pack 自己的开发过程里**连续踩了三次**，
每次都靠人工比对才发现。

**交接包的最后一次同步，必须是会话的最后一个动作。** 若检查报出缺口：
与本会话相关的补进「现状变化」一节；与本会话无关的（并行会话的提交）可忽略，
但要在交接包里说明忽略了什么，否则接手的人无从判断。

## 收尾

写完后：

- 把新文档挂进 `docs/handover/README.md` 的「现有文档」表（不进索引等于没建）
- 若这是项目里第一份某类交接包，考虑同时更新 `docs/README.md` 的索引
- 提交时**只 add 你自己改的路径**，禁 `git add -A`——本仓库常有并行会话，
  暂存区是共享的

## 常见错误（都是实际发生过的）

| 错误 | 后果 | 怎么避免 |
|---|---|---|
| 拿记忆当现状写 | 接手的人照着过期坐标找不到东西 | 第 3 步，落笔前重跑 |
| 只给行号不给关键词 | 行号漂移后引用失效 | 给符号名/关键词，或注明「用 X 搜」 |
| 声称"已转出/已登记"但没验证 | 账凭空消失，现场还留着假记录 | 落盘后 grep 实证，别信自己的自述 |
| 硬凑一个「看起来相关」的 RT | 误导接手的人去翻不相关的 RT 目录，比留空更费时间 | 问自己：接手的人读那个 RT 能读到有用上下文吗？不能就填 `none` |
| 把交接包写成流水账 | 接手的人读完仍不知道从哪下手 | §5 每条都要能直接动手 |
