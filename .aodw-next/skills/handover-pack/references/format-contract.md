# 交接包格式契约

> 本文件定义交接包的**强制格式**。校验器 `scripts/validate.py` 按本文件实现，
> 两者不一致时以校验器实际行为为准——**改规则先改校验器**，否则规则又变成一纸空文。

## 一、Frontmatter（YAML，必须是文件第一行开始）

```yaml
---
title: <一句话说清这是什么工作的交接包>
status: active | superseded | archived
kind: session | operations
created: YYYY-MM-DD
last_verified: YYYY-MM-DD
owners: [<项目或团队标识>]
rt: RT-143 | [RT-143, RT-152] | none
related_items:
  - DI-033: 结清
  - DI-013: 发现
  - RT-152: 同族
scope: >
  两三句话说清：这份交接包覆盖哪段工作、给谁看、读者最该先看哪一节。
related:
  - RT/_deferred-items.md          # 相关文件，带一句注释说明为什么相关
  - .aodw-next/tools/rt-guard.sh
---
```

### 字段定义

| 字段 | 必需 | 取值 | 说明 |
|---|---|---|---|
| `title` | ✅ | 字符串 | 一句话。不要只写主题名，要说清「是什么的交接包」 |
| `status` | ✅ | `active` / `superseded` / `archived` | 被新交接包取代时改 `superseded` 并在正文首行指向新的那份 |
| **`kind`** | ✅ | `session` / `operations` | **决定正文章节要求**。`session`＝工作过程交接（「我做了什么、下一个人接着做什么」），八节缺一不可；`operations`＝运维手册交接（「这个系统怎么运维」），结构由内容决定、**不套用八节**——强行套会把一份好用的手册改坏 |
| `created` | ✅ | `YYYY-MM-DD` | 首次落笔日期 |
| `last_verified` | ✅ | `YYYY-MM-DD` | **最后一次核实正文事实的日期**，不是最后一次编辑日期。只改错别字不更新此字段 |
| `owners` | ✅ | 列表 | 项目或团队标识，随宿主项目而定 |
| **`rt`** | ✅ | `RT-XXX` / 列表 / `none` | 本次会话是否在某个 RT 里进行。**字段必须存在，但 `none` 是完全正当的取值**——不挂 RT 的会话（轻量车道、工具改进、纯讨论）是常态。填 `none` 时在 `scope` 一句话说清工作性质。**禁止硬凑「看起来相关」的编号**：判断标准是「接手的人去读那个 RT，能读到有用上下文吗」 |
| **`related_items`** | ✅ | `编号: 关系` 列表 | 与台账条目/其它 RT 的关联。**确实没有关联时写 `[]` 即可**（纯工具改进、纯讨论很常见），正文一句话说明即可，校验器只给 WARN 不拦 |
| `scope` | ✅ | 多行字符串 | 覆盖范围 + 读者 + 先读哪节 |
| `related` | ✅ | 路径列表 | 关键文件，每条带注释说明为什么相关 |

### `related_items` 的关系类型（封闭枚举）

| 关系 | 含义 |
|---|---|
| `发现` | 本次工作新发现的问题（若尚未登记进台账，正文必须显式写「尚未登记」） |
| `认领` | 本次工作认领并正在处理的 |
| `结清` | 本次工作做完的 |
| `受阻于` | 本次工作被它挡住的 |
| `同族` | 同根因、建议一起做的 |

## 二、正文必需章节（仅 `kind: session`）

标题层级用 `##`，编号与措辞可微调，但**这七节缺一不可**（校验器按关键词匹配）：

| # | 章节 | 必须回答 |
|---|---|---|
| 0 | **一句话** | 不看别的，只读这段能知道发生了什么 |
| 1 | **做了什么** | 按时间或主题列，每项带 commit hash |
| 2 | **怎么做的、怎么查的** | **方法论，比结论更值得复用**。用什么命令查的、踩过什么坑 |
| 3 | **要解决什么问题** | 为什么做这件事。没有这节，接手的人会把手段当目的 |
| 4 | **发现了什么问题** | 实证结论 + 证据（file:line / 命令输出 / commit） |
| 5 | **下一步做什么** | **每条都要能直接动手**：改哪个文件、跑什么命令、预期什么结果 |
| 6 | **现状变化** | 落笔前重新核实的结果，与工作发生时的差异。无差异也要显式写 |
| 7 | **接手清单** | 照着做的操作步骤，含环境陷阱预警 |

推荐再加一节「相关提交索引」（表格：commit → 内容），便于接手的人回溯。

## 三、引用的写法

| 类型 | 写法 | 反例 |
|---|---|---|
| 代码位置 | `` `file.py` 的 `func_name()`（当前约 `:123`，搜 `关键词` 定位） `` | 只写 `file.py:123`——行号会漂移 |
| 提交 | `` `abc1234` `` + 一句话说明它做了什么 | 只贴 hash |
| 命令 | 可直接复制粘贴运行的完整命令 + 预期输出 | 「跑一下测试」 |
| 数据结论 | 数字 + 怎么算出来的 | 「有很多」「大部分」 |

## 五、文件命名

`docs/handover/H<三位序号>-<主题>.md`

- `H` + 三位序号（`H001`、`H002`…）：标识交接文档、给出顺序与总量、便于口头指代
- 不带日期：序号已给顺序，日期在 frontmatter 的 `created` / `last_verified` 里
- 不带 `handover`/`handoff` 字样：目录名已表达

**取号必须用脚本**（不可目测 `ls`）：

```bash
bash .aodw-next/skills/handover-pack/scripts/next-number.sh
```

它扫工作区 + 历史提交 + **全部分支（含未合并）**三处。只看工作区会重蹈本仓库
DI 编号的两次覆辙：跨分支占号后合并丢失、同一问题被重复登记。

## 四、校验

```bash
python3 .aodw-next/skills/handover-pack/scripts/validate.py <文件路径>
```

退出码：`0` 通过 / `1` 有必须修的问题 / `2` 用法错误。

校验器只能查机械项（字段齐全、格式合法、引用可达）。**它查不了的两件事必须人工过**：

1. §5 的每一条，接手的人照着能不能直接动手；
2. §6 读完会不会被误导。
