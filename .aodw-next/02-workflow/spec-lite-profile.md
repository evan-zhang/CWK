# 实现路径

和宪法打架时，听宪法。这份文件说明：批准之后，你如何自己把活做完。

先把实现拆成可验证阶段，内部维持待办。每阶段结束检查：结果是否在仓库里、是否覆盖已批准的目标、还缺什么证据。对人只报阶段结论，不播报每次工具调用。范围内的读取、修改、验证连续做完。

---

## 阶段

**1. 在 `main` 上占号，随即建 worktree**

`main` 上只提交 `meta.yaml`（编号、标题、状态），几秒钟的事，目的是让编号对并发会话
可见。提交完立刻建 worktree：

```bash
git worktree add -b feature/RT-XXX-short-name .claude/worktrees/RT-XXX-short-name main
```

**2. 在 worktree 里写 `rt-lite.md`**

先写给人看的判断：做什么、为什么、代价、不做什么、用户怎样算成功、关键假设。
实现备注放后面。

`rt-lite.md`、方案讨论、调查记录、评审往返和实现**全部在 worktree 里做**，不写在
`main` 上——理由见宪法「交付形态」：并发会话共用 `main` 的暂存区，方案阶段改动最密，
最容易把别人的文件卷进自己的提交。落点表以 `git-discipline.md`「在哪改」为准。

**3. 方案门**

用人话展示建议和成功标准，问做不做。没批准不改业务文件。

**4. 实现**

遵守 `AGENTS.md`。范围不超出已批准的方案。功能分支提交自己做。

**5. 自己验收**

跑匹配的检查。改了界面，在浏览器里按真实路径点一遍。
逐条对照成功标准。测试绿了但目标没达成，就还没完。

**6. 收口门**

用人话证明目标达成。有遗留事项就一并说：不进本次、为什么、准备放进需求池。
列出只保留分支、只在本地合并、合并并推送清理三种动作的影响，给出推荐。不要把 diff 当验收。
用户选定后按 `git-discipline.md` 收口；遗留事项写入 `RT/_deferred-items.md`，编号记进 `meta.yaml.deferred_items_raised`。RT 状态和分支信息只更新 `meta.yaml`。

事情变大了仍用这一份文件，把判断写清楚。

## rt-lite.md

```markdown
# RT-Lite: [RT-ID] - [任务标题]

> profile: Spec-Lite | execution_mode: collaborative

## 方案（给人看）

- 做什么：
- 为什么：
- 代价：
- 这次故意不做什么：
- 用户怎样算成功：
- 建议：（定论 / 推荐 / 倾向，一句话理由）

## 假设与现状

- 关键假设：
- 现状依据（文件 / 历史 RT / 提交）：

## 实现备注（用户不问可不展开）

- 计划改的文件：
- 不能破坏的约定：
- 内部阶段：（可验证的几步）

## 验证

- 要跑的检查 / 要点的界面路径：
- 对照成功标准的结果：

## 变更记录

- 用户能感到什么变化：

## 遗留事项

- （没有就写「无」。有则每条：什么问题、为何不在本次做、建议以后怎么处置）
```

收口时文件里要有「变更记录」四个字，机械检查会搜。也可从 `templates/rt-lite.template.md` 拷。
