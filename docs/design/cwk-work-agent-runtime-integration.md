# CWK Work Agent 备用执行池接入方案

> 状态：设计草案，未批准实施
> 记录日期：2026-08-31
> 适用对象：`cwk_cloud_wiki_compile.py` 的单篇工作协同汇报精编
> 方法来源：`bd-eval-loop` Work Agent 运行时规范（源提交 `08b0523c9457da9f59235e48e22227f369502ac6`）

## 1. 结论

CWK 可以新增一条 **Work Agent 备用执行池**，以独立账号或独立配额的 Codex CLI
作为首个运行时。它的作用是提高**整体可用并发**，并承接长文本、格式异常、主池重试
失败等难例；它不替换现有零工具 `cwk-ai-reviewer`，也不让任何 Worker 自行派生
subagent。

只有当 Work Agent 使用独立配额时，这个方案才会提高真实吞吐。若仍走现有 GLM/NewAPI
同一限流池，只是把 Python 线程换成 Agent 进程，排队和 429 不会消失。

本文件只冻结设计与验收方式，不授权实现、开通运行时、修改生产配置、接触真实原文、
发布或推送。

## 2. 背景与目标

CWK 当前的精编宿主负责选取原始汇报、调用专用 AI reviewer、核验引用与原文 SHA、
写入摘要和 manifest。现有 reviewer 是零工具 JSON transformer，安全边界清楚，但其
模型池的可用并发会受到账户级限流影响。

本方案新增一个可替换的执行层，而不改变事实底座：

```text
原始 raw（唯一事实源）
        │
        ▼
CWK 精编宿主：选择、冻结、限流、验收、落盘
        ├── R0：现有零工具 reviewer（默认主路径）
        └── R1：Work Agent 备用池（独立 runtime / 独立配额）
                    │
                    ▼
             只返回合同 JSON + 运行回执
        │
        ▼
宿主逐条核验 JSON、raw SHA、引文命中与路径边界
        │
        ▼
正式 summary / manifest，或 fallback / retry queue
```

目标是：在不削弱事实核验和数据边界的前提下，提供第二条可审计、可限流、可回退的
执行路径。

## 3. 设计原则

1. **事实合同稳定，执行者可替换。** Worker 不拥有事实真相；原始 `raw/`、引用核验和
   manifest 仍由宿主控制。
2. **一个冻结任务包只交给一个 Worker。** 并发由宿主拆分任务、控制上限并留回执；
   Worker 禁止启动 subagent、task、agent delegation 或递归执行器。
3. **默认最小权限。** Work Agent 不读取 CWK 工作区，不写 summary/manifest，不调用
   CWork、DocDB、Discord、浏览器、搜索、MCP 或 Skills；输入经 stdin，结果仅从 stdout
   返回。
4. **先候选、后采纳。** PoC 和试运行输出写入隔离 candidate 目录，宿主验收通过后才可
   由人工决定是否接入正式精编。
5. **配额和成本是运行时属性。** 每种 runtime 独立登记认证来源、并发上限、单位预算、
   超时和退避策略；宿主不假设模型名、工具语义或上下文窗口相同。
6. **失败不等于补写。** Worker 输出不合格时只进入 retry/fallback；宿主不让另一个模型
   悄悄改写或拼接事实。

## 4. 路由分类与编码

现有精编流程保持原分类，在它上面叠加两个维度：任务画像和执行路线。编码是后续
manifest、验收和告警共同使用的稳定引用，不替代已有 `report_id`。

### 4.1 任务画像（`T`）

| 编码 | 条件 | 首选路线 | 说明 |
|---|---|---|---|
| `T0` | 常规短汇报，当前主路径一次成功 | `R0` | 成本最低，保持现状。 |
| `T1` | 超长、多事项、结构复杂，但原文完整 | `R0` 或 `R1` | 根据容量闸门选择，必须记录选择理由。 |
| `T2` | 主路径格式失败、引用不足或达到一次可重试失败 | `R1` 候选 | Work Agent 只重做该冻结任务包。 |
| `T3` | 原文缺失、SHA 不一致、引用核验失败、权限/数据边界异常 | `H0` 人工/宿主处置 | 不得交给任何 Worker 继续“猜”。 |

### 4.2 执行路线（`R`）

| 编码 | 运行时 | 使用条件 | 是否可写正式摘要 |
|---|---|---|---|
| `R0` | 现有 `cwk-ai-reviewer` | 现有生产默认路径 | 是，沿用现有宿主验收。 |
| `R1` | Codex Work Agent（首个 PoC） | 独立配额已验证，且通过相应准入门 | 否；PoC/影子期只能写 candidate。 |
| `R2` | 后续已准入的 Claude/OMP/xAI 等 | 单独完成同等准入与数据边界审查 | 否，直到另一次采纳决定。 |
| `H0` | 宿主 fallback / 人工处理 | 任何硬失败或边界异常 | 否。 |

`T` 表示任务事实条件，`R` 表示宿主选择的执行者；两者不能混成“模型质量等级”。
例如 `T2 → R1` 只意味着需要独立重做，不代表 R1 的内容天然更可信。

## 5. 冻结任务包与输出合同

### 5.1 输入包：`CWK-TP-v1`

宿主在启动 Worker 前生成不可变任务包，至少包含：

- `task_id`、`report_id`、`attempt`、`route`、`prompt_version`、`schema_version`；
- 原文正文及其 `raw_sha256`；
- 原文相对来源标识、创建时间、作者、标题等已有元数据；
- 明确的 JSON 输出 schema、允许字段、引文格式和禁止行为；
- 本次 runtime 的时间预算、token/成本预算、无工具声明和 deadline；
- 只读输入文件清单的哈希，供回程核验。

任务包不能包含 CWork/DocDB/Discord/GitHub 凭据、整个项目目录、其他汇报、隐藏评测
答案或生产 manifest。真实原文只在受控本地临时目录与模型请求链中流转，不进入仓库、
日志、回执或外部搜索工具。

### 5.2 输出包：`CWK-WO-v1`

Worker 的 stdout 只能包含一个 JSON 对象：

- `report_id`、`task_id`、`raw_sha256`、`prompt_version`、`runtime_id`；
- 当前精编 schema 所需的摘要、事项、实体、证据引用；
- `worker_self_check`（仅声明，不取代宿主验证）；
- `runtime_receipt`：开始/结束时间、实际模型、退出状态、受限工具声明、token/成本若可得；
- `error` 或 `abstain_reason`，当它无法满足合同。

stdout 外的文本、多个 JSON 对象、未声明模型、`report_id`/SHA 不一致、无法解析的字段，
均按合同失败处理。stderr 仅供宿主诊断，不可作为事实或生成摘要的输入。

## 6. 三层责任边界

```text
CWK 宿主
  ├─ 选择 T 类、冻结 CWK-TP-v1、全局/每池并发闸门
  ├─ runtime adapter 选择、超时、终止、重试、候选目录
  ├─ JSON / raw SHA / 引文逐条核验、正式落盘和 manifest
  └─ 可观测性、成本累计、fallback 和人工升级
          │
          ▼
Thin Runtime Adapter
  ├─ stdin / stdout 合同转换
  ├─ 临时空目录、净化环境、进程组超时/终止
  └─ 标准化 runtime receipt；不解释业务事实
          │
          ▼
Work Agent
  ├─ 仅处理一份已冻结输入
  ├─ 只生成合同 JSON
  └─ 不读项目、不写项目、不派生 Agent、不调用外部工具
```

这与 bd-loop 的“宿主控制拓扑、Worker 自主完成冻结工作单元”相同，但 CWK 的事实安全
要求更严：bd-loop 的章节 Worker 可在授权范围研究与调用工具；CWK Worker 初期是无工具
结构化转换器，不得搜索或访问其他数据。

## 7. 生命周期、权威记录与例外

### 7.1 任务状态机

| 状态 | 进入条件 | 允许流转 | 推进者 | 超时/例外 |
|---|---|---|---|---|
| `S0 selected` | 宿主选择原文候选 | `S1` / `SX` | 宿主 | 原文不存在或年份/范围不符 → `SX`。 |
| `S1 frozen` | `CWK-TP-v1` 与 SHA 生成成功 | `S2` / `SX` | 宿主 | 任务包哈希不完整 → `SX`。 |
| `S2 dispatched` | Adapter 成功启动一个 Worker | `S3` / `SR` / `SX` | Adapter | 到 deadline 由宿主终止；Worker 不决定重试。 |
| `S3 candidate_validated` | JSON、SHA、路径、引文全部通过 | `S4` / `SR` | 宿主验证器 | 任一错引或合同不符 → `SR` 或 `SX`。 |
| `S4 committed` | 正式 summary/manifest 已由宿主写入 | 终态 | 宿主 | 仅已批准的生产路由可进入。 |
| `SR retry_queued` | 可恢复 runtime/格式失败 | `S1` / `SX` | 宿主调度器 | 受每路线最大尝试次数约束。 |
| `SX blocked` | 硬失败、边界异常或终态重试耗尽 | 人工/既有 fallback 流程 | 宿主 | 不得自动转交其他 Agent 猜测。 |

### 7.2 权威数据源（SoR）

| 数据/状态项 | 当前权威来源 | 目标权威来源 | 更新方式 | 转抄风险 |
|---|---|---|---|---|
| 原始事实 | `raw/` 原文 | 不变 | 只读镜像采集 | 摘要不能替代原文。 |
| 输入任务合同 | 本次 `CWK-TP-v1` | 运行目录的带哈希任务包 | 宿主一次生成 | 不得由 Worker 回写。 |
| 候选结果 | 隔离 candidate 输出 | 受控 run receipt | Adapter 追加 | 不可直接视为正式摘要。 |
| 引文是否成立 | 宿主对 raw 的逐条校验 | 不变 | 确定性验证器 | Worker 自检不具有权威性。 |
| 正式摘要与进度 | `wiki/summaries/` 与 manifest | 不变 | 宿主串行落盘 | 禁止 Adapter/Worker 写入。 |
| 运行成本与并发 | 宿主 receipt / quota ledger | 统一 runtime ledger | 宿主记录 | CLI 自报数据需标明缺失或估算。 |

### 7.3 熔断规则

- 出现任何错引、SHA 不一致、路径越界、凭据泄露迹象、未声明的工具/网络调用或子 Agent
  派生时，立即终止该路线的后续任务并标记 `SX blocked`。
- Work Agent 的连续基础设施失败达到未来 RT 冻结的阈值时，关闭 `R1` 路由，退回 `R0/H0`；
  不自动改模型、放宽权限或提高并发。
- 运行时成本、时延或失败率超过阈值时，宿主停止派发并生成回执，等待人工判断。

## 8. 职责矩阵

R = 负责执行；A = 最终拍板；C = 需咨询；I = 被告知。

| 机制/环节 | CWK 宿主 | Runtime Adapter | Work Agent | Evan | 后续人工审阅者 |
|---|---|---|---|---|---|
| 任务分类、冻结与并发 | R | I | I | A | I |
| runtime 身份、配额和预算配置 | R | C | I | A | I |
| 单篇 JSON 生成 | I | C | R | I | I |
| 引文/SHA/路径机械核验 | R | I | I | I | C |
| 候选质量抽检与准入结论 | R | I | I | A | C |
| 正式路由、生产配置、发布/推送 | R（执行已批准项） | I | I | A | C |
| 安全或事实边界熔断 | R | R（终止进程） | I | A | I |

## 9. 分阶段验收门

下表是建议门槛。实现 RT 启动时应把运行时、样本哈希、预算和确切阈值冻结为测试合同；
未冻结前不得宣称任何路线“可生产”。

| 门 | 目标 | 建议基线与目标 | 验收方式 | 未达标处理 |
|---|---|---|---|---|
| `G0` | 合同与隔离 | 100% 任务包含 ID/SHA/schema；0 个越界写入/工具调用 | 单元测试、临时目录审计、净化环境检查 | 不启动真实模型。 |
| `G1` | 单 Worker 冒烟 | 20 篇分层样本；100% JSON/SHA 合同通过；0 错引 | 影子 candidate 跑 + 宿主逐条校验 | 修 Adapter/提示词，不开并发。 |
| `G2` | 真实容量与质量对照 | 50 篇保留分层样本；引用 100% 可回溯；覆盖与可读性不低于 `R0` 基线 | 双路线盲抽检、P95/成本/重试率回执 | 仅保留为研究路线或关闭。 |
| `G3` | 小流量候选路由 | 初始并发 1；无边界事件；实际独立配额使总吞吐提升 | 受限比例影子/候选运行 | 停止 `R1`，保留回执复盘。 |
| `G4` | 正式采纳决定 | Evan 审阅完整结果后明确批准 | 独立验收报告与最小 Git diff | 另开实施 RT；未批准不改生产。 |

其中“0 错引”是硬门槛；质量更好、速度更快或成本更低都不能抵消一次错引。

## 10. 首个适配器：Codex 的限定方案

第一轮只评估 Codex，一次性进程而非持久 Agent 会话。理由是它具备独立登录/配额的可能，
且当前机器已有 CLI 与 ACP 一次性入口。实际接入需在 `G0` 验证以下前提：

- 能把 prompt/任务包通过 stdin 或只读临时文件传入，并稳定取得唯一 JSON stdout；
- 能在空白临时目录内运行，净化 CWK、CWork、DocDB、Discord 与 GitHub 相关环境变量；
- 能显式禁止或实际验证不存在搜索、浏览器、MCP、Skills、subagent、写文件和网络工具面；
- 能记录实际模型、实际启动参数、开始/结束时间、退出码和资源用量；
- 宿主可以在超时后终止整个进程组，不留下孤儿进程。

Claude Code、OMP、xAI/Grok 和 OpenClaw 可作为 `R2` 候选，但每种都需独立做同样的
工具面、身份、凭据、并发、真实样本和成本准入。特别是 OMP 的已知 Skills/MCP 暴露面
不能因其“可用”而省略隔离验证。

## 11. 后续实现范围（尚未批准）

若 Evan 说“按此实施”，应新建一个实施 RT，而不是直接在当前批量精编脚本上修改。建议
顺序如下：

1. 固化 `CWK-TP-v1` / `CWK-WO-v1` schema、hash、receipt 和错误分类；
2. 新建 `cwk_work_agent_runtime.py` 与 Codex thin adapter，输出仅进入 candidate 目录；
3. 复用现有 JSON、raw SHA、逐条引文和 manifest 验证器，不复制第二套事实判断；
4. 增加全局互斥锁、per-runtime 并发/预算闸门、退出清理和结构化 receipt；
5. 建立 20/50 篇脱敏样本与保留集，完成 `G0–G2`；
6. 只有 `G2` 通过后，讨论 `G3/G4` 及是否采纳到正式精编路由。

## 12. 明确不做

- 不修改 `cwk-ai-reviewer` 的 `skills=[]`、工具全拒绝或既有模型池；
- 不让 Work Agent 直接读取/写入 CWK 项目、raw、summary、manifest、DocDB 或 cron；
- 不把 Codex/Claude/OMP/xAI 作为相互自由调度的 Agent 网络；
- 不把 Work Agent 当作绕开数据授权、供应商审查或模型限流的办法；
- 不把 PoC 成功自动等同于生产启用、GitHub 推送或配置变更；
- 不在本方案阶段承诺吞吐倍数、单篇成本或供应商可用性。
